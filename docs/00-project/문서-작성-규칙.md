# 문서 작성 규칙

> Threadia 프로젝트의 모든 문서 작성 기준이다.  
> AI 도구가 문서를 생성·수정할 때도 이 규칙을 따른다.  
> 이 문서는 `docs/` 문서 구조와 작성 규칙의 canonical 위치다.

---

## 1. 기본 원칙

- `docs/00-project/문서-작성-규칙.md`를 단일 기준으로 둔다.
- `docs/README.md`, `docs/AGENTS.md`, `docs/CLAUDE.md`는 이 문서를 안내하는 보조 문서다.
- `docs/01-planning/`은 기획주간 raw archive다. 기획 종료 후에는 원본 보존을 기본으로 하고, 최종본은 canonical 폴더로 복사·승격한다.
- 하나의 문서는 하나의 주제를 다룬다.
- 확정 문서는 직접 수정하지 않고, 수정이 필요하면 `최종 수정`, `버전`, `상태`, 변경 이력을 갱신한다.
- 회의록, 결정 기록, Sprint 운영 문서, 개인 작업 기록은 서로 섞지 않는다.

---

## 2. 폴더 구조와 용도

```text
docs/
├── 00-project/                  프로젝트 공통 규칙과 운영 기준
│   └── sprint-운영/              Sprint/주차 계획, TODO, 리스크, 회고
├── 01-planning/                 기획주간 raw archive, 회의 전 자료, 분업 산출물, 검토 기록
├── 02-requirements/             사용자 시나리오, 기능 분해표, 요구사항, 추적표
├── 03-design/                   화면정의서, 화면 흐름, ERD
├── 04-api/                      API 명세서, error code, request/response 예시
├── 05-architecture/             Architecture, 인증/인가 구조, 인프라, 기술 연구
├── 06-meetings/                 실제 회의록과 회의 Action Item
├── 07-decisions/                ADR, 확정 결정, 보류 기능, 변경 이력
├── 08-members/                  팀원별 개인 작업 기록
└── assets/                      공용 이미지, 다이어그램, PDF, PPTX 등 첨부 자료
```

### 00-project

프로젝트 전체에 적용되는 운영 기준을 둔다.

- 문서 작성 규칙
- 팀 운영 규칙
- Definition of Done
- 검증 방법
- AI 사용 규칙
- CI 기준
- PR Template
- Sprint 운영 문서

`sprint-운영/`에는 주차별 계획, TODO, 리스크, 회고를 둔다. 회의에서 실제로 오간 발언과 결정 기록은 `06-meetings/` 또는 `07-decisions/`로 분리한다.

### 01-planning

기획주간 자료의 원본 보관소다.

- 0~6일차 원본 자료
- 회의 전 자료
- 분업 산출물
- 중간본, 검토본, 정합도 보정본
- 발표 준비 자료

기획 종료 후 `01-planning/` 자료는 읽기 전용 archive로 취급한다. 최종 산출물은 원본을 보존한 채 각 canonical 폴더로 복사한다.

### 02-requirements

제품 요구사항과 범위 기준을 둔다.

- 사용자 시나리오
- 기능 분해표
- 요구사항 목록
- 기능-시나리오-API-ERD 추적표
- Sprint 범위표

### 03-design

화면과 데이터 설계 기준을 둔다.

- 화면정의서
- 화면 흐름
- UI/UX 참고
- ERD

### 04-api

API 계약을 둔다.

- API 명세서
- endpoint 목록
- error code
- request/response 예시
- Postman/curl 검증 기준

### 05-architecture

기술 구조와 연구 문서를 둔다.

- System Architecture
- AWS architecture
- 인증/인가 구조
- 실시간, 알림, 검색, 파일 저장 등 기술 연구
- 기술 비교와 도입 근거

### 06-meetings

실제 회의록만 둔다.

- 파일명: `YYYY-MM-DD-회의-제목.md`
- 구조: 참석자 → 안건 → 결정 사항 → Action Item
- 회의 전 준비 자료나 주차별 TODO는 이 폴더에 두지 않는다.

### 07-decisions

확정된 결정 기록을 둔다.

- ADR
- scope 결정
- 보류 기능 최종표
- 기획문서 변경 이력
- 팀 합의로 확정된 정책

ADR 파일명은 `ADR-NNN-제목.md` 형식을 사용한다.

### 08-members

팀원별 개인 작업 기록을 둔다.

```text
08-members/
└── member-XX/
    ├── 개발-진행사항.md
    ├── 기술-연구/
    └── 포트폴리오/
        ├── 기여-내역.md
        └── 트러블슈팅.md
```

- `member-01` ~ `member-06` 폴더를 사용한다.
- 본인 폴더 외 타인 폴더는 수정하지 않는다.
- AI가 멤버 문서를 작성할 때는 해당 멤버 본인의 요청이 있어야 한다.

## 3. 최종 산출물 승격 규칙

기획주간 최종 산출물은 `01-planning/` 원본을 보존하고, canonical copy를 아래 기준으로 둔다.

| 산출물 유형 | 대상 폴더 |
|---|---|
| 사용자 시나리오, 기능 분해표, 추적표 | `02-requirements/` |
| 화면정의서, ERD | `03-design/` |
| API 명세서 | `04-api/` |
| 기술 연구, Architecture | `05-architecture/` |
| DoD, 검증 방법, AI/CI/PR 규칙 | `00-project/` |
| Sprint 계획, Sprint TODO, Sprint 리스크, Sprint 회고 | `00-project/sprint-운영/` |
| 보류 기능, 변경 이력, 확정 scope 결정 | `07-decisions/` |
| 발표 자료, 이미지, PDF, PPTX | `assets/` |

원본과 canonical copy가 둘 다 존재할 때, 개발주간 이후의 참조 기준은 canonical copy다.

---

## 4. 파일명 규칙

- 파일명은 kebab-case를 기본으로 한다.
- 한국어 파일명을 허용한다.
- `API`, `ERD`, `PR`, `CI`, `AI`, `DoD`, `JWT`, `OAuth` 같은 기술 용어와 약어는 대문자를 유지할 수 있다.
- 파일명에 날짜와 버전을 임의로 붙이지 않는다.
- 버전과 상태는 문서 상단 메타정보 또는 변경 이력에 기록한다.
- 문서는 `.md`를 기본으로 한다.
- 이미지, PDF, PPTX 등 첨부 자료는 `assets/`에 둔다.

---

## 5. 문서 상단 메타정보

새 문서는 최상단에 아래 메타정보를 둔다.

```markdown
> **작성자**: Threadia 팀  
> **작성일**: YYYY-MM-DD  
> **최종 수정**: YYYY-MM-DD  
> **버전**: v1.0  
> **상태**: 작성 중 | 검토 중 | 확정
```

- 기존 문서가 YAML frontmatter를 사용하면 기존 형식을 유지해도 된다.
- `상태`가 `확정`인 문서는 수정 전 팀 합의나 사용자 확인이 필요하다.
- 확정 문서를 수정하면 `최종 수정`, `버전`, 변경 이력을 함께 갱신한다.

## 6. 문체 규칙

| 항목 | 규칙 |
|---|---|
| 기본 언어 | 한국어 |
| 종결 어미 | `~다` 체 |
| 기술 용어 | 영어 원문 유지 |
| 영어 약어 | 첫 등장 시 필요하면 풀어서 병기 |
| 코드·명령어 | 인라인 코드 블록 사용 |
| 단위 표기 | ms, KB, Mbps 등 국제 표준 단위 사용 |

## 7. AI 작업 규칙

### 반드시 지킬 것

- 대상 파일을 먼저 읽고 수정한다.
- `01-planning/` 원본 archive는 명시 요청 없이 수정하지 않는다.
- 최종본 승격은 이동보다 복사를 우선한다.
- 상태가 `확정`인 문서는 수정 전 확인한다.
- 타인의 `08-members/member-XX/` 문서는 해당 멤버 요청 없이 수정하지 않는다.
- 새 문서 생성 전 같은 이름의 파일이 있는지 확인한다.
- 변경 후 diagnostics 또는 Markdown 검사를 수행한다.

### 하지 말 것

- 문서 내용 없이 폴더만 생성하지 않는다. 단, `.gitkeep`은 예외다.
- 회의록이 아닌 Sprint TODO를 `06-meetings/`에 넣지 않는다.
- 확정 결정이 아닌 논의 메모를 `07-decisions/`에 넣지 않는다.
- 한 문서에 여러 주제를 섞지 않는다.
- secret, token, password, 개인정보를 문서에 기록하지 않는다.
