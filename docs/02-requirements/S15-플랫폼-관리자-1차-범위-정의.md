> **작성자**: Threadia 팀  
> **작성일**: 2026-07-07  
> **최종 수정**: 2026-07-18
> **버전**: v1.5 WBS 4.10.4 Backend 완료 기준
> **상태**: 검토 중

## 1. 문서 목적

이 문서는 S15 플랫폼 관리자 콘솔의 1차 기능 범위를 정의한다. 기존 canonical 문서에서 `F/S15`는 보류 상태였으므로, 이 문서는 바로 구현 착수 문서가 아니라 WBS `3.7~3.7.5` planning gate를 거쳐 공식 WBS `4.10`으로 이어지는 기획 기준이다.

권한 모델의 기준은 `docs/07-decisions/플랫폼-관리자-인가-모델-결정.md`를 따른다.

## 2. 범위 결정 요약

| 항목 | 결정 |
|---|---|
| 화면 | S15 플랫폼 관리자 콘솔 |
| 사용자 | F 플랫폼 관리자 |
| 권한 모델 | `platform_admins` 기반 |
| 1차 핵심 | 고객센터 문의, 신고 처리, 사용자 정지, 회사 비활성화, 운영 로그, 시스템 설정 |
| 문의/신고 모델 | `support_cases`로 묶고 `type = INQUIRY / REPORT`로 구분 |
| 상태 변경 정책 | 삭제 금지, 상태 변경 중심 |
| Audit | 관리자 조치마다 reason과 audit log 필수 |
| 정책 상태 | WBS `4.10.4` Backend lifecycle/audit-read는 구현됐다. 사용자/회사 enforcement, S15 Frontend, retention/cleanup과 나머지 운영 확장은 후속 범위다. |

### 2.1 WBS 4.10.1 구현 승인 범위

WBS `4.10.1`은 위 1차 후보 전체가 아니라 support case Backend vertical slice와 이를 안전하게 실행하기 위한 platform authorization/audit foundation만 구현한다.

| 포함 | 제외 |
|---|---|
| `platform_admins`, support case 접수·조회·답변·내부 메모·상태 전이, mutation audit, 최초 `SUPER_ADMIN` bootstrap | 사용자/회사 enforcement, 시스템 설정, platform admin grant/revoke, dashboard, notification, Frontend |

플랫폼 관리자 API는 `/api/v1/platform` namespace를 사용한다. 일반 사용자의 case 생성과 본인 case 조회는 `/api/v1/support-cases`를 사용한다. `COMPANY_ADMIN`과 `PROJECT_ADMIN`은 platform authorization 근거가 될 수 없다.

## 3. S15 정보 구조

S15는 단순 대시보드가 아니라 플랫폼 운영 콘솔로 정의한다.

```text
S15 플랫폼 관리자 콘솔
├── 대시보드
├── 고객센터 문의/신고
├── 사용자 관리
├── 회사 관리
├── 시스템 설정
└── 운영 로그
```

## 4. 1차 기능 목록

| 영역 | 1차 기능 | 설명 |
|---|---|---|
| 대시보드 | 운영 현황 요약 | 신규 문의, 처리 중 신고, 정지 사용자, 비활성 회사, 최근 관리자 조치 요약 |
| 고객센터 문의 | 문의 접수 목록 | 사용자가 남긴 문의를 플랫폼 관리자가 확인한다. |
| 고객센터 문의 | 문의 답변 | 플랫폼 관리자가 답변을 작성하고 상태를 변경한다. |
| 신고 처리 | 신고 접수 목록 | 사용자, 회사, 프로젝트, 콘텐츠 관련 신고를 확인한다. |
| 신고 처리 | 신고 상태 변경 | 접수, 처리 중, 조치 완료, 반려 등으로 처리 상태를 관리한다. |
| 사용자 관리 | 사용자 조회 | 전체 사용자 목록과 상태를 확인한다. |
| 사용자 관리 | 사용자 정지 | 정책 위반 사용자를 `SUSPENDED`로 전환한다. |
| 회사 관리 | 회사 조회 | 전체 회사 목록과 상태를 확인한다. |
| 회사 관리 | 회사 비활성화 | 운영 정책 위반 또는 요청에 따라 회사를 비활성화한다. |
| 시스템 설정 | 운영 설정 관리 | 고객센터와 신고/제재 운영에 필요한 설정을 관리한다. |
| 운영 로그 | 관리자 조치 조회 | 플랫폼 관리자의 조치 이력을 조회한다. |

## 5. 고객센터 문의/신고 범위

문의와 신고는 하나의 case 개념으로 관리한다.

| 항목 | 기준 |
|---|---|
| 공통 개념 | `support_cases` |
| 유형 | `INQUIRY`, `REPORT` |
| 상태 | `OPEN`, `IN_PROGRESS`, `RESOLVED`, `REJECTED`, `CLOSED` |
| 담당자 | 플랫폼 관리자 |
| 답변 | 문의와 신고 모두 처리 메모 또는 사용자-facing 답변을 가질 수 있다. |
| 조치 연결 | 사용자 정지, 회사 비활성화 등 운영 조치와 연결할 수 있다. |

### 5.1 문의 처리

| 기능 | 설명 |
|---|---|
| 문의 접수 | 사용자가 고객센터 문의를 생성한다. |
| 문의 분류 | 문의 카테고리와 우선순위를 지정한다. |
| 관리자 답변 | 플랫폼 관리자가 답변한다. |
| 상태 변경 | 처리 상태를 변경한다. |
| 결과 알림 | 작성자에게 처리 결과를 알리는 정책은 후속 알림 설계에서 확정한다. |

### 5.2 신고 처리

| 기능 | 설명 |
|---|---|
| 신고 접수 | 사용자가 사용자, 회사, 프로젝트, 콘텐츠를 신고한다. |
| 신고 검토 | 플랫폼 관리자가 신고 대상과 사유를 검토한다. |
| 조치 실행 | 필요 시 사용자 정지 또는 회사 비활성화를 수행한다. |
| 반려 | 신고 근거가 부족하면 반려한다. |
| 처리 기록 | 신고 처리 결과와 조치 사유를 기록한다. |

### 5.3 WBS 4.10.1 상세 계약

| 항목 | 계약 |
|---|---|
| 상태 전이 | `OPEN→IN_PROGRESS/REJECTED/CLOSED`, `IN_PROGRESS→RESOLVED/REJECTED/CLOSED`, `RESOLVED→CLOSED`, `REJECTED→CLOSED`만 허용한다. `CLOSED`는 terminal이며 reopen하지 않는다. |
| 신고 대상 | `REPORT`는 `USER`, `COMPANY`, `PROJECT`, `CONTENT` target type과 nullable UUID target ID를 가진다. 다형성 FK나 target domain 검증은 추가하지 않는다. |
| 사용자 가시성 | 인증 사용자는 case를 생성하고 본인 case 목록·상세와 public reply만 읽는다. 다른 사용자의 case는 노출하지 않는다. |
| 관리자 가시성 | `PLATFORM_ADMIN`, `SUPER_ADMIN`은 전체 case 목록·상세, public reply 생성, internal note 생성·조회, 상태 변경을 수행한다. |
| reply/note 경계 | public reply는 관리자만 작성한다. internal note는 사용자 조회 query와 DTO에서 구조적으로 제외한다. |
| Audit reason | case 생성, public reply, internal note, 상태 변경은 body와 별개의 nonblank reason을 요구하며 trim 후 3~500자다. |
| 원자성 | mutation과 immutable `admin_action_audits` 저장은 같은 transaction에서 처리하며 audit 실패 시 mutation도 rollback한다. |
| 최초 관리자 | singleton bootstrap lock row를 transaction에서 선점한 뒤 `platform_admins`가 비었을 때만 환경변수 email을 기존 email 정규화로 조회해 ACTIVE 사용자 1명을 `SUPER_ADMIN`으로 등록한다. email 누락·형식 오류·불일치·비활성 사용자는 startup 실패다. 기존 관리자가 있거나 다른 instance가 먼저 생성했으면 환경변수 변경과 무관하게 no-op이다. |

Notification, hard delete, 사용자·회사 enforcement, 시스템 설정, grant/revoke API는 WBS `4.10.1`에 포함하지 않는다.

## 6. 사용자 정지와 회사 비활성화

| 대상 | 정책 | 영향 |
|---|---|---|
| 사용자 | `SUSPENDED` 상태로 전환 | 로그인, token refresh, `/auth/me` 성공 조건에서 제외한다. |
| 회사 | `INACTIVE` 상태로 전환 | 모든 회사 및 하위 프로젝트 read와 mutation 접근을 차단하고 사용자 회사 선택기에서 숨긴다. platform admin의 운영 접근은 유지한다. |

물리 삭제는 1차 범위에 포함하지 않는다. 정지와 비활성화는 반드시 사유를 요구하며 audit log에 남긴다.

## 7. 시스템 설정 1차 범위

시스템 설정은 전체 인프라 설정이 아니라 아래 전체 운영 설정 catalog로 제한한다. 각 설정은 key별 code-owned schema/validator, JSON value, versioning을 사용하는 typed catalog로 저장한다.

| 설정 | 포함 여부 | 설명 | 변경 권한 |
|---|---|---|---|
| 문의 카테고리 | 포함 | 계정, 회사, 프로젝트, 버그, 기타 등 문의 분류 | `SUPER_ADMIN` |
| 신고 사유 카테고리 | 포함 | 스팸, 사칭, 악성 콘텐츠, 권한 오남용 등 신고 사유 | `SUPER_ADMIN` |
| 제재 사유 preset | 포함 | 반복적으로 사용하는 정지/비활성화 사유 | `SUPER_ADMIN` |
| 제재 기간 preset | 포함 | 1일, 7일, 30일, 무기한 등 운영 기준 | `SUPER_ADMIN` |
| 답변 템플릿 | 포함 | 반복 문의 답변 템플릿 | `SUPER_ADMIN` |
| 공지/점검 배너 | 포함 | 전체 사용자에게 노출하는 공지 또는 점검 안내 | `SUPER_ADMIN` |
| 고객센터 운영 상태 | 포함 | 문의 접수 가능, 점검 중, 응답 지연 안내 | `SUPER_ADMIN` |
| 처리 결과 알림 on/off | 포함 | 문의 답변과 신고 처리 결과 알림 정책 | `SUPER_ADMIN` |

구체 설정 key 이름, catalog의 schema 저장 구조, version 충돌 처리, 변경 절차와 API 계약은 후속 구현 설계에서 결정한다.

### 7.1 시스템 설정 제외 범위

| 제외 항목 | 제외 이유 |
|---|---|
| DB/인프라 설정 | 운영 UI에서 변경하면 장애 위험이 크다. |
| OAuth provider on/off | 인증 정책과 연결되어 별도 보안 결정이 필요하다. |
| 전역 feature flag | 서비스 전체 기능 중단 위험이 있어 별도 release/ops 정책이 필요하다. |
| 가입 제한/도메인 제한 | 보안 정책 성격이 강해 별도 계정 정책 문서가 필요하다. |

## 8. 운영 로그 범위

운영 로그는 플랫폼 관리자 조치의 감사 원장이다.

| 기록 대상 | 예시 |
|---|---|
| 문의/신고 처리 | 답변 작성, 상태 변경, 담당자 변경 |
| 사용자 조치 | 사용자 정지, 정지 해제 |
| 회사 조치 | 회사 비활성화, 비활성 해제 |
| 시스템 설정 | 문의 카테고리 변경, 제재 preset 변경, 공지 배너 발행 |
| 권한 관리 | 플랫폼 관리자 권한 부여 또는 회수 |

운영 로그는 사용자 알림, 활동 피드, 시스템 로그와 구분한다. audit record는 3년간 보존하며 password, token, secret, message/case body 원문은 payload에 넣지 않거나 마스킹한다. `4.10.4` Backend는 platform admin의 keyset audit-read와 read-side allowlist redaction을 제공한다. S15 Frontend, 보존 종료 cleanup/purge, legacy migration은 후속 범위다.

## 9. 권한별 액션 범위

| 액션 | `PLATFORM_ADMIN` | `SUPER_ADMIN` |
|---|---:|---:|
| 문의 목록 조회 | 가능 | 가능 |
| 문의 답변 | 가능 | 가능 |
| 신고 처리 | 가능 | 가능 |
| 사용자 정지 | 가능 | 가능 |
| 회사 비활성화 | 가능 | 가능 |
| 운영 로그 조회 | 가능 | 가능 |
| 시스템 설정 조회 | 가능 | 가능 |
| 시스템 설정 변경 | 불가 | 가능 |
| 플랫폼 관리자 권한 부여/회수 | 불가 | 가능, reason과 immutable audit 필수 |
| 공지/점검 배너 발행 | 불가 | 가능 |

platform admin authority의 grant/revoke, reactivate, role change는 `SUPER_ADMIN`만 수행할 수 있다. 마지막 활성 `SUPER_ADMIN`의 revoke 또는 demote는 금지한다. lifecycle Backend는 구현됐으며 승인 workflow와 S15 Frontend는 후속 설계에서 결정한다.

## 10. 1차 범위에서 제외하는 기능

| 기능 | 제외 이유 |
|---|---|
| 결제/구독 관리 | 현재 요구사항과 ERD에 기반이 없다. |
| 고급 통계/BI | 데이터 축적 이후 별도 대시보드로 분리한다. |
| 실시간 상담 채팅 | 고객센터 case 처리와 범위가 다르다. |
| 관리자 조직/부서 관리 | 플랫폼 운영 조직 규모가 커진 뒤 필요하다. |
| 자동 제재 rule engine | 오탐 위험이 있어 수동 조치부터 시작한다. |
| DB/인프라 runtime 설정 | 장애 위험이 커서 운영 UI 범위에서 제외한다. |

## 12. 착수 조건

S15 구현 착수 전 아래 조건을 충족해야 한다.

1. Sprint 1.5 company invitation과 `company_members` 생성 흐름이 안정화되어야 한다.
2. Sprint 2 Company/RBAC foundation이 구현되어야 한다.
3. `SecurityConfig`의 실제 인증/인가 적용 방향이 확정되어야 한다.
4. `platform_admins`, `support_cases`, audit log 데이터 설계가 확정되어야 한다.
5. 확정된 시스템 설정과 운영 로그 정책을 구현할 catalog, audit, authorization 설계와 API 계약이 필요하다.
