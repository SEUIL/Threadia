# 허브 실시간 채팅 + 3D 아바타 설계

> 개인 기술 연구 노트다. S03 3D 사무실 메인 허브에 실시간 채팅을 추가하되,
> 일반 2D UI에서도 되고 **3D 공간의 아바타 위에 말풍선으로도** 보이게 만드는
> 방향을 기획한다. "기술적으로 가능한 건 아는데 정확한 방식을 확실히 정해두고
> 싶다"는 요청에서 시작했다.
>
> **⚠️ 이 문서는 설계 초안이다.** 아직 팀 합의나 실제 백엔드 도메인 착수 전
> 단계이고, 화면정의서 S03에는 이 기능이 정의돼 있지 않다(신규 확장 제안).
> 구현 착수 전 팀 논의와 최신 라이브러리 버전 재확인이 필요하다.

## 1. 문제 제기와 범위 확정

### 1-1. 범위 결정 사항 (2026-07-04 논의)

| 항목 | 결정 | 근거 |
|---|---|---|
| 아바타 이동 방식 | **Phase 1: 고정 자리(desk)만 구현**. 자유이동(멀티플레이어 실시간 위치 동기화)은 Phase 2로 미룬다 | 자유이동은 위치 동기화·보간·전용 채널이 필요해 구현 범위가 훨씬 커진다. 고정 자리로 먼저 검증하고 여유가 되면 확장하는 게 리스크가 낮다 |
| 채팅 채널 성격 | **Phase 1: 허브/로비 전용 새 채널**. 기존 프로젝트 채팅·DM을 3D로 시각화하는 방향은 참고만 해두고 채택하지 않는다 | 기존 `messages`(project_id 필수), `direct_messages`(room_id 필수) 테이블에 회사 단위 로비 개념이 안 맞는다. 새 채널이 데이터 모델도 깨끗하고 화면 책임도 명확하다 |

### 1-2. 기존 문서와의 관계

- 화면정의서 S03에는 현재 "채팅/DM 진입"만 정의돼 있고, 허브 자체에 채팅
  기능은 없다 — 이번 설계는 **S03의 신규 확장 제안**이다.
- 기획 6일차 자료(`API-명세서.md` §12 "6일차 이월 기술 검토")에 **"메시지 목록
  실시간 업데이트 방식"이 미결정 항목으로 남아있었다.** 이번 설계가 그 미결정
  사항에 대한 첫 구체안이기도 하다.
- 실시간 push 방식 자체는 이미 활동 피드(§10.1 조건부 확장 API)에서
  **STOMP push topic** 패턴으로 선례가 있다(`/topic/projects.{projectId}.activity`).
  이번 설계는 그 패턴을 채팅에도 일관되게 확장하는 방향으로 잡았다.
- 3D 아바타의 가변 정보(이름, 말풍선) 표현 방식은 기존
  [3D 오피스 렌더링 연구](./3d-오피스-렌더링-연구.md) §2-4에서 이미
  "drei `<Html>` 오버레이로 분리" 결론이 나 있어 그대로 재사용한다.

## 2. 전체 아키텍처

```
[클라이언트 A]                    [백엔드]                     [클라이언트 B]
                                     |
  STOMP CONNECT  ─────────────────▶ WebSocket 세션 등록
  (SockJS handshake)                 |
                                     |
  SEND /app/hub-chat.send  ────────▶ HubChatService
  { companyId, content }             |  1) MySQL INSERT (hub_chat_messages)
                                     |  2) SimpMessagingTemplate으로 브로드캐스트
                                     |
                          ◀───────── SUBSCRIBE /topic/companies.{id}.hub-chat
  SUBSCRIBE 응답 수신                |                              SUBSCRIBE 응답 수신
  (신규 메시지 payload)              |                              (신규 메시지 payload)
       |                                                               |
       ├─ 2D 채팅 패널에 append                                        ├─ 2D 채팅 패널에 append
       └─ 3D 아바타 위 <Html> 말풍선 표시(수 초 후 자동 소멸)             └─ 동일하게 3D 말풍선 표시
```

핵심 원칙: **채팅 시스템은 하나, 렌더링만 두 가지(2D 리스트 / 3D 말풍선)다.**
같은 STOMP 토픽과 같은 REST 히스토리 API를 두 렌더러가 동시에 구독하는
구조로 만들어서, 채팅 로직을 이중으로 유지하지 않는다.

## 3. 실시간 전송 계층 — STOMP over WebSocket

### 3-1. 왜 STOMP인가 (다른 옵션과 비교)

| 방식 | 장점 | 단점 | 채택 여부 |
|---|---|---|---|
| **STOMP over WebSocket** | Spring이 `spring-boot-starter-websocket`으로 1급 지원. pub/sub(topic 구독) 모델이 채팅에 자연스럽게 맞음. 기존 activity feed와 패턴 통일 | 순수 WebSocket보다 프레이밍 오버헤드 약간 있음(무시 가능한 수준) | **채택** |
| 순수 WebSocket (raw) | 가장 가볍다 | 채널 구독/브로드캐스트를 직접 구현해야 함 — STOMP가 이미 해주는 걸 재발명하는 셈 | 비채택 |
| Server-Sent Events(SSE) | 구현 간단 | 단방향(서버→클라이언트)이라 채팅 전송(클라이언트→서버)은 별도 REST POST 필요, 양방향 실시간엔 부적합 | 비채택 |
| 폴링(Short polling) | 인프라 추가 없음 | 말풍선처럼 "즉시성"이 중요한 UX엔 지연이 체감됨 | 비채택(초기 프로토타입에서만 임시로 고려 가능) |

### 3-2. 백엔드 구성

- 의존성 추가: `spring-boot-starter-websocket` (현재 `build.gradle`에 없음 —
  신규 추가 필요).
- `@EnableWebSocketMessageBroker` + `WebSocketMessageBrokerConfigurer` 구현체
  하나 신설.
- **Broker**: 팀 규모(6명, 회사 1곳 기준)로는 Spring 내장
  **simple in-memory broker**(`enableSimpleBroker("/topic")`)로 충분하다.
  기존 activity feed 문서의 "Redis는 조건부 확장" 원칙과 동일하게, 백엔드
  인스턴스가 여러 대로 늘어나 브로커 상태 공유가 필요해지는 시점에만
  Redis/RabbitMQ 기반 STOMP relay로 전환을 검토한다(현재는 불필요).
- **Endpoint**: `/ws` (SockJS fallback 포함) 하나로 통일하고, 그 안에서
  destination(`/app/...`, `/topic/...`)으로 기능을 구분한다 — 기능마다
  엔드포인트를 새로 만들지 않는다.
- **인증**: 기존 JWT access token을 STOMP CONNECT 프레임의 헤더(예:
  `Authorization: Bearer ...`)로 실어 보내고, `ChannelInterceptor`에서
  CONNECT 시점에 검증한다. HttpOnly 쿠키는 JS가 못 읽으므로 WebSocket
  핸드셰이크에는 access token(메모리 보관 중인 값)을 명시적으로 실어야 한다.

### 3-3. Destination(토픽) 명명 규칙

기존 activity feed 패턴 `/topic/projects.{projectId}.activity`와 통일한다.

| 용도 | Destination |
|---|---|
| 허브 채팅 메시지 브로드캐스트 구독 | `/topic/companies.{companyId}.hub-chat` |
| 허브 채팅 메시지 전송(클라이언트→서버) | `/app/hub-chat.send` (body에 `companyId` 포함) |
| (Phase 2 예약) 위치 동기화 브로드캐스트 | `/topic/companies.{companyId}.presence.positions` |

### 3-4. 프론트 구성

- 라이브러리: `@stomp/stompjs` + `sockjs-client` 신규 추가(현재
  `package.json`에 없음).
- `contexts/AuthContext.tsx`가 이미 access token을 메모리로 갖고 있으니,
  STOMP client 생성 시 `connectHeaders: { Authorization: `Bearer ${token}` }`로
  그대로 재사용한다.
- 커넥션 관리(연결/재연결/구독 해제)는 커스텀 훅(`useHubChat` 같은)으로
  캡슐화해서, 2D 채팅 패널과 3D 말풍선 컴포넌트가 같은 훅을 각자
  `useHubChat(companyId)`로 불러 쓰게 한다(§2의 "하나의 소스, 두 렌더러"
  원칙을 코드 레벨에서 강제).

## 4. 데이터 모델

### 4-1. 새 테이블: `hub_chat_messages`

기존 `messages`(project_id 필수 FK), `direct_messages`(room_id 필수 FK) 둘 다
"회사 단위 로비"라는 스코프를 표현할 수 없어 새 테이블이 필요하다.

```sql
CREATE TABLE hub_chat_messages (
    id             BIGINT   NOT NULL AUTO_INCREMENT,
    company_id     BIGINT   NOT NULL,
    author_user_id BIGINT   NOT NULL,
    content        TEXT     NOT NULL,
    created_at     DATETIME NOT NULL,
    PRIMARY KEY (id),
    KEY idx_hub_chat_company_created (company_id, created_at, id),
    KEY idx_hub_chat_author (author_user_id),
    CONSTRAINT fk_hub_chat_company FOREIGN KEY (company_id) REFERENCES companies (id)
        ON DELETE RESTRICT ON UPDATE RESTRICT,
    CONSTRAINT fk_hub_chat_author FOREIGN KEY (author_user_id) REFERENCES users (id)
        ON DELETE RESTRICT ON UPDATE RESTRICT
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

`messages`/`direct_messages`와 구조·명명 규칙을 그대로 따라 팀 컨벤션과
통일했다(`author_user_id`, `created_at`, 인덱스 패턴 등).

### 4-2. REST API (히스토리 조회 — 원장 조회는 WebSocket이 아니라 REST로)

기존 activity feed 원칙("push는 신호만, 클라이언트는 REST로 재조회")을
그대로 따른다.

| Method | Endpoint | 설명 |
|---|---|---|
| GET | `/api/v1/companies/{companyId}/hub-chat/messages` | 최근 메시지 목록(페이지네이션) |
| POST | `/api/v1/companies/{companyId}/hub-chat/messages` | 메시지 전송(REST 경로도 열어둠 — WebSocket 미연결 시 폴백, 또는 STOMP `/app/hub-chat.send`가 내부적으로 같은 서비스 메서드 호출) |

MySQL이 원장이라는 원칙(활동 피드와 동일)을 유지하므로, WebSocket 연결이
끊겨도 REST로 최신 히스토리를 다시 불러오면 데이터 정합성은 깨지지 않는다.

## 5. 3D 아바타 + 말풍선 구현

### 5-1. 아바타 배치 (고정 자리, Phase 1)

- 회사 구성원 목록(`company_members`)을 사무실 내 책상 좌표 배열에 순서대로
  매핑한다. 이미 `OfficeFloor.tsx`에 책상 위치가 있으니, "구성원 N번째 →
  책상 N번째" 정도의 단순 인덱스 매핑으로 시작한다.
- 아바타 자체의 3D 형태는 이번 설계 범위 밖이다(간단한 도형/캡슐이든 Kenney
  캐릭터 에셋이든, 시각 디자인은 별도로 다룬다) — 이 문서는 "말풍선과 채팅
  파이프라인"에 집중한다.

### 5-2. 말풍선 — `@react-three/drei`의 `<Html>` 재사용

[3D 오피스 렌더링 연구](./3d-오피스-렌더링-연구.md) §2-4에서 이미 결론
내린 방식을 그대로 쓴다.

```tsx
// 개념 스케치 — 실제 구현 시 파일/네이밍은 재검토
<Html position={[avatar.x, avatar.y + 1.2, avatar.z]} center distanceFactor={8}>
  {latestMessage && !expired && (
    <div className="chat-bubble">{latestMessage.content}</div>
  )}
</Html>
```

- `<Html>`은 3D 좌표를 화면 2D 좌표로 자동 투영해주는 drei 컴포넌트라,
  카메라가 움직여도 말풍선이 아바타를 계속 따라다닌다 — 텍스트를 3D
  geometry/텍스처에 베이킹할 필요가 없다.
- 말풍선 노출 시간: 메시지 수신 후 고정 시간(예: 6~8초) 뒤 자동 소멸시킨다
  (게더타운류 UX). 타이머는 클라이언트에서 `setTimeout`으로 처리하고 서버
  상태와는 무관하게 둔다(순수 프레젠테이션 로직).
- 동시 표시 인원(팀 규모 최대 수십 명 기준)에서 `<Html>` 오버레이 개수가
  성능에 영향을 주는지는 3D 렌더링 연구 문서의 "구현 착수 전 재확인 목록"에
  이미 있는 항목이라 그대로 승계한다.

### 5-3. "누가 지금 허브에 있는가" (presence) — Phase 1에서는 단순화

- 진짜 온라인/오프라인 추적(WebSocket CONNECT/DISCONNECT 브로드캐스트)은
  Phase 2(자유이동)로 미룬다.
- Phase 1에서는 **회사 구성원 전원의 아바타를 항상 표시**하고(자리 배치만
  보여줌), 말풍선은 실제로 메시지를 보낸 사람에게만 그 순간 잠깐 뜨는
  방식으로 단순화한다. "온라인 상태 점" 같은 presence UI는 이번 범위에
  넣지 않는다.

## 6. 단계별 구현 순서 제안

| 단계 | 내용 | 비고 |
|---|---|---|
| 1 | 백엔드: `hub_chat_messages` 테이블 + WebSocket 설정 + REST 히스토리 API + STOMP 전송 핸들러 | 신규 도메인 하나(`hubchat` 패키지 정도) |
| 2 | 프론트: `useHubChat` 훅(STOMP 연결/구독/전송 공통 로직) | 2D/3D 공통 사용 |
| 3 | 프론트: 허브 오버레이에 2D 채팅 패널 UI 추가 | 가장 먼저 검증 가능한 형태(3D 없이도 실시간 채팅 자체는 확인 가능) |
| 4 | 프론트: 3D 아바타 + `<Html>` 말풍선 | 2D가 안정된 뒤 같은 데이터 소스에 렌더러만 추가 |
| (보류) | Phase 2: 자유이동, 실시간 위치 동기화, 진짜 presence | 시간 남으면 재검토 |

2D 패널을 먼저 만들면 "채팅 파이프라인 자체가 도는가"를 3D 렌더링 이슈와
분리해서 검증할 수 있어 디버깅이 쉬워진다.

## 7. 구현 착수 전 재확인할 것

- [ ] `spring-boot-starter-websocket`, `@stomp/stompjs`, `sockjs-client`의
      구현 시점 최신 버전과 breaking change 여부.
- [ ] STOMP CONNECT 시 JWT 검증 방식(헤더 vs 쿼리 파라미터) — 쿼리 파라미터에
      토큰을 실으면 로그에 노출될 위험이 있어 헤더 방식을 우선 검토.
- [ ] 팀 규모가 커졌을 때 in-memory broker의 한계(다중 인스턴스 배포 시
      브로커 상태 미공유) — 지금은 단일 인스턴스라 문제없음.
- [ ] `<Html>` 말풍선 동시 표시 개수가 실제 3D 씬 성능에 주는 영향(3D 렌더링
      연구 문서 §3-1 재확인 목록과 동일 항목).
- [ ] 이 기능이 화면정의서 S03에 정식 반영될지, 별도 화면 ID를 받을지 팀 논의 필요.
