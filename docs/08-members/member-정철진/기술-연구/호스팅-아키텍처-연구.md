# 호스팅 아키텍처 연구

> 개인 기술 연구 노트다. Threadia 배포 단계에서 사용할 호스팅 조합(Backend: Docker + EC2, Frontend: Amplify 또는 Vercel)을 비교한다.
> Sprint 1 DoD 문서 기준 AWS(EC2/RDS/S3) 사용 방향은 이미 확정되어 있으며, 실제 배포 구현은 Sprint 1 이후다. 이 노트는 그 시점을 위한 사전 조사다.

---

## 1. 문제 제기

Threadia는 Frontend(Next.js)와 Backend(Spring Boot)를 분리한 구조다. 웹 표준 관행과도 맞고, Sprint 1 기술 스택 결정과도 일치한다. 배포 단계에서 결정할 것은 다음 두 가지다.

| 영역 | 후보 |
|---|---|
| Backend 호스팅 | Docker + EC2 |
| Frontend 호스팅 | AWS Amplify Hosting 또는 Vercel |

Backend는 Docker + EC2로 가는 방향에 이견이 없다. RDS(MySQL)와 같은 VPC에 둘 수 있고, 팀 규모(6명, bootcamp 성격 프로젝트)에서는 ECS/Fargate보다 운영·디버깅이 단순하다. 쟁점은 Frontend다.

---

## 2. AWS Amplify Hosting 조사

### 2-1. Next.js App Router 지원 범위

Amplify Hosting compute는 Next.js 12~15의 SSR을 정식 지원하며, App Router(Next.js 13+), SSG, ISR(on-demand 제외), API Routes, Image Optimization을 모두 지원한다.

### 2-2. 제약 사항

| 제약 | 내용 |
|---|---|
| Edge API Routes 미지원 | non-edge API와 middleware만 사용 가능 |
| On-Demand ISR 미지원 | 페이지별 수동 캐시 무효화 기능 동작하지 않음 |
| Build 출력 크기 제한 | SSR 앱 기준 최대 220MB |
| Node.js 버전 | 14/16/18 미지원, 20/22/24만 지원 |

Threadia Sprint 1~2 범위(인증, 칸반, 문서, 채팅)에서는 Edge API Routes나 On-Demand ISR을 요구하는 기능이 없어 실질적인 blocker는 아니다.

---

## 3. Vercel과의 비용/운영 비교

### 3-1. 비용 구조

| 구분 | Vercel | AWS Amplify |
|---|---|---|
| 무료 티어 | Hobby 플랜 — 개인/비상업적 용도만 허용 | 개발용 무료 티어 제공 |
| 상업적 사용 | Pro 플랜 $20/월(팀원당) 필요 | 트래픽 기준 사용량 과금 |
| 소규모 저트래픽 기준 | Pro 사용 시 $20/월 | 약 $3/월 (사례 기준 최대 85% 절감) |
| 예측 가능성 | 인당 고정 요금이라 예측 쉬움 | 데이터 전송·API 호출에 따라 변동 가능 |

핵심 차이는 Vercel의 무료 Hobby 플랜이 **비상업적 용도로 제한**된다는 점이다. Threadia는 학습 목적이지만 팀 프로젝트 제출·발표용 산출물이라 상업적 사용 여부가 모호하다. 순수 개인 학습용이면 Vercel 무료 티어가 가장 저렴하고, 상업적 사용으로 분류된다면 저트래픽 구간에서는 Amplify가 더 저렴하다.

### 3-2. 개발 경험(DX) 차이

Vercel은 Next.js를 만든 회사가 운영하므로 최신 기능 지원이 가장 빠르고, Edge Runtime이나 On-Demand ISR 같은 기능 제약이 없다. Amplify는 AWS 생태계 안에서 빌드·배포·CDN을 통합 관리할 수 있다는 장점이 있다.

## 4. Backend: Docker + EC2 + Nginx 구성

### 4-1. 기본 구조

Spring Boot 애플리케이션을 Docker 컨테이너로 띄우고, EC2 인스턴스에 Nginx를 리버스 프록시로 둔다.

```text
Client → Nginx (EC2, 80/443) → Docker Container (Spring Boot, 8080)
                                        ↓
                                  RDS (MySQL 8.4)
```

Nginx를 앞에 두면 SSL/TLS 종료를 한 곳에서 관리할 수 있고, 인증서 갱신과 보안 설정이 Spring Boot 코드와 분리된다.

### 4-2. CORS와 쿠키 정책

Frontend(Amplify 또는 Vercel)와 Backend(EC2)가 서로 다른 도메인에 위치하므로 **CORS 설정이 필수**다. Nginx를 Frontend와 Backend 양쪽 앞에 두고 같은 origin으로 묶는 방식도 있으나, Threadia처럼 Frontend를 별도 호스팅 서비스(Amplify/Vercel)에 맡기는 구조에서는 Backend가 명시적으로 CORS 허용 origin을 설정해야 한다.

refresh token을 `HttpOnly`, `SameSite=Lax` cookie로 저장하기로 한 Sprint 1 JWT 정책([sprint-1-백엔드-dod.md](../../../00-project/sprint-운영/sprint-1-백엔드-dod.md) 참조)은 Frontend와 Backend가 서로 다른 도메인일 때 `SameSite=Lax`가 cross-site 요청으로 분류되어 쿠키가 전달되지 않을 수 있다. 배포 도메인이 확정되면 다음 중 하나로 조정이 필요하다.

- 같은 상위 도메인(`app.threadia.com` / `api.threadia.com`)으로 배치해 `SameSite=Lax`를 유지한다.
- 도메인이 완전히 분리되면 `SameSite=None; Secure`로 전환한다.

## 5. Frontend·Backend 통합(단일 지점) 호스팅 조사

Frontend와 Backend를 분리 배포(Amplify/Vercel + EC2)하는 대신, 한 곳에서 같이 운영하는 방안도 비교했다. 후보는 단일 EC2 인스턴스 통합, Elastic Beanstalk, App Runner, Lightsail 4가지다.

### 5-1. 단일 EC2 인스턴스 + Docker Compose

가장 직접적인 방식이다. 같은 EC2 인스턴스에 Frontend(Next.js), Backend(Spring Boot), Nginx를 각각 Docker 컨테이너로 띄우고 Docker Compose로 함께 관리한다.

```text
Client → Nginx (80/443)
            ├── / (정적·SSR 요청) → Next.js 컨테이너 (3000)
            └── /api (API 요청)   → Spring Boot 컨테이너 (8080)
```

- Next.js는 `next.config.js`의 `output: 'standalone'` 설정으로 Docker 이미지 크기를 줄인 빌드를 사용한다.
- 같은 origin(같은 도메인, path만 분리)으로 묶이므로 **CORS 문제와 cross-site 쿠키 문제가 사실상 사라진다.** `SameSite=Lax` refresh token cookie도 별도 조정 없이 그대로 쓸 수 있다.
- Next.js 서버를 인터넷에 직접 노출하지 않고 Nginx 뒤에 둬야 한다. Nginx가 비정상 요청, 느린 연결, payload 크기 제한, rate limiting을 흡수해 Next.js 서버 자원을 렌더링에만 쓸 수 있게 한다.
- streaming 응답을 쓰면 Nginx에서 `proxy_buffering off`로 버퍼링을 꺼야 한다. 켜져 있으면 streaming이 깨진다.
- 장점: 추가 관리형 서비스 비용이 없어 가장 저렴하다(중간 트래픽 기준 월 $300~500대 사례 보고 있음, Threadia 규모에서는 훨씬 낮음). 인프라 전체를 직접 통제할 수 있다.
- 단점: DevOps 지식이 필요하고(Docker, Nginx, 인증서, 모니터링 전부 직접 구성), 인스턴스가 단일 장애점(SPOF)이 되며, 스케일링도 수동이다.

### 5-2. AWS Elastic Beanstalk

코드를 올리면 AWS가 EC2, 로드밸런서, Auto Scaling, 모니터링까지 자동으로 구성해주는 PaaS다. Java(Spring Boot), Node.js(Next.js)를 포함한 여러 런타임을 지원하며, Frontend와 Backend를 하나의 환경에서 함께 운영하기에 적합하다고 평가된다. EC2를 직접 만지는 것보다 적은 작업으로, App Runner보다는 더 많은 AWS 인프라 가시성과 제어권을 가진 절충 지점이다.

### 5-3. AWS App Runner

컨테이너나 Git 저장소만 연결하면 빌드·배포·스케일링·HTTPS 엔드포인트까지 AWS가 전부 처리하는 가장 단순한 옵션이다. Heroku와 비슷한 경험을 제공한다. 컨테이너화된 SSR 앱이나 풀스택 앱에 적합하다고 평가되지만, 인프라 제어 범위와 커스터마이징은 가장 제한적이다.

### 5-4. Amazon Lightsail

고정 월 요금과 단순한 사전 정의된 스택(컨테이너 배포 시 500GB 데이터 전송 포함)을 제공한다. 다만 커스터마이징 옵션이 적어 Threadia처럼 복잡한 풀스택 앱에는 일반적으로 권장되지 않는다.

### 5-5. 통합 호스팅 비교 요약

| 옵션 | 관리 부담 | 비용 특성 | 인프라 제어권 | Threadia 적합도 |
|---|---|---|---|---|
| 단일 EC2 + Docker Compose | 높음(직접 구성) | 가장 저렴 | 최대 | CORS/쿠키 문제 회피, 학습 목적엔 적합 |
| Elastic Beanstalk | 중간(AWS가 일부 자동화) | EC2 기반 비용 + 약간의 관리 비용 | 중간 | 풀스택 단일 환경 운영에 적합 |
| App Runner | 낮음(거의 완전 자동) | 사용량 기반, 가장 단순 | 낮음 | 빠른 배포가 우선일 때 적합 |
| Lightsail | 낮음 | 고정 요금, 예측 쉬움 | 낮음(커스터마이징 제한) | 복잡한 구조엔 비권장 |

### 5-6. 분리 배포와의 비교

분리 배포(Frontend: Amplify/Vercel, Backend: EC2)는 각 서비스가 전용 CDN·엣지 캐싱·자동 스케일링을 갖는다는 장점이 있고, 통합 배포(단일 EC2 등)는 CORS·쿠키 설정이 단순해지고 비용이 한 곳에 묶여 관리가 쉬워진다는 장점이 있다. Threadia 규모(팀 프로젝트, 저트래픽)에서는 두 방식 모두 동작에 문제가 없으며, 선택 기준은 비용 단순성(통합)과 운영 분리·확장성(분리) 중 무엇을 우선할지에 달려 있다.

## 6. 결론 및 Threadia 적용 방향

### 6-1. 단계별 적용 제안

| 단계 | Backend | Frontend | 근거 |
|---|---|---|---|
| 초기(Sprint 배포 직후) | Docker + EC2 | AWS Amplify | AWS 계정 하나로 EC2/RDS/S3/Amplify 통합 관리, 기존 AWS 확정 방향과 일치 |
| 비용 절감 필요 시 | Docker + EC2 유지 | Vercel로 전환 | 무료 Hobby 티어로 비용 절감, 단 상업적 사용 여부 확인 필요 |
| 운영 단순화가 더 중요할 때 | 단일 EC2로 통합 | 단일 EC2로 통합 (Docker Compose) | CORS/쿠키 설정이 단순해지고 관리 지점이 하나로 줄어듦 |

Backend는 분리 배포 단계에서는 항상 Docker + EC2를 유지한다. 변경이 필요한 쪽은 Frontend뿐이며, Next.js는 Amplify·Vercel·단일 EC2 어디서든 빌드 방식이 표준적이라 전환 비용이 크지 않다. 통합 배포로 가는 경우는 별도 전환이 아니라 처음부터 한 인스턴스에 같이 구성하는 선택이다.

### 6-2. 배포 전 확인할 것

- [ ] Threadia 프로젝트 제출/발표가 상업적 사용으로 분류되는지 확인 (Vercel Hobby 약관 기준)
- [ ] Frontend·Backend 도메인 구조 확정 (서브도메인 분리 여부)
- [ ] 도메인 구조에 맞춰 refresh token cookie `SameSite` 속성 재확인
- [ ] Backend CORS 허용 origin 목록에 실제 Frontend 도메인 반영
- [ ] EC2 보안 그룹에서 Nginx(80/443) 외 포트 비노출 확인
