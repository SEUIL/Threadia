# 3D 오피스 렌더링 연구

> 개인 기술 연구 노트다. S03 3D 사무실 메인 허브에서 사용할 3D 오피스 모델의 성능·확장성·커스터마이징 방향을 비교한다.

> **⚠️ 지속 조사 및 최신화 필요**
> 이 문서가 다루는 Three.js `BatchedMesh`는 r156에서 추가된 비교적 최신 기능이고, 관련 API(예: `multiDrawInstanced` 지원 여부)가 Three.js 저장소에서 현재도 논의·개선 중이다. React Three Fiber/drei 생태계도 버전업이 빠른 편이라, 실제 구현 착수 전 아래 항목을 반드시 재확인해야 한다.
> - 구현 시점의 Three.js / @react-three/fiber / @react-three/drei 최신 버전과 breaking change 여부
> - `BatchedMesh`의 기능 안정화 상태(현재도 issue가 열려 있는 기능 존재)
> - 실제 회사/프로젝트 규모가 커졌을 때(드로우콜 100개 기준 초과 시점)의 재검토
> 이 문서의 결론은 작성일 기준 조사 결과이며, 확정 설계가 아니라 **구현 착수 직전 재검증이 필요한 방향성 메모**로 취급한다.

## 1. 문제 제기

### 1-1. 사용 범위

3D 모델은 [화면정의서](../../../03-design/화면정의서.md) 기준 **S03 3D 사무실 메인 허브 한 곳에서만** 사용한다. 다른 화면에서는 3D 모델을 쓰지 않는다.

### 1-2. Role별 동시 렌더링 개수

사무실 단위는 프로젝트(팀) 단위다. 화면에 동시에 떠야 하는 사무실 개수는 로그인한 사용자의 role에 따라 달라진다.

| Role | 보이는 사무실 | 동시 인스턴스 수 |
|---|---|---|
| A (팀원) | 본인 소속 프로젝트 사무실(팀원+팀장) | 1 |
| P (프로젝트 관리자) | 본인이 관리하는 프로젝트들의 사무실 | N (관리 프로젝트 수) |
| C (회사 관리자) | 회사 전체 프로젝트 사무실 | N (회사 전체 프로젝트 수) |

C 입장에서는 회사 프로젝트 수만큼 사무실이 동시에 렌더링되어야 하므로, "사무실 1개"가 아니라 **가변 개수의 동일 구조 객체를 효율적으로 반복 렌더링하는 문제**로 봐야 한다.

> **2026-07-02 갱신**: 아래 1-4에서 이 전제 자체가 "건물/층" 구조로 바뀌면서 완화된다. C도 N개 사무실을 **동시에 상세 렌더링하지 않는다** — 자세한 내용은 1-4 참고.

### 1-3 인스턴스 수 결정 기준

새로운 권한 로직을 따로 만들 필요는 없다. 기존 `GET /api/v1/companies/{companyId}/projects`(`PROJECT-01`)가 "C는 회사 전체, A/P는 소속 프로젝트만" 반환하도록 이미 설계되어 있다. 프론트는 이 응답의 프로젝트 개수를 그대로 렌더링할 사무실 인스턴스 개수로 사용한다.

### 1-4. 건물/층 구조와 카메라 전환 (2026-07-02 추가)

S03을 "사무실 여러 개를 평면에 나열"하는 대신 **건물 1개 + 층(사무실) N개**로 재설계했다. 프로젝트 개수만큼 층이 쌓인 하나의 건물로 표현하고, 카메라를 두 단계로 나눈다.

| 카메라 상태 | 보이는 것 | 렌더링 대상 |
|---|---|---|
| Overview | 건물 전체 실루엣 (층 = 프로젝트 개수만큼 쌓인 슬랩) | 단순 도형(슬랩)만. 가구·인테리어는 렌더링하지 않는다 |
| Floor | 클릭해서 진입한 층 1개의 내부(사무실 인테리어: 벽, 책상, 캐릭터 등) | **동시에 1개 층만** 상세 렌더링 |

전환은 `@react-three/drei`의 `CameraControls`(`setLookAt` 등)로 부드럽게 처리한다.

- A(팀원, 사무실 1개): 고를 층이 없으므로 Overview를 생략하고 바로 Floor 상태로 진입한다.
- P/C(사무실 N개): Overview로 진입 후 층을 선택하면 Floor로 전환한다.

**1-2에서 우려했던 "C가 N개 사무실을 동시에 완전 렌더링"하는 문제는 이 구조에서 발생하지 않는다.** Overview에서는 층이 전부 단순 슬랩(동일 geometry, InstancedMesh)이라 가볍고, 상세 인테리어(가구 포함)는 진입한 층 1개에서만 그려진다. 즉 원래 문서가 걱정하던 드로우콜 부담은 이 구조 변경만으로 상당 부분 완화된다.

### 1-5. 실제 3D 자산 결정: Kenney Furniture Kit (2026-07-02 추가)

3장(결론 및 적용 방향)에서 "1차는 단순 도형 조합"으로 정했던 방향을 다음과 같이 구체화한다.

- **자산**: [Kenney Furniture Kit](https://kenney.nl/assets/furniture-kit) (CC0 라이선스, 상업/과제 이용 가능, 출처 표기 불필요)
- **포맷**: glTF(`.glb`)만 사용. 동봉된 DAE/FBX/OBJ/STL은 three.js가 로드할 수 없어 제외했다
- **배치 위치**: `frontend/public/models/kenney-furniture-kit/` (glTF 140개 + `License.txt`, 총 2.3MB)
- **검증**: `desk.glb`, `chairDesk.glb`, `lampSquareTable.glb`를 drei `useGLTF`로 로드해 브라우저에서 실제 렌더링 확인 완료 (200 OK, 콘솔 에러 없음)

이에 따라 "단순 도형 조합"이라는 1차 방향의 표현을 다음처럼 구체화한다: **Floor 내부의 개별 가구(책상·의자·조명)는 Kenney glTF 모델을 쓰고, Overview의 건물 층 슬랩만 순수 도형(box)으로 유지한다.**

## 2. 기술 조사

### 2-1. InstancedMesh

| 항목 | 내용 |
|---|---|
| 드로우콜 | 동일 geometry를 N개 그릴 때 단일 드로우콜 |
| 제약 | 모든 인스턴스가 geometry를 공유해야 한다. 형태 자체는 인스턴스마다 다르게 할 수 없다 |
| 인스턴스별 커스터마이징 | `setColorAt` 등 instance attribute로 색상·텍스처 인덱스 정도는 가능 |

### 2-2. BatchedMesh (Three.js r156+)

| 항목 | 내용 |
|---|---|
| 드로우콜 | InstancedMesh와 동일하게 단일 드로우콜 유지 |
| 제약 | 인스턴스마다 **다른 geometry**를 허용한다 (InstancedMesh의 핵심 제약을 해소) |
| 추가 기능 | `setVisibleAt`으로 개별 가시성 제어 가능 |
| 안정성 | 비교적 최근 추가된 기능이라 일부 세부 동작(예: `multiDraw*Instanced` 지원)이 Three.js 저장소에서 현재도 논의 중이다 |

InstancedMesh와 BatchedMesh 모두 목표(드로우콜 1개)는 같다. 선택 기준은 **사무실 형태가 모두 동일한가, 회사/프로젝트마다 형태가 달라야 하는가**다.

> **2026-07-02 갱신**: 1-4/1-5의 건물/층 구조 이후, InstancedMesh 적용 단위가 바뀐다.
> - **Overview 층 슬랩**: 여전히 "사무실(층) 단위"로 InstancedMesh 적용 — 전부 동일한 단순 box geometry라 그대로 유효하다.
> - **Floor 내부 가구**: "사무실 단위"가 아니라 **"같은 가구 모델 단위"**로 적용한다. 예를 들어 책상이 여러 개 있는 층이라면 `desk.glb` geometry를 공유하는 책상 N개를 InstancedMesh 하나로 묶는다. 동시에 상세 렌더링되는 층이 1개뿐이라(1-4) 실제로는 층당 가구 개수가 적어(수 개~십수 개 단위) InstancedMesh 없이 개별 mesh로만 그려도 드로우콜 100개 기준에 여유가 크다. 필요성이 커지면 그때 도입한다.

### 2-3. Geometry Merging (BufferGeometryUtils.mergeGeometries) — 비채택

| 항목 | 내용 |
|---|---|
| 방식 | 여러 geometry를 정적으로 하나로 합친다 |
| 문제 | 합친 뒤에는 개별 인스턴스를 따로 움직이거나 수정하기 어렵다. GPU 메모리도 vertex 데이터가 중복 저장되어 더 크다 |
| 결론 | 회사/프로젝트 단위로 동적으로 추가·제거되는 Threadia 구조와 맞지 않아 채택하지 않는다 |

### 2-4. 가변 정보(팀명, 멤버 아바타) 표현 방식

사무실마다 달라야 하는 텍스트·아바타 같은 정보를 3D geometry에 베이킹하지 않고, React Three Fiber의 `<Html>`(drei) 같은 DOM 오버레이로 분리하는 방식을 검토했다.

- 3D geometry는 계속 InstancedMesh로 단일 드로우콜을 유지할 수 있다.
- 텍스트/아바타 변경은 React state로 처리되어 구현·유지보수가 쉽다.
- 사무실 외형 자체를 회사·프로젝트마다 다르게 할 필요가 없다면 BatchedMesh까지 가지 않고 InstancedMesh만으로 충분해질 수 있다.

### 2-5. 드로우콜 성능 기준

매끄러운 60fps 기준 **드로우콜 100개 이하**가 일반적으로 권장되는 가이드라인이다. 사무실 하나가 드로우콜 1개라면, 6주 MVP 데모 규모(한 회사의 프로젝트 수가 많아야 수십 개 단위)에서는 성능 여유가 크다.

### 2-6. 이펙트(Post-processing) 사용 최소화

Bloom, SSAO 같은 post-processing 효과는 화면 전체에 매 프레임 적용되는 별도 비용이다. 사무실이 여러 개 동시에 보이는 화면(C 역할)에서 fps를 가장 먼저 깎아먹는 요인이 될 수 있어 최소화하는 방향이 맞다.

## 3. 결론 및 적용 방향 (2026-07-02 갱신 — 건물/층 구조 반영)

| 단계 | 선택 | 전환 조건 |
|---|---|---|
| 건물 Overview | InstancedMesh + 단순 도형(box 슬랩)으로 층 개수만큼 구성 | 모든 층 외형이 동일할 때 (현재 기준) |
| Floor 내부 가구 | Kenney Furniture Kit glTF 모델(desk/chair/lamp 등) 개별 배치 | 층당 가구 개수가 적어 InstancedMesh 없이도 충분 |
| 전환 시점 | 층 슬랩을 BatchedMesh로 교체 | 회사/프로젝트마다 층 외형(레이아웃, 규모 등)을 다르게 표현해야 할 필요가 생길 때 |
| 가변 정보 | drei `<Html>` 오버레이로 분리 | 팀명, 멤버 아바타 등 텍스트성 정보는 geometry에 넣지 않는다 |
| 카메라 | drei `CameraControls`로 Overview ↔ Floor 부드러운 전환 | 1-4 참고 |

인스턴스 개수는 기존 `PROJECT-01` API 응답의 프로젝트 개수를 그대로 사용하며, 별도 권한 로직을 새로 만들지 않는다.
