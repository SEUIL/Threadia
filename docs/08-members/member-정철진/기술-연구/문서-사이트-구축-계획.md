# 문서 사이트 구축 계획

> 개인 기술 연구 노트다. 멘토 피드백("문서는 정리가 잘 되어 있는데 한눈에 들어오지 않는다")에 대응해, `docs/`를 렌더링하는 별도 사이트를 만들 수 있는지와 어떤 방식이 되는지를 정리한다.
> 이 문서는 실행 계획이 아니라 가능성과 방식에 대한 사전 검토다. 팀 전체에 적용할 변경(태그 메타정보 등)은 별도 합의를 거쳐야 한다.

## 1. 문제 제기

### 1-1. 멘토 피드백

멘토링 중 받은 피드백 중 하나는 다음과 같다.

> 문서를 보다 보면 왔다 갔다 하느라 내용이 잘 기억나지 않는다. 한눈에 들어오지 않는다. 정리는 잘 되어 있는데 그 부분이 아쉽다.

### 1-2. 대응 방향

단순히 `.md` 문서 사이에 링크를 거는 것보다, 문서를 연관성별로 모아서 보여주는 사이트를 만들면 더 나을 것이라고 판단했다. 다만 다음 두 가지를 구분해야 한다.

- **즉시 사용 가능한 대안**: 기존 일부 문서가 이미 Obsidian 스타일 frontmatter(`related:`, `aliases:`)를 쓰고 있어, Obsidian Graph View로 별도 구축 없이 일부 효과를 볼 수 있다.
- **별도 구축**: 검색·분류까지 포함한 전용 사이트를 만드는 것은 더 큰 작업이며, 방식을 잘못 고르면 Sprint 일정을 갉아먹는 사이드 프로젝트가 될 수 있다.

이 문서는 후자, 즉 별도 사이트 구축이 기술적으로 가능한지와 어떤 방식으로 가능한지를 다룬다.

## 2. 구현 방식 조사

### 2-1. 사이트 프레임워크 비교와 Nextra 시도 결과

| 옵션 | 특징 | 비고 |
|---|---|---|
| Docusaurus | React 기반, 가장 큰 플러그인 생태계, 버저닝 지원 | 학습 비용 있음 |
| VitePress | Vue 기반, 빠른 개발 루프 | Threadia 스택(React/Next.js)과 불일치 |
| Nextra | Next.js 기반 문서 프레임워크, Vercel 자체 문서도 이 도구로 제작 | **시도 후 폐기.** 아래 참조 |
| **일반 Next.js + 개별 모듈 조합** | 프레임워크 없이 표준 Next.js App Router와 검증된 개별 라이브러리만 사용 | **최종 채택** |

#### Nextra 시도 결과 — 폐기

1차로 Nextra를 채택해 실제로 구현을 시도했으나, 다음 문제로 폐기했다.

- Next.js 16.2.9 + Nextra 4.6.1 조합에서 정적 빌드(`next build`) 시 모든 페이지가 동일한 digest로 prerender 에러가 발생했다. Next.js 15.5.19로 내려도 동일하게 재현됐다.
- dev 모드에서 확인한 실제 원인은 Nextra의 `importPage()`가 콘텐츠를 동적으로 불러오는 `webpackContext` 단계에서 발생하는 `MODULE_NOT_FOUND`였다. 에러 로그에 OneDrive 경로의 한글("바탕 화면")이 깨진 문자로 출력되는 것으로 보아 Windows 비-ASCII 경로와 Turbopack/webpack의 동적 모듈 해석이 충돌하는 것으로 추정된다.
- 한글 경로를 피하려고 ASCII 경로로 디렉터리 junction을 만들어 우회를 시도했으나, Next.js가 내부적으로 실제 경로(realpath)로 다시 resolve해 동일하게 실패했다.
- Nextra는 동적 webpack 모듈 로딩, 자체 페이지맵(`_meta.global`) 시스템, 테마 Layout의 props 스키마 검증까지 자체 파이프라인이 복잡해 문제를 진단하기 어려웠다. 검증된 공식 스타터 템플릿(`phucbm/nextra-docs-starter`)으로 처음부터 다시 시작해도 동일한 증상이 재현되어, Threadia 환경(Windows + OneDrive + 한글 경로) 자체와 Nextra의 동적 로딩 방식이 근본적으로 맞지 않는 것으로 판단했다.

#### 채택안: 일반 Next.js + 개별 모듈 조합

프레임워크의 "매직"(동적 콘텐츠 로딩, 자체 라우팅/테마 시스템) 없이, 이미 Threadia Frontend(`frontend/design-sample`)에서 검증된 표준 Next.js App Router 위에 필요한 기능만 개별 라이브러리로 조합한다. Server Component에서 `fs.readFileSync`로 마크다운을 직접 읽는 것은 Next.js의 가장 기본적인 사용 패턴이라, Nextra의 동적 모듈 로딩 단계에서 겪은 것과 같은 프레임워크 특유의 버그를 만날 가능성이 훨씬 낮다.

### 2-1-A. 모듈 선정과 버전 호환성 (확인일: 2026-06-27)

| 역할 | 모듈 | 버전(npm 최신) | 확인한 호환성 |
|---|---|---|---|
| 마크다운 → React 렌더링 | `react-markdown` | 10.1.0 | peerDependencies `react >= 18` — React 19.2.4와 호환 |
| GFM 표/취소선/체크리스트 지원 | `remark-gfm` | 4.0.1 | `react-markdown@10`과 함께 쓰는 표준 조합 |
| 코드 블록 문법 강조 | `rehype-prism-plus` | 2.0.2 | peerDependencies 없음(React 버전 제약 없음), 최근 업데이트 활발, 줄 번호·라인 하이라이트 지원 |
| Mermaid 다이어그램 | `mermaid` | 11.16.0 | peerDependencies 없음(프레임워크 비의존 순수 JS). `'use client'` 컴포넌트로 감싸서 사용 |
| 검색 인덱스 | `flexsearch` | 0.8.212 | ESM 환경에서 `import { Index } from 'flexsearch'` 형태로 사용 가능. CJS/ESM 혼용 이슈가 보고된 적이 있어 빌드 후 동작 확인 필요 |

`gray-matter`(YAML frontmatter 파서)는 검토했으나 채택하지 않는다. Threadia 문서는 YAML frontmatter(`---`)가 아니라 `> **작성자**: ...` 블록쿼트 메타정보 형식을 쓰므로, 표준 frontmatter 파서가 맞지 않는다. 대신 이 형식을 직접 읽는 간단한 정규식 파서를 작성한다.

### 2-1-B. Next.js 버전과 Turbopack 주의사항

Next.js는 `frontend/design-sample`과 동일한 `16.2.9`를 사용해 두 워크스페이스 간 버전 차이를 만들지 않는다. Next.js 16부터 Turbopack이 `next dev`/`next build` 기본 번들러로 안정화되었다고 공식 발표되어 있으나, Nextra 시도 과정에서 Windows 환경에서의 동적 모듈 해석 이슈를 직접 겪었다. 일반 Next.js 사용(정적 `fs` 읽기 + 표준 라이브러리)에서는 재현되지 않을 것으로 예상하지만, 빌드 단계에서 유사한 증상이 다시 나타나면 `next build --webpack`(Turbopack 대신 classic webpack 강제)을 1차 우회책으로 시도한다.

> 확인됨: Mermaid는 Nextra가 아니라 `mermaid` 패키지를 직접 써도 다이어그램 렌더링에 문제가 없다. `ERD.md`, `실시간-아키텍처-연구.md` 등의 다이어그램은 클라이언트 컴포넌트에서 `mermaid.render()`를 호출하는 방식으로 처리한다.

> 확인됨(2026-06-27 실제 구현): `docs-site/`를 일반 Next.js 16.2.9 App Router + `react-markdown`/`remark-gfm`/`rehype-prism-plus`/`mermaid` 조합으로 스캐폴드하고 빌드·dev 서버 모두 정상 동작을 확인했다. 표·코드 하이라이팅·Mermaid 다이어그램 렌더링 파이프라인까지 검증 완료. Nextra에서 겪은 prerender 에러는 재현되지 않았다.

### 2-2. 검색 방식

**Pagefind**를 1차로 검토했으나, 한국어 처리 한계를 확인하고 **FlexSearch + bigram 커스텀 인코더**로 방향을 바꿨다.

#### Pagefind 검토 결과 (기각)

- 빌드가 끝난 정적 HTML을 스캔해 WebAssembly 기반 검색 인덱스를 생성한다. 백엔드, API key, 월 비용이 없다.
- 한국어(CJK)는 extended 모드(기본값)에서 지원되지만, 진짜 형태소 분석이 아니라 **블랙박스 휴리스틱 기반 단어 분리**다. 공식 문서에도 "네이티브가 기대하는 부분 문자열 검색 수준엔 못 미친다"고 명시돼 있다.
- 동작 방식이 Rust 바이너리 내부에 있어 한국어 처리가 잘 안 될 때 직접 디버깅하거나 보정하기 어렵다.

#### 채택안: FlexSearch + bigram 커스텀 인코더

- Elasticsearch/Lucene가 한중일(CJK) 텍스트 검색에 표준으로 쓰는 기법이 **bigram**(인접 2글자씩 겹치게 쪼개는 방식)이다. 예: "동경도는" → "동경", "경도", "도는". 띄어쓰기가 없는 언어의 단어 경계 문제를 형태소 분석 없이 실용적으로 푸는 검증된 방법이다.
- **FlexSearch**는 `Charset.CJK` 인코더를 내장하고, `normalize`/`prepare`/`finalize` 커스텀 함수로 bigram 토크나이저를 직접 끼울 수 있다. Pagefind와 동일하게 정적 배포·서버 불필요·무료다.
- Threadia 문서 코퍼스가 canonical 약 25개로 작아서, 검증된 기법을 직접 구현해도 부담이 크지 않다. 블랙박스 휴리스틱보다 우리가 동작을 이해하고 고칠 수 있는 쪽이 더 안정적이다.
- 검색 UI는 Pagefind와 달리 기본 제공 컴포넌트가 없어 직접 만들어야 한다. 일반 Next.js 프로젝트 안의 React 컴포넌트로 만들면 된다.
- 태그(§3-3)는 한글이 아니라 영어 키워드이므로 bigram 처리 없이도 정확히 매칭된다. 한국어 본문 검색이 다소 부정확해도 태그·제목 매칭으로 결과를 보완할 수 있다.

자동 분류(임베딩 기반 의미 유사도 계산)는 검토했으나 채택하지 않는다. 별도 ML 프로젝트 규모이며, Sprint 1 진행 중에 부담할 범위가 아니다.

### 2-3. 저장소 구조

```text
Threadia/
├── backend/
├── frontend/
├── docs/                 ← 콘텐츠 원본, 그대로 유지
└── docs-site/            ← 신규: docs/를 렌더링하는 일반 Next.js 프로젝트
```

`docs-site/`는 Threadia 저장소 내부에 둔다(완전 별도 저장소 방식은 운영 복잡도가 커서 제외). `docs/`의 마크다운을 가져오는 방식은 두 가지가 가능하다.

| 방식 | 동작 | 비고 |
|---|---|---|
| A. 직접 참조 | 동적 라우트 Server Component에서 `fs.readFileSync('../../docs/...')`로 상위 폴더를 직접 읽음 | 구현 단순, 1차 채택 후보. 프레임워크 컨벤션에 묶이지 않으므로 Nextra 시도 때보다 적용이 단순함 |
| B. 동기화 스크립트 | 빌드 전 `docs/` → `docs-site/content/`로 복사 | A안에서 상위 폴더 접근이 문제가 되면 전환 |

#### 포함 범위 필터

사이트에 올릴 문서는 `docs/01-planning/`(raw archive, 검토용 중복 산출물 다수)과 `docs/08-members/`(팀원별 개인 폴더)를 **제외**한다. 두 폴더를 그대로 올리면 양이 너무 많아져서 멘토 피드백("한눈에 안 들어온다")을 오히려 악화시키고, 개인 폴더 비공개 원칙과도 맞지 않는다. 빌드 스크립트의 glob 패턴에 명시적으로 제외 조건을 넣는다(예: `../docs/**/*.md` 중 `01-planning`, `08-members` 경로 제외).

### 2-4. Vercel 배포 동작

1. 같은 GitHub 저장소를 Vercel에 새 프로젝트로 한 번 더 연결한다(Threadia 앱용 프로젝트와 별개).
2. Root Directory를 `docs-site`로 지정한다.
3. `dev`(또는 `main`) 브랜치에 push가 들어오면 Vercel이 자동으로 재빌드·배포한다. 별도 GitHub Actions 설정이 필요 없다.

흐름: `docs/*.md` 수정 → PR → dev merge → Vercel이 push 감지 → `docs-site` 빌드 → 사이트 자동 반영.

## 3. 문서 간 연관성 정의 방식

### 3-1. 폴더만으로는 부족한 이유

폴더 구조(`00-project`~`08-members`)는 문서가 1개 카테고리에만 속하는 1차원 분류다. 실제로는 `ERD.md`가 `API-명세서.md`, `기능-분해표.md`, `보류-기능-최종표.md`와 동시에 강하게 연관되는 것처럼, 폴더를 가로지르는 연관성은 따로 정의해야 한다.

### 3-2. 파일명 태그 방식 — 채택하지 않음

파일명에 태그를 박는 방식(예: `ERD-auth-db.md`)은 태그가 바뀔 때마다 파일명을 바꿔야 해서 기존 문서에 걸린 링크가 깨진다. `문서-작성-규칙.md` §4("파일명에 날짜·버전을 임의로 붙이지 않는다")의 취지와도 충돌한다.

### 3-3. 채택안: 3계층 연관성 모델

| 계층 | 역할 | 비용 |
|---|---|---|
| 폴더 (기존) | 대분류, 사이트 사이드바 섹션 | 0 |
| 태그 (신규 제안) | 횡단 연관 — 예: "Auth 관련 문서 전부 모아보기" | 문서당 1줄 |
| 명시적 "관련 문서" 링크 (일부 기존 적용 중) | 정밀 연결 — 특정 문서가 다른 특정 문서의 직접적 근거임을 표시 | 문서당 몇 줄 |

태그는 별도 YAML frontmatter 대신, 기존 메타정보 블록 형식에 한 줄을 추가하는 방식을 제안한다.

```text
> **작성자**: Threadia 팀
> **작성일**: 2026-06-15
> **태그**: auth, erd, invitation
> **상태**: 6일차 수정본
```

이렇게 하면 `문서-작성-규칙.md` §5가 이미 허용한 "기존 형식을 유지해도 된다"는 메타정보 패턴 안에서 확장되고, `docs-site` 빌드 스크립트가 이 한 줄을 정규식으로 파싱해 태그별 인덱스를 만들 수 있다. 별도 frontmatter 파서가 필요 없다.

> 진행 상황(2026-06-27): `문서-작성-규칙.md` §5에 태그 필드를 정식으로 추가했다. 새 문서부터는 YAML frontmatter를 쓰지 않고 블록쿼트 형식으로 단일화하도록 규칙을 갱신했고, UTF-8 인코딩 요구사항도 명시했다. 기존 canonical 문서 25개를 점검한 결과 전부 태그가 빠져 있는 것을 확인했다(22개 블록쿼트, 2개 frontmatter, 4개는 메타정보 자체가 없음). 실제 일괄 적용은 아직 진행하지 않았다.

## 4. 결론

### 4-1. 가능성

기술적으로 가능하다. 추가로 필요한 인프라는 Vercel 프로젝트 1개 추가뿐이며, 정적 문서 사이트라 비용은 무료 티어로 충분하다.

### 4-2. 1차 구축 범위

1. `docs-site/`에 일반 Next.js(App Router) 프로젝트 생성, 버전은 `frontend/design-sample`과 동일한 16.2.9로 고정
2. `react-markdown` + `remark-gfm` + `rehype-prism-plus`로 마크다운 렌더링 파이프라인 구성
3. `mermaid` 패키지를 `'use client'` 컴포넌트로 감싸 다이어그램 렌더링 처리
4. `docs/`의 마크다운을 읽어오는 동적 라우트 구성 (방식 A, `01-planning`·`08-members` 제외 필터 포함)
5. 메타정보 블록(`> **작성자**: ...`)을 읽는 간단한 정규식 파서 작성 (`gray-matter` 미사용)
6. FlexSearch 인덱스 빌드 스텝 추가 (bigram 커스텀 인코더 적용)
7. Vercel 프로젝트 연결 + Root Directory 설정

빌드 단계에서 Turbopack 관련 증상이 재현되면 `next build --webpack`을 1차 우회책으로 시도한다(§2-1-B).

공개 범위(누구나 접근 가능한 공개 URL로 둘지, 보호할지)는 최종 검토 후 구현 단계에서 결정한다. 1차 구축 범위에는 포함하지 않는다.

> 진행 상황(2026-06-27): 1~3단계 완료. `docs-site/`에 Next.js 16.2.9 + react-markdown/remark-gfm/rehype-prism-plus/mermaid/flexsearch 의존성을 갖춘 프로젝트를 생성하고, 헤더+사이드바+본문 레이아웃과 마크다운 렌더링 파이프라인(샘플 콘텐츠 기준)을 구현해 빌드·dev 서버 정상 동작을 확인했다. 사이드바는 아직 `docs/` 폴더명을 하드코딩한 placeholder이고, 본문도 실제 파일이 아니라 샘플 텍스트다. 4~7단계(실제 파일 연동, 메타정보 파서, 검색 인덱싱, 배포)는 남아 있다.

### 4-3. 태그 메타정보 적용 시점

태그를 canonical 문서(약 25개) 전체에 적용하는 것은 `문서-작성-규칙.md`에 `태그` 필드를 정식으로 추가하는 **팀 차원의 규칙 변경**이다.

개인 폴더 시범 적용 단계는 건너뛴다. 팀원이 진행할 **문서 전체 최신화 작업 시점에 맞춰, canonical 문서 전체에 태그를 일괄 적용하고 바로 구현까지 진행**하는 흐름으로 처리한다. 이 docs-site 작업은 그 문서 최신화와 맞물려 진행되어야 하며, 별도로 먼저 진행하지 않는다.

> 정정(2026-06-27): 위 결정은 dev에 병합된 DB schema 정책 문서 최신화(PR #5, `docs/db-schema-policy`)를 가리킨 것이었다. 태그 일괄 적용은 그 작업과 무관한 별도 작업이며 본인(정철진)이 직접 진행한다. `문서-작성-규칙.md` 규칙 추가는 이미 완료했고, 기존 25개 문서에 실제로 태그를 채우는 작업이 남아 있다.

### 4-4. 다음 확인할 것
