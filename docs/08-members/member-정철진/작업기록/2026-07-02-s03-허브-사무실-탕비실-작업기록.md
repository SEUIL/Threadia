## 1. 이전 세션까지 진행 상황 (상세)

### 1.1 기술 스택 결정과 환경 구성

- 3D 렌더링 방향은 개인 기술연구 문서(`3d-오피스-렌더링-연구.md`)의 결론을 따랐다.
  그 문서를 이번 착수 시점 기준으로 재검증하면서 **건물/층 구조**와 **Kenney 자산 채택**을
  반영해 v1.1로 갱신했다(1-4/1-5 섹션 추가).
- 설치: `three@0.185.1`, `@react-three/fiber@9.6.1`, `@react-three/drei@10.7.7`,
  타입용 `@types/three@0.185.0`(devDependency). React 19.2.4와 peer dependency 호환
  확인(`fiber` 요구: `react >=19 <19.3`). `npm audit`의 postcss 취약점은 Next.js 자체
  의존성이라 손대지 않았다.
- 검증: 임시 `<Canvas>`에 teal 큐브를 띄워 WebGL 렌더링이 실제로 되는지 확인 후 진행.

### 1.2 Kenney Furniture Kit 도입 (자산)

- `kenney.nl`에서 **Furniture Kit**을 받았다. 라이선스는 **CC0**(퍼블릭 도메인) — 상업·과제
  이용 가능, 출처 표기 불필요(`License.txt`로 재확인). 발표/제출에 문제없음.
- 동봉 포맷 중 **glTF(`.glb`)만** three.js가 로드 가능하므로 그것만 채택(DAE/FBX/OBJ/STL
  제외). glTF 140개(약 2.3MB) + `License.txt`를
  `frontend/public/models/kenney-furniture-kit/`에 배치했다.
- 원칙: "지금은 써보고 필요 없는 파일만 나중에 삭제"하기로 해서 140개 전부 커밋해 둠.

  모니터와 겹쳐 **램프는 제거**했다.

### 1.5 방 배치와 벽 구역화

- **방 크기**: 바닥을 x`[-1,6]`(7m) × z`[-7,1]`(8m)로 확장. 장식·로비 여유 포함.
- **8자리 책상 모듈**: 4×2 격자. **고정 수용인원 8명** 모듈로, 팀원 수는 좌석 점유 여부만
  바꾸고 방 크기·장식 좌표는 항상 고정한다. **8명을 넘으면 같은 모듈을 옆으로 증축**
  (층을 새로 쌓지 않음, "프로젝트=층" 매핑 유지). 좌석 점유/캐릭터 로직은 미구현.
- **외벽 4면**: `wall.glb`를 이어 붙임. `wall.glb`는 앞면 `wood`/뒷면 `metalDark`로 양면
  재질이 달라, 안쪽이 어두워 보이는 앞·오른쪽 벽은 180°/–90°로 뒤집어 나무색이 실내를
  향하게 보정했다. 오른쪽 벽 한 칸을 `wallDoorway`로 교체(메인 출입구).
- **구역 분리**: 왼쪽 스트립을 가로 divider(z=-4)로 라운지 룸/키친·로비존으로 나누고,
  세로 divider(x=2)로 키친·로비존을 감쌌으며, 가로 divider를 오른쪽 벽까지 연장해 방
  전체를 앞(키친·로비존+책상존)/뒤(빈 뒷방)로 분리했다. 각 칸막이에 출입구를 내
  **총 3곳의 실내 문**을 확보. 결과적으로 라운지 룸 / 키친·로비존 / 책상존 / 빈 뒷방 4구역.
- **책상 블록 90° 회전**: "가로 2줄×4개" 모양은 그대로 두고 블록 전체를 `<group>`으로 감싸
  통째로 회전(개별 회전 아님 — 개별 회전으로 오해해 한 번 삽질). 최종적으로 오른쪽·뒤쪽 벽에
  맞춰 배치(사용자가 수동 미세조정, 대략 x`[2.67,5.9]` z`[-3,1]`).
- **라운지존**: 코너소파(`loungeSofaCorner`) + 커피테이블(`tableCoffee`) + 화분
  (`pottedPlant`) + 러그(`rugRectangle`)를 키친·로비존 안쪽 코너에 배치. 세트 전체를
  같은 델타로 옮겨 상대 배치(모양)를 유지하는 방식으로 이동했다.

키친·로비존만 빈 채로 남아 있었고, 그것을 이번 세션에서 탕비실로 채웠다(§2 이후).

### 1.6 이어서 적용한 기술 교훈

이전 세션에서 확립해 이번 세션에도 계속 쓴 것들:

- **회전 좌표 변환식** `x' = x·cosθ + z·sinθ`, `z' = -x·sinθ + z·cosθ` (부호를 여러 번
  헷갈려, 회전 후 로컬 범위를 실측하고 offset을 역산하는 방식으로 정착).
- **파티션/벽 양면 재질**(`wood`/`metalDark`)을 고려한 방향 보정.
- **Turbopack `.next` 캐시 함정**: 새 상수·`@theme` 토큰 추가 후 "X is not defined" 류의
  옛 에러가 반복되면 **서버 중지 → `rm -rf .next` → 재시작**(서버 켠 채 삭제 시 OneDrive
  동기화와 충돌해 손상되니 순서 주의).
- **손계산보다 `preview_eval` 실측** — `window.__scene`을 순회해 world bbox를 직접 재는 게
  훨씬 정확. `preview_screenshot`은 이 환경에서 30초 타임아웃이 잦음.

## 3. 발생한 문제와 해결 (중요)

### 3.1 균등 1m 간격 배치 → 벽 클리핑 + 아이템 간 간격 불일치

- **증상**: 조리대 4개(냉장고·싱크대·조리대·커피머신)를 벽에서 같은 거리(x=-0.7), 1m
  간격(z축)으로 배치했더니, 싱크대·조리대가 벽을 뚫고 튀어나왔고 커피머신처럼 폭이 좁은
  모델은 옆 모델과 사이가 크게 벌어졌다. 테이블과 의자도 서로 떨어진 채로 렌더링됐다.
- **원인**: 모델마다 **pivot(기준점) 위치가 다르고**(냉장고/싱크대/조리대/커피머신은
  "앞쪽 모서리" 기준, 쓰레기통/화분은 "중심" 기준) **실제 크기도 제각각**이었다
  (싱크대·조리대 폭 0.45m, 커피머신 폭 0.19m). 손으로 어림잡은 1m 격자 가정이 맞지 않았다.
- **해결**: `preview_eval`로 `window.__scene`(기존 `SceneCapture` dev 도구가 노출)을
  순회하며, 각 mesh의 `geometry.attributes.position` 정점을 `matrixWorld`로 직접
  변환해 world-space bounding box를 실측하는 스크립트를 작성했다. 이 실측값으로
  각 모델의 pivot 기준 폭/깊이를 역산한 뒤, 서로 맞닿도록(터치하도록) 좌표를 재계산했다.
  검증할 오브젝트에는 `name` prop을 붙여 `scene.getObjectByName()`으로 특정했다.
- **교훈**: Kenney 킷이라도 카테고리(kitchen vs lounge vs 기본 가구)에 따라 pivot 관례가
  다를 수 있다. 손계산보다 `preview_eval`로 직접 실측하는 쪽이 훨씬 빠르고 정확하다.

### 3.2 커피머신을 조리대 위에 올릴 때 상판 높이 추정이 부정확

- **증상**: 싱크대 상판 위에 커피머신을 얹으려고 정점 y값을 그리드로 샘플링해
  heightmap을 만들었는데, 싱크대(basin 굴곡)·조리대 모두 모서리 rim과 안쪽 면 높이가
  제각각이라 "이 지점의 정확한 표면 높이"를 확신하기 어려웠다.
- **해결**: 1차로 heightmap 샘플링 결과 기준값(y≈0.45~0.47)으로 배치했고, 이후 사용자가
  브라우저에서 직접 보면서 위치(`x=-0.59, y=0.47, z=-2.49`, 싱크대 옆 **조리대** 위)로
  수동 미세조정했다. 조정 후 `preview_eval`로 재측정해 조리대 발판 범위 안에 완전히
  들어가는지(옆으로 안 튀어나오는지)만 재확인했다.
- **교훈**: 낮은 폴리곤 모델의 표면 높이는 정점 샘플링만으로 완벽히 재구성하기 어렵다.
  좌우 위치(클리핑 여부)는 실측으로 보장하고, 미세한 높이감은 사람이 눈으로 보는 게 더
  정확하고 빠르다.

### 3.3 쓰레기통 방향(페달이 문 쪽을 향하게) 지정

- **증상**: 모델 자체에 "정면이 어디"라는 표시가 없어서 회전각을 어떻게 줘야 페달이
  특정 방향을 향하는지 알 수 없었다.
- **해결**: `br-trash` 오브젝트의 전체 정점을 앵커 기준 상대좌표로 덤프해봤더니, 로컬
  `+z` 방향에 낮은 높이(y 0.05~0.077)로 튀어나온 점들이, 반대쪽 로컬 `-z`에는 높은 위치
  (y 0.39~0.42)의 다른 돌출부가 있었다. 낮고 바닥에 가까운 돌출부를 **페달**, 위쪽
  돌출부를 **뚜껑 힌지**로 판단했다. 이 방+에서 책상존 쪽 문(x=2, z`[0,1]`)이 라운지 쪽
  문보다 가까워 그쪽을 "문"으로 보고, 로컬 `+z`(페달 방향)가 월드 `+x`를 향하도록
  `rotation.y = +90°`(이전 세션에서 확립한 회전 변환식 `x'=x·cosθ+z·sinθ,
  z'=-x·sinθ+z·cosθ` 사용)를 적용했다.
- **교훈**: 방향성이 있는 소품은 bbox만으론 알 수 없고, 정점을 앵커 기준 상대좌표로
  펼쳐서 비대칭 돌출부를 찾는 방식이 유효했다. 다만 스크린샷 확대가 이 세션에서
  잘 안 먹혀서(§3.4) 최종 방향은 시각적으로 완전히 확인하지 못했고, 사용자에게 직접
  확인을 요청했다.

### 3.4 (참고) 프리뷰 도구 불안정

- `preview_resize`로 뷰포트를 키우면 R3F `<Canvas>`가 절반만 리사이즈되는 문제가
  재발했다(`window.dispatchEvent(new Event('resize'))`로도 완전히는 안 고쳐짐) → 원래
  뷰포트(800x600)로 되돌려 우회.
- `canvas`에 synthetic `WheelEvent`를 쏴서 OrbitControls를 확대하는 방식이 이번 세션엔
  잘 먹히지 않아(카메라가 튀거나 바닥 아래로 내려가는 등) 특정 소품을 클로즈업하는 데
  여러 번 시행착오가 있었다. `preview_screenshot` 자체의 30s 타임아웃 이슈는 이번엔
  발생하지 않았다.
