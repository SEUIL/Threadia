# 2026-07-08 작업 기록 — WBS 3.2 회사 프론트/진입점 실 API 연동 (PR #62) + PR #61 리뷰

> 개인 작업 노트다. `feature/company-frontend-entry` 브랜치에서 WBS 3.2(3.2.1~3.2.4)를
> phase별로 끊어서 구현했고, 팀원 PR #61(Project API) 리뷰를 마친 뒤 dev를
> 받아 내 작업을 PR #62로 올렸다. 설계 배경은
> [sprint2-3.2-company-frontend-rbac-사전조사.md](../기술-연구/sprint2-3.2-company-frontend-rbac-사전조사.md) 참고.

## 1. 작업 방식

사용자가 "천천히 정확하게, 끊어서" 진행을 명시적으로 요청해서, phase마다
구현 → `tsc`/`eslint` 검증 → 시드 데이터로 실 브라우저 검증 → 시드 정리 →
사용자 보고 → "진행하자" 확인 후 다음 phase, 순서를 7번 반복했다. Commit은
중간에 하지 않고 전체 완료 후 한 번에 묶었다(사용자가 도중에 "다 완료한
다음에 다 함께 커밋하자"로 방침을 바꿈).

특히 이전 `/invitations` orphan-route 버그(진입점 없이 존재하던 페이지)가
재발하지 않도록, 화면을 새로 연동할 때마다 실제로 그 화면에 도달하는 링크가
존재하는지를 매 phase마다 같이 확인했다.

## 2. Phase 1~2 — 타입/서비스 + AuthContext

- `company.service.ts`/`department.service.ts`/`company-member.service.ts`와
  대응 타입(`company.types.ts`)을 백엔드 DTO(PR #56, #60)와 필드명을 맞춰
  신규 작성했다.
- `AuthContext`에 `companyMemberships`(실제 회사 소속·role)를 추가했다.
  기존 `auth.types.ts`의 `companies` 필드는 백엔드가 항상 빈 배열로 내려주던
  죽은 필드라 통째로 제거했다.
- **주의해서 고친 race condition**: `companyMemberships`를 인증 상태
  전환(`status = "authenticated"`)보다 먼저 fetch/set하도록 순서를
  맞췄다 — 안 그러면 소비 컴포넌트가 "인증됨인데 회사 목록은 비어있는"
  순간을 잠깐 보게 된다.

## 3. Phase 3 — 허브 진입점

`HubOverlay`/`RailShell`의 nav를 mock role에서 `companyMemberships` 기준
실 데이터로 바꿨다. 다중 회사 소속 시 어떤 회사로 들어갈지는 화면정의서에
명시가 없어서 우선 `companyMemberships[0]`(서버가 companyId asc 정렬)을
쓰기로 했다(회사 전환 UI는 범위 밖, 설계문서 §9 미결 항목).

소속 회사가 0개인 사용자를 위해 `hub/page.tsx`에 안내 화면(`NoCompanyNotice`)을
추가했다 — 3D Canvas 대신 "받은 초대 확인하기" 링크만 있는 화면. 이게 없으면
신규 가입자가 허브에 들어와도 갈 곳이 없는 진입점 공백이 생겼을 것이다.

브라우저로 0/1 소속, COMPANY_ADMIN/MEMBER 조합을 모두 확인했다.

## 4. Phase 4~5 — S13 설정 / S14 구성원

두 화면의 `MOCK_*` 상수를 전부 실 API 호출로 교체했다.

가장 신경 쓴 부분은 구성원 PATCH의 **full-replace 제약**이다 — 백엔드가
`role`/`status`를 둘 다 `@NotNull`로 받아서, role 셀렉트와 department
셀렉트가 원래 독립된 UI 컨트롤이었는데도 항상 현재 상태 전체를 같이
보내는 하나의 `updateMember()` 핸들러로 합쳐야 했다. 부서만 바꿔도 role이
날아가거나 반대 상황이 생기는 걸 막기 위한 조치라 브라우저에서 양방향(부서만
변경 시 role 유지, role만 변경 시 부서 유지)을 DB 직접 대조로 검증했다.

S13 "생성 모드"는 설계문서 §9 미결 항목이라 의도적으로 미구현 상태로 남겼다.

## 5. Phase 6 — 나머지 화면 RBAC

`useCurrentCompanyRole()` 훅을 새로 만들어 projects/backlog/board 3개
화면의 module-level `MOCK_ROLE`을 걷어내고 실 회사 role로 교체했다.

**3단계(A/P/C) 화면 role vs 2단계(COMPANY_ADMIN/MEMBER) 백엔드 role
불일치**를 다뤄야 했다 — "P"(PROJECT_ADMIN)는 프로젝트 단위 정보라 아직
없는 Project Member API(WBS 3.3.4) 없이는 판별이 안 된다. COMPANY_ADMIN이
아니면 전부 "A"로 보수적으로 처리하기로 했다: 실제 PM인 사용자가 관리
버튼을 못 보는 손해는 있지만(어차피 그 기능 자체도 아직 mock이라 실질
손해는 없음), 권한 없는 사용자에게 관리 UI가 노출되는 것보다는 안전하다는
판단이다. 이 트레이드오프는 훅 파일에 근거를 남겨뒀다.

`[projectId]/settings`(S12)는 Project 자체가 전부 mock이라(Project API가
그때는 없었음) role을 연동해도 실효가 없어 제외하고 주석만 정리했다.

board 페이지의 `reporterName`도 하드코딩된 mock 이름 대신 `useAuth()`의
실제 로그인 닉네임으로 교체했다.

각 화면을 COMPANY_ADMIN/MEMBER 양쪽으로 시드 유저를 만들어 직접 확인했다
(관리 버튼/필드 노출 여부, 콘솔 에러 없음).

## 6. Phase 7 — 종합 검증

- (app) 하위 모든 `page.tsx`를 훑어서 WBS 3.2가 건드린 화면들이 전부 실제
  nav 링크로 도달 가능한지 확인했다. 특히 `[companyId]/notifications`가
  예전에 이미 고쳐진 orphan 버그였다는 걸 그 파일 자체 주석에서 재확인했고,
  `[projectId]/notifications`는 PROJECT scope 알림이 MVP에서 보류되며
  의도적으로 남겨진 스텁이라는 것도 확인했다(연결 안 되는 게 정상).
- `npx tsc --noEmit` 전체 통과.
- `npx eslint`를 프로젝트 전체(`design-sample/`, `.next` 포함)로 한 번
  돌렸다가 무관한 대량 에러에 놀랐는데, `design-sample/`은 별개 참고
  프로젝트이고 `.next`는 빌드 산출물이라 스코프가 잘못됐던 것 — `app
  components contexts hooks services types lib`로 좁혀서 재실행했다.
  남은 에러 2건(`graph/page.tsx`, `notifications/page.tsx`)은 `git status`로
  대조해서 이번 브랜치가 건드리지 않은 기존 파일의 pre-existing 이슈임을
  확인하고 그대로 뒀다.

## 7. 커밋 + PR #61 리뷰 + PR #62

- Phase 1~7을 커밋 하나로 묶어서(`feat(company): ...`) 올렸다(18개 파일).
- 이 시점에 내가 검수자로 지정된 PR #61(팀원의 Project API, WBS 3.3.2)이
  올라와 있어서 먼저 리뷰했다. RBAC(company-admin만 생성, non-admin은
  ACTIVE project membership 기준 필터), ARCHIVED/날짜범위 검증, projectKey
  중복 스코프, 생성 트랜잭션 원자성을 diff와 `db/schema.sql`/API 명세서
  대조로 확인하고 approve + 참고용 코멘트 4건(검증 에러 필드명, pagination
  없음, 테스트 커버리지 공백 1건, 서비스 레벨 중복 검증이 실제로는
  도달 불가 코드라는 점)을 남겼다. 사용자가 승인하고 머지했다.
- `origin/dev`를 `feature/company-frontend-entry`에 merge(충돌 없음, PR #61의
  Project API가 같이 들어옴), tsc 재확인 후 push, PR #62 생성.
- PR #62 "추가 메모"에 Project Member API 부재로 인한 "P" role 보수적
  처리, S12 제외 사유, 허브 0-소속 안내화면을 진입점 공백 예방 목적으로
  추가했다는 점을 명시해뒀다 — 다음 리뷰어가 배경을 바로 알 수 있게.

## 8. 다음에 남는 것

- `projects/page.tsx`를 mock에서 real API로 바꿀 때 `pmName`/`memberCount`/
  `issueCount`는 이번 PR #61 응답에 없다 — Project Member API(WBS 3.3.4)와
  Issue API가 나온 뒤에 채울 수 있다. PR #61 코멘트에도 남겨뒀다.
- `useCurrentCompanyRole()`은 Project Member API가 생기면 "P" 판별까지
  확장해야 한다.
- S13 "생성 모드"와 회사 전환 UI(다중 회사 소속)는 설계문서 §9 미결 항목으로
  여전히 남아있다.
