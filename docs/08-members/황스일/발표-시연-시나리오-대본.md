# Threadia 발표 시연 시나리오와 대본

## 1. 목적과 운영 원칙

이 문서는 배포 완료된 Threadia를 15분 이내에 시연하기 위한 화면 순서와 발표 대본이다. 시연의 중심 메시지는 다음과 같다.

> Threadia는 채팅에서 나온 논의를 이슈로 전환하고, 문서와 연결하며, 프로젝트·회사·플랫폼 운영까지 하나의 맥락으로 관리하는 통합 협업 플랫폼이다.

시연에서는 이미 준비된 발표용 데이터를 조회만 한다. 이슈 생성·상태 이동, 메시지 전송, 문서 수정·삭제, 초대·권한·회사 정보 변경, 문의 답변·상태 변경·시스템 설정 변경은 수행하지 않는다.

## 2. 사전 준비

| 구분 | 준비 내용 |
|---|---|
| 배포본 | `https://threadia.click`의 `main` 배포 결과를 사용한다. |
| 회사·프로젝트 관리자 | Google OAuth로 로그인한 회사 관리자 계정을 사용한다. |
| 플랫폼 관리자 | 플랫폼 관리자 계정으로 별도 Chrome 프로필 또는 별도 탭을 준비한다. |
| 시작 화면 | 회사 관리자 계정에서 `/hub`를 열어 3D 허브를 보여준다. |
| 보조 탭 | 플랫폼 관리자 계정에서 `/platform/support-cases`를 미리 열어 둔다. |
| 네트워크 대비 | 3D 허브, 프로젝트 홈, 채팅, 보드, 그래프, 플랫폼 콘솔의 스크린샷을 준비한다. |

발표용 노트북에서 WebGL 3D 허브가 정상 렌더링되는지 발표 직전에 확인한다. 3D 허브가 실패하면 해당 기능에 머무르지 않고 좌측 레일에서 프로젝트 화면으로 바로 이동한다.

## 4. 상세 대본

### 4.1 3D 허브: 협업 공간의 시작 (0:00~1:20)

**화면**: `/hub`

**대본**

> 안녕하세요. Threadia는 Jira, Slack, Confluence처럼 분리된 협업 도구에서 업무 맥락이 끊기는 문제를 해결하기 위해 만든 통합 협업 플랫폼입니다.
>
> 첫 화면은 3D 허브입니다. 단순한 메뉴 목록이 아니라, 회사 구성원이 협업 공간에 들어와 프로젝트·채팅·알림·회사 관리로 이동하는 공통 진입점으로 구성했습니다.
>
> 이 좌측 레일을 통해 사용자는 필요한 기능으로 바로 이동할 수 있고, 이후 화면에서는 채팅에서 시작된 논의가 이슈와 문서로 어떻게 이어지는지 보여드리겠습니다.

**시연 포인트**

- 3D 오피스와 좌측 레일을 20~30초만 보여준다.
- 카메라 조작은 최소화한다.
- `프로젝트` 메뉴로 이동한다.

### 4.2 프로젝트 홈: 업무 현황을 한눈에 확인 (1:20~2:40)

**화면**: `/6/10/dashboard`

**대본**

> 프로젝트 홈에서는 전체 업무의 진행 상태를 요약해서 보여줍니다. 현재 전체 이슈 중 완료된 이슈의 비율과 최근 이슈, 최근 문서를 함께 확인할 수 있습니다.
>
> 관리자는 여러 화면을 오가지 않고도 프로젝트가 어느 정도 진행됐는지, 최근 어떤 작업과 문서가 추가됐는지 빠르게 파악할 수 있습니다.
>
> 이제 이슈가 실제로 어디에서 시작되는지 프로젝트 채팅 화면으로 이동하겠습니다.

**시연 포인트**

- 이슈 진행률과 최근 이슈·문서 목록을 짚는다.
- 숫자 자체보다 요약 화면의 역할을 설명한다.

### 4.3 프로젝트 채팅: 대화에서 이슈로 전환 (2:40~4:40)

**화면**: `/6/10/messages`

**대본**

> 실무에서는 업무 요청과 결정이 채팅에서 먼저 발생하지만, 채팅만으로 관리하면 시간이 지나면서 중요한 논의가 묻히게 됩니다.
>
> Threadia는 프로젝트 채팅에서 논의된 메시지를 이슈로 연결할 수 있습니다. 여기 보이는 기존 메시지는 `TWS-1` 이슈와 연결되어 있습니다.
>
> 이 방식으로 대화의 맥락은 유지하면서, 실행해야 할 업무는 이슈로 분리해 담당·상태·진행 상황을 관리할 수 있습니다. 채팅과 이슈가 분리되는 것이 아니라 하나의 흐름으로 이어지는 것이 핵심입니다.

**시연 포인트**

- 기존 메시지의 `→ TWS-1` 링크를 보여준다.
- `이슈로 만들기` 기능은 소개만 하고 실행하지 않는다.
- 연결된 이슈가 칸반에서 관리된다는 다음 흐름을 예고한다.

### 4.4 칸반 보드: 이슈 실행 상태 관리 (4:40~6:10)

**화면**: `/6/10/board`

**대본**

> 채팅에서 연결된 업무는 칸반 보드에서 실행 단위로 관리합니다. Threadia는 백로그, 할 일, 진행 중, 검토 중, 완료의 다섯 단계로 이슈 상태를 구분합니다.
>
> 팀원은 어떤 업무가 진행 중인지, 검토 대기 업무가 무엇인지, 완료된 결과가 무엇인지 한눈에 확인할 수 있습니다. 프로젝트 홈의 진행률도 이 이슈 상태를 바탕으로 집계됩니다.
>
> 이슈의 단순 목록뿐 아니라, 해당 이슈를 뒷받침하는 문서와의 연결 관계도 함께 관리합니다.

**시연 포인트**

- 다섯 상태 컬럼과 기존 이슈 카드를 보여준다.
- 새 이슈 추가, 카드 이동, 휴지통은 실행하지 않는다.

### 4.5 문서·그래프: 업무 맥락의 추적 (6:10~7:50)

**화면**: `/6/10/docs` → `/6/10/graph`

**대본**

> 이슈만으로는 기획 배경, 회의 결정, 작업 기록을 충분히 보존하기 어렵습니다. 그래서 Threadia는 프로젝트 문서와 회의록을 함께 관리합니다.
>
> 그래프 화면에서는 문서와 이슈를 노드로 표현하고, 서로 연결된 관계를 한눈에 볼 수 있습니다. 담당자가 바뀌거나 시간이 지난 뒤에도 특정 이슈가 어떤 문서와 연결되는지 빠르게 추적할 수 있습니다.
>
> 즉, Threadia는 단순히 할 일을 관리하는 도구가 아니라 업무가 왜 시작됐고 어떤 산출물과 연결되는지를 보존하는 도구입니다.

**시연 포인트**

- 문서 목록에서 작업 기록과 Sprint 계획이 존재함을 보여준다.
- 그래프의 문서·이슈 노드와 자동 정렬 버튼을 보여준다.
- 노드 클릭은 미리보기 목적일 때만 수행하고, 오래 머무르지 않는다.

### 4.6 백로그·프로젝트 설정: 관리자 운영 범위 (7:50~9:10)

**화면**: `/6/10/backlog` → `/6/10/settings`

**대본**

> 프로젝트 관리자는 백로그에서 이슈를 Sprint에 배정하고, 프로젝트 설정에서 멤버와 역할을 관리할 수 있습니다.
>
> 이 화면에서는 프로젝트 관리자와 일반 멤버의 역할을 분리하고, 같은 회사 구성원만 프로젝트에 초대할 수 있도록 권한 범위를 제한했습니다.
>
> 업무 관리 기능과 권한 관리 기능을 함께 제공함으로써, 팀 규모가 커져도 프로젝트 범위 안에서 안전하게 협업할 수 있습니다.

**시연 포인트**

- 백로그 이슈 목록과 Sprint 배정 UI를 소개한다.
- 프로젝트 멤버의 역할 목록과 초대 영역을 보여준다.
- Sprint 생성, 멤버 역할 변경·제거, 초대는 실행하지 않는다.

### 4.7 회사 관리: 조직과 프로젝트의 통합 관리 (9:10~10:20)

**화면**: `/6/settings`

**대본**

> 프로젝트보다 한 단계 위에서는 회사 관리 기능을 제공합니다. 회사 정보, 전체 프로젝트 수, 구성원 수, 부서 수, 프로젝트 상태 분포를 한 화면에서 확인할 수 있습니다.
>
> 따라서 회사 관리자는 조직 구조와 프로젝트 운영 현황을 분리된 서비스가 아니라 하나의 플랫폼에서 관리할 수 있습니다.

**시연 포인트**

- 회사 현황 카드와 부서 목록을 보여준다.
- 회사 정보 수정, 부서 추가·삭제는 실행하지 않는다.

### 4.8 플랫폼 관리자: 서비스 운영과 감사 (10:20~12:40)

**계정 전환**: 플랫폼 관리자 계정

**화면**: `/platform/support-cases` → `/platform/settings` → `/platform/audits`

**대본**

> 지금까지는 회사와 프로젝트 내부의 협업 흐름을 보여드렸습니다. 마지막으로 서비스 운영자 관점의 기능을 소개하겠습니다.
>
> 플랫폼 관리자 콘솔에서는 문의와 신고를 접수 상태부터 처리 상태까지 관리할 수 있습니다. 공개 답변은 사용자에게 노출되고, 내부 메모는 관리자만 확인할 수 있도록 분리했습니다.
>
> 시스템 설정에서는 공지 배너, 제재 기간과 사유, 답변 템플릿, 고객센터 정책을 관리합니다. 설정 값에는 버전을 두어 운영 변경의 기준을 추적할 수 있게 했습니다.
>
> 마지막으로 운영 로그에서는 문의 처리, 설정 변경, 권한 변경 등 관리자 행위를 감사 기록으로 조회할 수 있습니다. 사용자 협업 기능뿐 아니라 운영 책임성까지 고려했다는 점이 Threadia의 확장 범위입니다.

**시연 포인트**

- 문의 상세의 공개 답변·내부 메모 분리 UI를 보여준다.
- 시스템 설정의 정책 항목과 버전을 보여준다.
- 감사 로그의 action 필터를 보여준다.
- 문의 상태 변경, 답변·메모 등록, 설정·권한 변경은 실행하지 않는다.

### 4.9 배포와 품질: 실제 서비스 운영 기반 (12:40~14:00)

**화면**: 발표 자료의 Architecture 슬라이드 또는 README Architecture

**대본**

> Threadia는 실제 배포 환경까지 구성했습니다. 사용자는 `threadia.click`로 HTTPS 접속하고, Nginx가 Frontend와 Backend 컨테이너로 요청을 전달합니다.
>
> Backend는 private network의 RDS MySQL과 통신하며, 배포는 GitHub Actions, ECR, S3 release manifest, SSM을 통해 전달됩니다. 이미지 digest와 health check를 기반으로 배포 실패 시 기존 버전을 유지할 수 있도록 구성했습니다.
>
> 기능 구현뿐 아니라 테스트, Build, API, DB, 화면 검증 기준을 문서화하고 검증 evidence를 남기는 방식으로 품질을 관리했습니다.

**시연 포인트**

- 서비스 화면에서 인프라 콘솔로 이동하지 않는다.
- Architecture는 다이어그램 한 장으로만 설명한다.

### 4.10 마무리 (14:00~15:00)

**대본**

> Threadia는 채팅에서 발생한 논의를 이슈로 전환하고, 문서와 연결하며, 칸반과 그래프를 통해 업무의 진행 상태와 맥락을 함께 관리합니다.
>
> 여기에 회사·프로젝트·플랫폼 관리자 역할을 분리하고, 조직 관리와 운영 감사 기능까지 제공해 팀 협업과 서비스 운영을 하나의 플랫폼으로 연결했습니다.
>
> 앞으로는 실시간 협업과 알림 고도화, 검색 품질 개선, 협업 데이터 분석 기능을 확장해 나갈 계획입니다. 감사합니다.

## 5. 발표 중 유의사항

| 상황 | 대응 |
|---|---|
| 3D 허브 WebGL 실패 | 레일에서 프로젝트 화면으로 즉시 이동하고, 3D 허브는 지원 환경에서 제공되는 보조 진입점이라고 짧게 설명한다. |
| 네트워크 지연 | 새로고침을 반복하지 말고 미리 준비한 다음 화면 탭으로 이동한다. |
| 플랫폼 관리자 계정 전환 지연 | 프로젝트 기능 시연을 먼저 마친 뒤, 별도 탭에서 준비한 플랫폼 콘솔을 연다. |
| 질문으로 시간이 부족 | 문서·그래프와 플랫폼 관리자 중 한 화면만 짧게 보여주고 결론으로 이동한다. |
| 데이터 변경 우려 | 조회 전용 화면 이동만 수행한다. 입력·저장·변경·삭제 버튼은 누르지 않는다. |

## 6. 핵심 한 문장

> Threadia는 대화, 이슈, 문서, 조직, 운영 데이터를 연결해 업무의 실행과 맥락이 분리되지 않도록 만든 통합 협업 플랫폼이다.
