---

## 1. 문서 목적

이 문서는 플랫폼 관리자 `F`의 인가 모델을 확정한다. 기존 A/P/C 권한 체계와 플랫폼 운영자 권한을 분리해, S15 플랫폼 관리자 기능을 후속 설계와 WBS 재작성으로 넘길 수 있는 기준을 만든다.

이 문서는 구현 상세가 아니라 권한 모델과 운영 정책의 결정 기록이다. API endpoint, DB column 상세, 화면 layout은 후속 설계 문서에서 확정한다.

---

## 2. 배경

기존 canonical 문서에서 `F/S15`는 Sprint 1 제외, Sprint 2 최우선 후보로만 정리되어 있다. `S15`에는 전체 플랫폼 운영, 회사 목록, 시스템 설정, 운영 로그가 필요하다고 기록되어 있으나 세부 인가 모델은 확정되지 않았다.

기존 A/P/C 권한은 사용자 계정 자체에 고정하지 않고 membership 관계에서 판정한다.

| 권한 영역 | 기준 |
|---|---|
| 회사 권한 | `company_members.role` |
| 프로젝트 권한 | `project_members.role` |
| 로그인 가능 계정 | `users` |

플랫폼 관리자는 특정 회사나 프로젝트에 소속된 관리자가 아니라 서비스 전체를 운영하는 주체다. 따라서 기존 `company_members` 또는 `project_members`에 `F`를 추가하지 않는다.

---

## 3. 결정 요약

| 항목 | 결정 |
|---|---|
| 로그인 계정 | `users`는 일반 로그인 계정으로 유지한다. |
| 사용자 단일 role | `users.role`은 만들지 않는다. |
| 플랫폼 관리자 권한 | 별도 `platform_admins` 개념으로 분리한다. |
| 회사/프로젝트 권한과의 관계 | `company_members.role`, `project_members.role`과 섞지 않는다. |
| 정지/비활성화 정책 | 삭제가 아니라 상태 변경으로 처리한다. |
| 관리자 조치 기록 | 모든 관리자 조치에 사유와 audit log를 강제한다. |
| 문의/신고 처리 | `support_cases` 개념으로 묶고 `type = INQUIRY / REPORT`로 구분한다. |

## 4. 플랫폼 관리자 역할 모델

플랫폼 관리자 권한은 `platform_admins`로 분리한다.

| 역할 | 책임 |
|---|---|
| `PLATFORM_ADMIN` | 고객센터 문의 처리, 신고 처리, 사용자 정지, 회사 비활성화, 운영 로그 조회 |
| `SUPER_ADMIN` | 플랫폼 관리자 권한 부여/회수, 시스템 설정 변경, 공지/점검 배너 발행, 제재 preset 관리 |

초기 구현은 `PLATFORM_ADMIN`과 `SUPER_ADMIN` 두 단계만 둔다. 더 세분화된 고객센터 담당자, 보안 담당자, 결제 담당자 등은 운영 규모가 커진 뒤 별도 결정으로 분리한다.

---

## 5. 기존 A/P/C 권한과의 경계

| 구분 | 권한 기준 | 관리 범위 |
|---|---|---|
| A 일반 사용자 | `company_members.role = MEMBER`, `project_members.role = MEMBER` | 소속 프로젝트 업무 수행 |
| P 프로젝트 관리자 | `project_members.role = PROJECT_ADMIN` | 특정 프로젝트 운영 |
| C 회사 관리자 | `company_members.role = COMPANY_ADMIN` | 회사 workspace와 회사 내 프로젝트 관리 |
| F 플랫폼 관리자 | `platform_admins` | 전체 플랫폼 운영, 고객센터, 신고, 제재, 시스템 운영 |

F는 회사 관리자 C의 상위 버전이 아니다. F는 여러 회사와 사용자에 걸친 운영 조치를 수행하는 별도 platform-level 권한이다.

---

## 6. 관리자 조치 정책

플랫폼 관리자가 수행하는 변경성 조치는 삭제가 아니라 상태 변경을 기본으로 한다.

| 대상 | 처리 정책 |
|---|---|
| 사용자 | `SUSPENDED` 상태로 정지한다. 물리 삭제하지 않는다. |
| 회사 | 비활성화 상태로 전환한다. 회사 데이터는 보존한다. |
| 문의/신고 | 상태 전이와 답변 기록을 남긴다. |
| 시스템 설정 | 변경 전후 값과 변경 사유를 기록한다. |

사용자 정지 시 로그인, token refresh, `/auth/me` 성공 조건은 기존 `users.status = ACTIVE` 기준과 연결한다. 회사 비활성화는 회사 workspace 진입과 회사 하위 프로젝트 액션 차단 정책으로 후속 설계한다.

## 7. Audit log 원칙

모든 플랫폼 관리자 조치는 audit log 대상이다.

| 원칙 | 내용 |
|---|---|
| 사유 필수 | case 생성, 상태 변경, public reply, internal note는 본문과 별개의 3~500자 reason 없이 수행할 수 없다. |
| 행위자 기록 | 일반 사용자 case 생성 또는 플랫폼 관리자 조치의 actor와 authority source, 관리자 role을 기록한다. |
| 대상 기록 | 사용자, 회사, 문의/신고, 설정 중 어떤 대상에 대한 조치인지 기록한다. |
| 변경 전후 기록 | 상태 변경과 설정 변경은 변경 전후 값을 보존한다. |
| case 연결 | 문의/신고에서 발생한 조치는 가능한 경우 `support_case_id`와 연결한다. |

Audit log는 운영자 책임 추적과 장애/분쟁 대응을 위한 원장이다. 화면 표시용 활동 피드나 사용자 알림과 동일한 개념으로 합치지 않는다.

### 7.1 WBS 4.10.1 구현 결정

- platform API namespace는 `/api/v1/platform`이다.
- `PLATFORM_ADMIN`과 `SUPER_ADMIN`은 모두 support case를 처리할 수 있다.
- 최초 `SUPER_ADMIN`은 singleton bootstrap lock row를 transaction에서 먼저 잠근 뒤 `platform_admins`가 비었을 때만 환경변수 email과 일치하는 기존 ACTIVE 사용자로 bootstrap한다. 동시 instance는 같은 row에서 직렬화하며, 기존 관리자 또는 선행 instance가 생성한 관리자가 있으면 email 변경으로 승격·교체하지 않고 no-op한다.
- public reply와 internal note는 별도 table과 API로 분리한다. internal note는 일반 사용자 query와 DTO에 포함하지 않는다.
- `admin_action_audits`는 actor, authority source/role, action, target, reason, before/after state, timestamp, `support_case_id`를 보존하며 mutation과 같은 transaction에 저장한다.
- `SecurityConfig`의 broad permit 정책을 platform authorization으로 간주하지 않고, bearer token 해석 후 service에서 `platform_admins`를 조회해 인가한다.

## 8. 범위에서 제외한 대안

| 대안 | 제외 이유 |
|---|---|
| `users.role = PLATFORM_ADMIN` | 사용자 계정과 운영 권한이 결합되어 기존 membership 기반 권한 모델과 충돌한다. |
| `company_members.role`에 F 추가 | F는 특정 회사 소속 권한이 아니므로 부적절하다. |
| `project_members.role`에 F 추가 | F는 특정 프로젝트 운영자가 아니므로 부적절하다. |
| 관리자 조치 물리 삭제 | 감사 추적과 분쟁 대응이 어렵다. |
