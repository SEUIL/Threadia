## 0. 작성 규칙

### 기록 대상

`docs/01-planning/` 원본 archive에서 승격된 canonical 확정 문서의 의미가 바뀌면 이 문서에 변경 묶음을 추가한다.

대상 예시는 다음과 같다.

| 유형 | 경로 |
|---|---|
| 요구사항 | `docs/02-requirements/` |
| 설계 | `docs/03-design/` |
| API | `docs/04-api/` |
| 프로젝트 운영 기준 | `docs/00-project/` |
| 확정 결정 | `docs/07-decisions/` |

## 2026-07-17 WBS 4.8.1 Notification Core Backend 계약

> 변경이력 묶음 ID: WBS 4.8.1 Notification Core Backend 계약 ^change-2026-07-17-wbs-481-notification-core-backend

### 1. 목적

WBS `4.8` 알림 parent를 `4.8.1` Backend와 `4.8.2` Frontend로 실행 분리하고, 기존 MySQL 알림 DDL을 사용하는 inbox 목록, unread count, 개별 read, 조건부 read-all Backend 계약을 확정한다.

### 2. 변경 원칙

## 2026-07-16 Issue 응답에 reporterUserId 추가와 S06 조회 정책 명시

> 변경이력 묶음 ID: Issue 응답에 reporterUserId 추가와 S06 조회 정책 명시 ^change-2026-07-16-issue-reporter-and-s06-query-policy

### 1. 목적

PR #111(WBS 4.4.2) 리뷰 지적을 반영하며 드러난 계약 공백 두 가지를 정리한다.

### 2. 문제와 결정

**(1) `reporterUserId` 부재로 "등록자" 권한을 판정할 수 없었다.**

trash/restore는 **P/C 또는 등록자**에게 허용되는데(`IssueService.trashOrRestore`) `IssueResponse`에 reporter가 없어, 클라이언트가 "내가 등록한 이슈"인지 알 수 없었다. 그 결과 일반 멤버가 자기 이슈를 휴지통에 넣는 UI를 만들 수 없어 기능분해표 `ISSUE-04`("P/C, 등록자")를 충족할 수 없었다.

→ `IssueResponse`에 `reporterUserId`를 추가한다. **표시용이 아니라 권한 판정용**이다. reporter는 immutable이므로 갱신 경로는 없다.

**(2) S06의 조회 정책이 문서에 없었다.**

API 계약은 백로그를 `unassignedOnly=true`로, Sprint 배정 이슈를 `sprintId` filter로 **각각** 조회하도록 정의한다. 그런데 S06은 한 화면에서 백로그와 모든 Sprint의 이슈를 동시에 보여주므로, filter를 그대로 쓰면 백로그 1회 + Sprint 수만큼 추가 호출(N+1)이 된다.

→ S06은 프로젝트 이슈를 **한 번만 조회한 뒤 `sprintId`로 그룹핑**한다. 결과는 filter를 쓴 것과 같다. filter 계약 자체는 유지하며 단건 조회가 필요한 화면에서 쓴다. 이 정책을 화면정의서 S06 설계 메모에 명시한다.

### 3. 변경 문서

| 문서 | 변경 내용 |
|---|---|
| `docs/04-api/API-명세서.md` | §13.6 full Issue contract 서술과 이슈 응답 예시 4곳에 `reporterUserId` 추가, 권한 판정용이라는 근거 명시 |
| `docs/03-design/화면정의서.md` | S06 설계 메모에 단일 조회 + 그룹핑 정책과 그 이유(N+1 회피) 추가 |

## 2026-07-15 Issue #113 Sprint 배정 해제 계약

> 변경이력 묶음 ID: Issue #113 Sprint 배정 해제 계약 ^change-2026-07-15-issue-113-sprint-unassignment

### 1. 목적

이슈를 Sprint에서 빼는 경로를 추가한다.

### 2. 문제

`sprint`를 바꿀 수 있는 경로가 배정(`POST /sprints/{sprintId}/issues`)과 Sprint 완료뿐이었고, `PATCH /issues/{issueId}`의 허용 필드에 `sprintId`가 없었다. 그래서 **한 번 배정하면 Sprint를 종료하기 전까지 되돌릴 수 없었다.** 잘못 배정하면 Sprint 전체를 끝내거나(다른 이슈까지 백로그로 감) 이슈를 버리고 다시 만드는 수밖에 없어, PLANNED 단계의 백로그 그루밍이 "넣기만 가능"한 상태였다.

### 3. 변경 원칙

- `PATCH /api/v1/issues/{issueId}`의 허용 필드에 `sprintId`를 추가하되 **해제 전용**으로 둔다. 명시 `null`이면 Sprint에서 떼고, non-null이면 `400 VALIDATION_ERROR`로 거절하며 `POST /sprints/{sprintId}/issues`를 안내한다.

- trashed 이슈의 변경은 기존대로 `409`다. Sprint 완료 시의 원자적 rollover 의미는 변경하지 않는다.

## 2026-07-04 OAuth handoff canonical 동기화

> 변경이력 묶음 ID: OAuth handoff canonical 동기화 ^change-2026-07-04-oauth-handoff-canonical-sync

### 1. 목적

PR #25와 PR #33 검토에서 확인된 실제 OAuth handoff 구현 방식을 canonical API/Frontend 문서에 반영한다. 기존 문서의 “추후 협의” 표현을 제거해 팀원이 OAuth callback 후 access token 복구 경로를 같은 기준으로 참조하게 한다.

### 2. 변경 원칙

- OAuth callback은 access token을 URL query/fragment나 callback JSON body로 노출하지 않는다.

- 기존 AUTH-03 범위와 endpoint는 유지하며, 구현된 handoff 경로만 문서화한다.

## 2026-07-03 Auth refresh endpoint 구현 반영

> 변경이력 묶음 ID: Auth refresh endpoint 구현 반영 ^change-2026-07-03-auth-refresh-endpoint

### 1. 목적

PR #24 review에서 확인된 OAuth callback 후 access token 복구 공백을 닫기 위해 `POST /api/v1/auth/refresh` 구현 상태를 backend 구조 문서에 반영한다.

### 2. 변경 원칙

- OAuth callback은 access token을 URL query/string에 노출하지 않고 refresh cookie만 설정한 뒤 frontend로 redirect한다.
- Frontend는 redirect 후 `POST /api/v1/auth/refresh`를 호출해 HttpOnly refresh cookie 기반으로 access token을 복구한다.
- Refresh 성공 시 기존 refresh token을 rotate/revoke하고, 새 refresh token은 `Set-Cookie`로만 전달하며 DB에는 hash만 저장한다.
- CSRF, endpoint별 authorization policy, refresh token reuse detection은 production-ready hardening 후속 과제로 유지한다.

### 3. 변경 문서

| 문서 | 변경 내용 |
|---|---|
| `docs/05-architecture/백엔드-구조.md` | 이메일 Auth 구현 범위에 `/auth/refresh`를 추가하고 OAuth redirect 후 access token 복구 경로, refresh token rotation 구현 상태, 남은 hardening 범위를 반영 |

### 4. 영향 범위

| 구분 | 영향 |
|---|---|
| 요구사항 | WBS 1.3 Auth API/OAuth 범위에서 OAuth callback 후 사용 가능한 로그인 흐름을 닫는다. |

## 2026-07-02 Auth API cookie 계약 보강

> 변경이력 묶음 ID: Auth API cookie 계약 보강 ^change-2026-07-02-auth-api-cookie-contract

### 1. 목적

WBS 1.3.1 이메일 Auth API 구현 전 login/logout 응답 shape, refresh token cookie 전달 방식, OAuth callback 응답 경계를 구현자가 같은 기준으로 볼 수 있게 canonical 문서에 고정한다.

### 2. 변경 원칙

- Access token은 JSON body와 `Authorization: Bearer` header 흐름으로 사용하고, refresh token은 response body에 노출하지 않는다.
- Login/refresh 성공 시 refresh token은 `Set-Cookie`로만 전달하며 `HttpOnly`, `SameSite=Lax`, `Path=/`, `Max-Age=1209600`을 사용한다. 운영 HTTPS 환경에서는 `Secure`를 사용한다.
- Logout은 대상 refresh token을 revoke하고 같은 `Path=/` cookie를 `Max-Age=0`으로 만료시킨다.
- OAuth callback은 이메일 login과 동일한 Threadia access/refresh token pair를 발급하지만, callback endpoint의 직접 HTTP response shape를 login JSON 응답과 동일하다고 확정하지 않는다.

### 3. 변경 문서

| 문서 | 변경 내용 |
|---|---|
| `docs/04-api/API-명세서.md` | login 응답에 `tokenType`, `expiresIn`, refresh token `Set-Cookie` header를 명시하고 logout clear cookie와 OAuth callback 응답 경계를 보강 |
| `docs/05-architecture/프론트엔드-구조.md` | access token memory, refresh cookie `Path=/`, `Max-Age=1209600`, logout cookie 만료, OAuth callback 전달 방식 미확정 경계를 보강 |
| `docs/05-architecture/백엔드-구조.md` | Backend Auth 구현 기준에 refresh token body 미노출, `Set-Cookie` 전용 전달, login/logout cookie header 기준을 추가 |
| `docs/00-project/sprint-운영/sprint-1-백엔드-dod.md` | Backend DoD와 완료/미완료 기준에 login `Set-Cookie`, logout clear cookie, refresh token body 미노출 검증을 추가 |

## 2026-06-27 DB schema 관리 방식 변경

## 2026-07-15 Invitation 응답에 projectName 추가

> 변경이력 묶음 ID: Invitation 응답에 projectName 추가 ^change-2026-07-15-invitation-response-project-name

### 1. 목적

PROJECT scope 초대 응답에 표시용 `projectName`을 추가해, 초대 수신 화면(S14 수신, `/invitations`)이 어느 프로젝트로부터 온 초대인지 보여줄 수 있게 한다.

### 2. 문제

`GET /api/v1/users/me/invitations`는 PROJECT 초대에 `projectId`만 내려주고 프로젝트 이름을 주지 않았다. 그런데 초대 대상자는 아직 그 프로젝트의 member가 아니라 `GET /api/v1/projects/{projectId}`가 `403`이므로, **수신 화면이 프로젝트 이름을 알아낼 방법이 없었다.** 회사에 프로젝트가 여러 개면 사용자는 어느 프로젝트인지 모른 채 수락하게 된다.

Issue #108에 곁가지로 적어둔 항목인데, PR #114(후보 조회 API)의 범위에 없는 상태로 이슈가 `Closes #108`로 닫히면서 함께 묻혔다.

### 3. 변경 원칙

- `InvitationResponse`에 `projectName`을 추가한다. **PROJECT scope에서만 채우고 COMPANY scope는 `null`**이다.

- 받은 초대 목록은 COMPANY와 PROJECT가 섞여 내려오므로 `projectId`를 모아 한 번에 조회한다(초대마다 개별 조회하면 N+1). PROJECT 초대가 하나도 없으면 조회하지 않는다.
- 표시용 필드이므로 action 처리와 권한 검증에는 계속 `id`/`scopeType`/`companyId`/`projectId`/`inviteeUserId`를 쓴다.
- DB schema, invitation 생성·수락 의미, 권한 계약은 변경하지 않는다.

## 2026-07-15 초대 후보 조회 email 노출 범위 정정

> 변경이력 묶음 ID: 초대 후보 조회 email 노출 범위 정정 ^change-2026-07-15-invitable-member-lookup-enumeration-fix

### 1. 목적

바로 앞 묶음(Issue #108 프로젝트 초대 후보 exact-email 조회 API)이 확정한 후보 조회 error semantics를 정정한다. 후보가 아닌 email의 응답이 갈려서, 이 endpoint의 권한 범위인 "프로젝트"를 넘어 전역 서비스 가입 여부가 PROJECT_ADMIN에게 노출됐다.

### 2. 문제

기존 계약은 대상 user가 없으면 `404 NOT_FOUND`, 존재하지만 ACTIVE user가 아니거나 다른 회사면 `409 TARGET_NOT_ACTIVE_COMPANY_MEMBER`였다. 구현도 전역 email 조회를 먼저 하고 회사 소속을 나중에 검사했다. 그 결과 PROJECT_ADMIN이 임의의 email을 넣어 404와 409를 구분하는 것만으로 **해당 email의 Threadia 가입 여부를 판별**할 수 있었다(user enumeration). 이 정보는 원래 `GET /api/v1/users/lookup`의 COMPANY_ADMIN 전용 계약으로만 접근 가능했다.

프론트에서는 막을 수 없다. 응답 코드는 네트워크 계층에 그대로 남고, 호출자는 화면을 거치지 않고 API를 직접 호출할 수 있다.

### 3. 변경 원칙

- 후보 조회 범위를 **해당 프로젝트 회사의 ACTIVE company member로 한정**한다. 미가입, 비ACTIVE user, 다른 회사 소속은 호출자가 구분할 수 없도록 전부 `404 NOT_FOUND`로 통일한다.
- self, ACTIVE 프로젝트 멤버, live pending invitation은 기존 `409` conflict code를 유지한다. 이미 같은 회사 안에서 확인 가능한 정보라 노출 문제가 없다.
- 생성 endpoint(`POST /projects/{projectId}/invitations`)는 `inviteeUserId`를 받으므로 `409 TARGET_NOT_ACTIVE_COMPANY_MEMBER`를 그대로 둔다.
- 후보 조회는 아무것도 쓰지 않으므로 프로젝트 행 비관적 락(`SELECT ... FOR UPDATE`)을 제거하고 readOnly 트랜잭션으로 바꾼다. 이메일 입력마다 호출되는 경로가 같은 프로젝트의 쓰기 작업과 직렬화되던 문제를 없앤다. eligibility 최종 판정은 기존대로 생성 endpoint가 담당한다.
- `UserLookupService`의 C-only global lookup, 회사 구성원 목록 계약, invitation 생성 의미, DB schema는 변경하지 않는다.

|---|---|
| `docs/04-api/API-명세서.md` | §6/§6-A endpoint 표, §6-A Invitation 정책, §13.5-A 후보 조회 예시의 error semantics를 404 통일과 readOnly 기준으로 정정 |
