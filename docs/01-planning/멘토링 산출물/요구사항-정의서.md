## 2. 프로젝트 개요

Threadia는 Jira, Slack, Confluence처럼 분리된 협업 도구의 흐름을 하나의 프로젝트 협업 서비스로 통합하는 것을 목표로 한다.

핵심 흐름은 이슈, 채팅, 쓰레드, 문서, 그래프, 알림을 연결해 업무 맥락이 흩어지지 않게 하는 것이다.

```text
알림 수신
→ 이슈 확인
→ 이슈 또는 문서의 쓰레드에서 논의
→ 필요 시 프로젝트 채팅 또는 1:1 DM으로 소통
→ 문서에 결정사항 정리
→ 문서와 이슈를 연결
→ 그래프에서 연결 관계 확인
→ 변경사항을 알림으로 회수
```

## 3. 사용자 유형

| 코드 | 사용자 유형 | 설명 | 주요 권한 |
|---|---|---|---|
| A | 일반 사용자 | 소속 프로젝트 안에서 업무를 수행하는 사용자 | 이슈 확인/상태 변경, 문서 작성, 채팅/DM, 알림 확인 |
| P | 프로젝트 관리자 | 특정 프로젝트의 운영 담당자 | 프로젝트 설정, Sprint 운영, 이슈 관리, 문서/그래프 관리 |
| C | 회사 관리자 | 회사 workspace의 관리 담당자 | 회사 정보, 부서, 구성원, 권한, 프로젝트 관리 |
| F | 플랫폼 관리자 | 전체 서비스 운영 담당자 | Sprint 1 제외, Sprint 2 최우선 후보 |

| 권한 기준 | 설명 |
|---|---|
| 회사 권한 | `company_members.role` 기준 |
| 프로젝트 권한 | `project_members.role` 기준 |
| Sprint 1 인증 | `users.status = ACTIVE` 사용자만 로그인, OAuth callback, token refresh, `/auth/me` 성공 |

## 4. 범위 기준

Threadia 문서는 MVP 전체 reference와 Sprint 1 실제 구현 범위를 분리한다.

| 구분 | 기준 |
|---|---|
| MVP reference | 전체 서비스가 최종적으로 제공할 기능 계약 |
| Sprint 1 implementation | Auth only, Spring Boot/MySQL/Frontend skeleton, CI/PR baseline, Auth flows |
| Sprint 1.5 candidate | 등록 사용자 대상 company invitation |
| Sprint 2 이후 | project invitation, 플랫폼 관리자, 고급 협업 기능, 보류 기능 |

### 4.1 Sprint 1 확정 범위

| 영역 | 포함 항목 |
|---|---|
| Backend | Spring Boot skeleton, MySQL 연결 확인, Auth entity, Auth API |
| Frontend | React + Next 구조, 로그인/회원가입/비밀번호 재설정 route, Auth API 연동 |
| DB | `users`, `oauth_accounts`, `password_reset_tokens`, `refresh_tokens` 정합성 확인 |
| Auth | 이메일 회원가입/로그인/로그아웃, Google OAuth, 비밀번호 재설정, token refresh, `/auth/me` |
| CI/PR | 초기 `./gradlew test`, skeleton 안정화 후 build/GitHub Actions 확대 |

### 4.2 Sprint 1 제외 범위

아래 항목은 MVP reference에는 남기되 Sprint 1 구현 범위에서는 제외한다.

## 8. 수용 기준

### 8.1 Sprint 1 Auth 수용 기준

| 기능 ID | 수용 기준 |
|---|---|
| AUTH-01 | 이메일은 저장·조회·비교 전 `trim + lowercase`로 정규화한다. 중복 이메일은 가입할 수 없다. 가입 성공 시 `users` row가 생성된다. |
| AUTH-02 | 로그인, token refresh, `/auth/me`는 `users.status = ACTIVE`인 사용자만 성공한다. 로그아웃 시 refresh token은 invalidation된다. |
| AUTH-03 | OAuth callback 성공 시 `oauth_accounts`를 통해 사용자를 매핑하거나 생성한다. 이메일만 같다는 이유로 기존 계정에 blind auto-link하지 않는다. |
| AUTH-04 | reset token 원문은 저장하지 않고 hash/만료/사용 시각을 관리한다. `password-reset/confirm` 성공 시 해당 사용자의 기존 `refresh_tokens`를 revoke한다. |

### 8.2 MVP reference 수용 기준

| 영역 | 수용 기준 |
|---|---|
| 권한 | A/P/C 권한은 회사/프로젝트 소속 테이블에서 판정한다. |
| 프로젝트 | 프로젝트 삭제는 물리 삭제가 아니라 `ARCHIVED` 상태로 처리한다. |
| 이슈/칸반 | 칸반은 `BACKLOG`, `TODO`, `IN_PROGRESS`, `IN_REVIEW`, `DONE` 5컬럼을 기본으로 한다. A는 `DONE` 이동이 제한된다. |
| 문서 | 문서와 회의록은 `.md` 저장 기준을 사용한다. 문서와 이슈는 양방향 연결될 수 있다. |
| 메시지/이슈 연결 | 프로젝트 메시지만 이슈로 전환할 수 있다. DM 메시지는 이슈로 전환할 수 없다. |
| 그래프 | 문서-이슈 연결은 그래프 뷰의 node/edge에 반영된다. |
| 알림 | `notification_events`는 알림 사건 원본이고, `notification_recipients`는 사용자별 수신/읽음 상태다. |

### 8.3 Sprint 1.5 Invitation 수용 기준

| 기능 ID | 수용 기준 |
|---|---|
| INVITE-01 | lookup email은 `trim + lowercase`로 정규화하고 등록 사용자 exact match만 반환한다. |
| INVITE-02 | 회사 초대는 `PENDING`, `ACCEPTED`, `DECLINED`, `CANCELED`, `EXPIRED` 상태를 가진다. 기본 만료 기간은 7일이다. |
| INVITE-03 | accept 시점에만 `company_members` membership을 생성한다. 만료된 초대 수락은 `409 INVITATION_EXPIRED`로 거절한다. |
| INVITE-04 | 취소된 초대는 수락할 수 없다. |

## 9. 비기능 요구사항

| 분류 | 요구사항 |
|---|---|
| 인증/인가 | JWT Bearer access token과 refresh token을 사용한다. refresh token은 서버에 hash로 저장하고 rotation/revoke 상태를 추적한다. |
| 계정 상태 | login, OAuth callback, token refresh, `/auth/me`는 `users.status = ACTIVE`인 사용자에게만 허용한다. |
| 이메일 정규화 | signup, login, password reset, OAuth 계정 연결, invitation lookup의 email은 모두 `trim + lowercase` 기준을 따른다. |
| 시간 | 모든 서버 생성 시각과 만료 시각은 UTC 기준으로 생성, 저장, 비교하고 API 응답은 ISO-8601 UTC `Z` 형식으로 반환한다. |
| DB 관리 | DB schema는 `docs/03-design/ERD.md`와 `db/schema.sql` 기준으로 관리한다. |
| DB 변경 이력 | DB schema 변경 이유, 대상, 영향 범위는 `docs/07-decisions/DB-schema-변경이력.md`에 기록한다. |
| JPA 설정 | JPA는 schema 생성보다 mapping 검증에 사용한다. `spring.jpa.hibernate.ddl-auto=validate`를 권장하고 `update`에 의존하지 않는다. |
| Migration tool | Sprint 1에서는 Flyway/Liquibase versioned migration을 구성하지 않는다. |
| 보안 | token, password, 개인정보, secret은 코드, 로그, 문서, PR 본문에 노출하지 않는다. |
| 알림/활동 | `activity_events`는 활동 원장, `notification_events`는 알림 사건 원본으로 분리한다. |
| Redis | Redis는 원본 저장소가 아니라 cache/push 보조 계층으로만 사용한다. |
| 검증 | Backend는 `./gradlew test` 또는 `./gradlew build`, API는 curl/Postman, Frontend는 브라우저 확인을 기준으로 검증한다. |
