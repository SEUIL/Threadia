# Acorn 최종 프로젝트 기획 방법

## 프로젝트 주제

**클라우드 서버(AWS)를 활용한 그룹웨어 클라우드 플랫폼 구축**

1일차 회의 결과, 구현 방향은 **Jira + Confluence + Slack을 합쳐놓은 경량 애자일 협업 플랫폼**으로 잡는다. 전체 그룹웨어를 넓게 만들기보다 업무/이슈, 문서/회의록, 공지/알림을 중심으로 기능을 좁힌다.

이 프로젝트는 6주 안에 완성해야 하므로, 처음부터 모든 그룹웨어 기능을 구현하려고 하면 위험하다. 1주차에는 코드를 많이 작성하는 것보다 **무엇을 만들지, 무엇은 만들지 않을지, 누가 무엇을 책임질지, 어떤 기준으로 완료를 판단할지**를 먼저 정해야 한다.

## 한 줄 결론

6주 프로젝트에는 **가벼운 Scrum + 1주 Lean Inception + 하네스 기반 협업 규칙**이 적합하다.

| 구분 | 의미 | 이번 프로젝트 적용 |
|---|---|---|
| Lean Inception | 짧은 기간에 목표, 범위, MVP, 리스크를 합의하는 기획 방식 | 1주차 기획에 사용 |
| Scrum | 짧은 Sprint 단위로 계획, 구현, 리뷰, 회고를 반복하는 방식 | 2~6주차 운영에 사용 |
| 하네스 운영 | 팀원이 같은 규칙으로 작업하고 검증받게 만드는 구조 | `README`, PR Template, CI, 리뷰 규칙에 적용 |

## 6주 전체 운영 구조

| 주차 | 목표 | 핵심 산출물 |
|---:|---|---|
| 1주차 | 5일 기획, 범위 확정, 협업 규칙 세팅 | 기획서 초안, 화면정의서 초안, ERD 초안, API 명세서 초안, 개발 명세서 초안, Sprint 1 Backlog |
| 2주차 | 프로젝트 기반 구축 | repository, Spring Boot/React+Next 구조, MySQL 연결, CI 통과, 개발 명세서 갱신 |
| 3주차 | 핵심 기능 1차 구현 | 게시판/공지, 일정/할 일 등 주요 기능 |
| 4주차 | 핵심 기능 2차 구현 및 AWS 연동 | 파일 업로드, 관리자 기능, AWS 배포 초안 |
| 5주차 | 통합, 버그 수정, UX 정리 | 통합 테스트, 배포 안정화, 발표 자료 초안, 제출 문서 통합 점검 |
| 6주차 | 최종 안정화와 발표 준비 | 최종 배포, 시연 시나리오, 발표 자료, 제출 문서 최종본 |

> [!warning]
> 6주 프로젝트에서 가장 위험한 패턴은 1주차에 범위를 넓게 잡고, 4~5주차에 통합하면서 무너지는 것이다. 1주차의 핵심은 기능 욕심을 줄이고 완료 기준을 명확히 하는 것이다.

## 제출 문서 주차별 작성 흐름

| 제출 문서 | 작성 시작 | 이후 보정 시점 | 완료 기준 |
|---|---|---|---|
| 기획서 | 1주차 2일차 | 1주차 5일차 MVP freeze 후 | 배경, 목표, 주요 기능, 기대효과가 현재 MVP와 일치 |
| 화면정의서 | 1주차 2일차 | 2주차 Frontend route 초안 생성 후 | 주요 화면과 이동 흐름, 화면별 핵심 기능이 있음 |
| ERD | 1주차 3일차 | 2주차 domain/entity 구현 중 | 핵심 table과 관계가 MVP/API 범위와 일치 |
| API 명세서 | 1주차 3일차 | 2주차 API 후보 구현 중 | Method, URL, 권한, 설명이 화면/기능과 연결 |
| 개발 명세서 | 1주차 5일차 | 2주차부터 Sprint마다 갱신 | 기능, 경로/파일, 완료 조건, 검증 방법이 있음 |

## 1주차 기획 진행 방식

### Day 1. OT, 목표 공유, Repository 준비

첫 회의는 2시간 OT 중심으로 운영한다. 기술 세부 설계보다 **프로젝트의 성공 조건, 팀 운영 방식, GitHub repository 생성 전 결정사항**을 먼저 정한다.

결정할 것:

- 프로젝트 한 줄 목표: Jira + Confluence + Slack을 합쳐놓은 경량 애자일 협업 플랫폼
- 주요 사용자
- 반드시 구현할 기능 후보
- 시간이 부족하면 제외할 기능 후보
- GitHub repository 이름과 owner
- 기본 branch와 `main` 직접 push 금지 원칙
- README 한 줄 설명 초안

예시:

```text
우리 프로젝트는 Jira + Confluence + Slack을 합쳐놓은 경량 애자일 협업 플랫폼을 구축한다.
```

MVP 후보:

| 우선순위 | 기능 | 설명 |
|---:|---|---|
| 필수 | 로그인/권한 | 사용자, 관리자 구분 |
| 필수 | 업무/이슈 관리 | Jira 역할의 작업 관리 기능 |
| 필수 | 문서/회의록 관리 | Confluence 역할의 지식 공유 기능 |
| 필수 | 공지/알림 | Slack 역할을 우선 공지/알림 중심으로 축소 |
| 필수 | 관리자 기능 | 사용자/게시글 관리 등 최소 관리 기능 |
| 선택 | 파일 업로드 | S3 연동 가능하면 포함 |
| 선택 | 댓글/검색 | 시간이 남으면 추가 |
| 보류 | 실시간 채팅 | 구현 난이도와 통합 리스크가 큼 |
| 보류 | 복잡한 전자결재 | 6주 MVP 범위로는 과함 |

### Day 2. Repository 세팅, 사용자 흐름과 기능 분해

2일차에는 GitHub repository를 실제로 생성하고 팀원이 접근할 수 있는지 확인한다. 단, 이때는 협업 공간을 여는 정도로 제한하고, `AGENTS.md`, PR Template, CI, branch protection은 4일차에 확정한다.

기능 이름만 정하면 구현 중 해석이 달라진다. 각 기능은 사용자 흐름으로 쪼개야 한다.

예시:

```text
PM 또는 관리자 로그인
→ 프로젝트와 팀원 관리
→ 업무/이슈 등록
→ 문서/회의록 작성
→ 팀원이 대시보드에서 업무와 공지 확인
→ 선택 기능이 가능하면 파일 첨부 확인
```

산출물:

- GitHub repository URL
- 팀원 clone 가능 여부
- README 초안
- Issue 후보 목록
- 사용자 시나리오 2~3개
- 기능 목록
- 기능별 우선순위
- 화면 목록 초안
- API 목록 초안
- 화면정의서 초안 입력값

### Day 3. 기술 스택과 Architecture 결정

기술 스택은 새롭고 화려한 것보다 팀원이 구현 가능한 조합을 우선한다.

권장 기본안:

| 영역 | 선택지 |
|---|---|
| Backend | Java, Spring Boot, Gradle |
| DB | MySQL 8.4 |
| Frontend | React + Next, 필요 시 Three.js/TypeScript |
| Infra | AWS EC2, S3 |
| CI | GitHub Actions |
| 협업 | GitHub Issues, Pull Request, Discord 또는 Slack |

초기 Architecture는 단순하게 잡는다.

```text
Frontend
→ Spring Boot API Server
→ RDS Database
→ S3 File Storage
→ EC2 Deployment
```

이날 결정해야 할 것:

- DB 종류
- AWS에서 사용할 서비스 범위
- ERD 초안
- API 명세서 초안
- API URL 규칙
- branch 전략
- local 실행 방법

### Day 4. 협업 규칙과 하네스 세팅

하네스는 팀원이 같은 방식으로 일하게 만드는 운영 장치다. 2일차에 만든 repository를 기준으로 4일차에 최소한 아래를 정해야 한다.

| 하네스 요소 | 목적 |
|---|---|
| `README.md` | 실행 방법과 프로젝트 구조 고정 |
| `AGENTS.md` 또는 협업 규칙 문서 | AI 사용, 코드 작성, 리뷰 기준 고정 |
| PR Template | PR 제출 전 자기 점검 강제 |
| GitHub Actions | test/build 자동 검증 |
| Code review 규칙 | 위험한 변경을 사람 리뷰로 확인 |

팀 규칙 최소안:

1. 모든 코드는 작성자가 설명할 수 있어야 한다.
2. PR 전에는 local test 또는 build를 실행한다.
3. AI를 사용했다면 PR에 사용 범위를 적는다.
4. `.env`, API key, token, password, 개인정보는 AI에 입력하지 않는다.
5. 인증/인가, DB schema, AWS 배포 변경은 단독 merge하지 않는다.
6. CI 실패 PR은 merge하지 않는다.
7. 기능 완료는 말이 아니라 실행 결과와 PR 기준으로 판단한다.

### Day 5. Sprint 1 계획, 검증, 발표/리스크 정리

마지막 날에는 Week 2에 바로 개발을 시작할 수 있게 Sprint 1 Backlog를 만들고, 발표 목차와 리스크 대응표까지 함께 정리한다. 기존 6일차 발표 정리와 리스크 점검은 5일차 후반으로 흡수한다.

Backlog 항목에는 아래 4개가 반드시 있어야 한다.

| 항목 | 설명 |
|---|---|
| 담당자 | 누가 책임지는지 |
| 완료 조건 | 어떤 상태가 되면 끝난 것인지 |
| 검증 방법 | 어떻게 확인할 것인지 |
| 의존성 | 먼저 끝나야 하는 작업이 있는지 |

Sprint 1 예시:

| 작업 | 담당 | 완료 조건 | 검증 방법 |
|---|---|---|---|
| Spring Boot 기본 프로젝트 생성 | Backend | local 실행 가능 | `./gradlew bootRun` |
| DB 연결 설정 | Backend/DB | MySQL 8.4 연결 성공 | repository test |
| 로그인 API 초안 | Backend | 로그인 요청/응답 동작 | Postman 또는 curl |
| 기본 화면 구조 | Frontend | 라우팅과 layout 구성 | 브라우저 확인 |
| GitHub Actions CI | Infra | PR에서 build 자동 실행 | CI 초록 체크 |
| README 작성 | PM/문서 | 실행 방법 문서화 | 팀원이 보고 실행 가능 |

마지막에 함께 확인할 것:

- 최종 MVP 범위
- 발표 목차
- 3~5분 시연 시나리오
- 리스크 대응표
- Week 2 진입 조건 checklist
- 제출 문서 5종 진행 상태: 기획서, 화면정의서, ERD, API 명세서, 개발 명세서

## 팀장 운영 원칙

팀장은 모든 코드를 직접 작성하는 사람이 아니라, **결정 지연과 통합 실패를 막는 사람**이다.

### 회의 운영

매일 회의는 15~30분으로 제한한다.

질문은 3개만 반복한다.

1. 어제 한 일은 무엇인가?
2. 오늘 할 일은 무엇인가?
3. 막힌 것은 무엇인가?

회의에서 피해야 할 것:

- 결론 없는 기술 토론
- 담당자 없는 작업
- 완료 조건 없는 작업
- “나중에 정하자” 반복
- 말로만 완료 처리

### 팀원 이끄는 방식

| 상황 | 팀장의 대응 |
|---|---|
| 팀원이 무엇을 해야 할지 모름 | 작업을 1~2일 안에 끝나는 단위로 쪼개서 배정 |
| 특정 팀원이 계속 막힘 | 개인 탓보다 blocker를 확인하고 페어 작업 배정 |
| 기능 욕심이 커짐 | MVP와 보류 기능을 분리 |
| PR이 늦어짐 | 작은 PR을 자주 올리게 유도 |
| 통합이 불안함 | CI, code review, daily check로 조기 감지 |

## 역할 분담 초안

팀원 수에 따라 조정하되, 책임 영역은 반드시 나눈다.

| 역할 | 책임 |
|---|---|
| PM/팀장 | 일정, 회의, 범위 조절, 최종 통합 판단 |
| Backend | API, 인증/인가, 비즈니스 로직 |
| DB | ERD, schema, query, data consistency |
| Frontend | 화면, routing, API 연동 |
| Infra/AWS | EC2, RDS, S3, 배포, secret 관리 |
| QA/문서/발표 | 테스트 시나리오, README, 발표 자료, 시연 흐름 |

역할은 사람을 고정하는 것이 아니라 책임 공백을 막기 위한 것이다. 한 사람이 여러 역할을 맡을 수 있고, 어려운 영역은 2명이 같이 맡는 것이 좋다.
