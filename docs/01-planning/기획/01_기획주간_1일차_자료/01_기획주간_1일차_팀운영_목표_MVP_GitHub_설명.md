# 기획주간 1일차 팀 운영 목표 MVP GitHub 설명

## 목적

이 자료는 1일차 OT에서 팀원들에게 **기획주간 운영 방식, 프로젝트 목표를 정하는 방식, MVP 후보를 나누는 방식, GitHub 협업 흐름, repository 생성 전 결정사항**을 설명하기 위한 자료다.

1일차는 실제 구현을 시작하는 날이 아니다. 오늘의 핵심은 팀원들이 같은 흐름으로 움직일 수 있게 기준을 맞추고, 2일차에 바로 repository 생성과 기능 분해를 시작할 수 있는 입력값을 남기는 것이다.

## 오늘 설명할 5가지

| 순서 | 설명할 내용 | 목표 |
|---:|---|---|
| 1 | 팀 운영 방식 | 회의-작업-공유-마무리 구조 이해 |
| 2 | 프로젝트 목표 | 팀이 만들 서비스의 한 줄 방향 잡기 |
| 3 | MVP 후보 | 필수/선택/보류 기능 구분 방식 이해 |
| 4 | GitHub 흐름 | Issue→branch→PR→review→merge 흐름 이해 |
| 5 | repository 결정 | 이름, owner, 기본 branch, 직접 push 금지 원칙 합의 |

## 1. 팀 운영 방식 설명

### 설명할 핵심

이번 1주차 기획은 매일 아래 흐름으로 진행한다.

```text
회의
→ 작업 묶음 배정
→ 팀원별/그룹별 작업
→ 결과 공유
→ 황스일 종합
→ 다음 회차 입력값 확정
```

팀장은 모든 작업을 직접 하는 사람이 아니라, 결정이 지연되지 않게 하고 작업 결과가 다음 단계로 이어지게 만드는 역할을 한다.

### 팀원들이 이해해야 할 기준

| 기준 | 설명 |
|---|---|
| 회의 | 오늘 결정할 것과 작업 묶음을 정한다. |
| 작업 | 1명부터 4명까지 필요한 인원수로 나눠 진행한다. |
| 공유 | 작업 결과를 Notion 또는 공용 채널에 남긴다. |
| 종합 | 황스일이 중복, 누락, 충돌을 정리한다. |
| 마무리 | 다음날 바로 쓸 입력값을 확정한다. |

### 팀원에게 말할 문장

```text
이번 주는 코드를 많이 치는 주가 아니라, 2주차부터 개발을 시작할 수 있게 기준을 맞추는 주입니다.
매일 회의에서 할 일을 나누고, 작업 결과를 공유하고, 마지막에 다음날 쓸 입력값을 확정하는 방식으로 진행하겠습니다.
```

## 2. 프로젝트 목표 논의

### 설명할 핵심

목표는 길게 쓰는 것이 아니라, 팀 전체가 같은 방향을 볼 수 있게 **한 줄 문장**으로 정한다.

이번 프로젝트 주제는 다음과 같다.

```text
클라우드 서버(AWS)를 활용한 그룹웨어 클라우드 플랫폼 구축
```

이 주제를 그대로 구현하려고 하면 범위가 너무 넓다. 따라서 1일차에는 “우리 팀이 6주 안에 실제로 보여줄 수 있는 그룹웨어가 무엇인지”를 좁혀야 한다.

### 목표 문장 예시

```text
우리 프로젝트는 Jira + Confluence + Slack을 합쳐놓은 경량 애자일 협업 플랫폼을 구축한다.
```
### 팀원들이 써본 그룹웨어 플랫폼

```text
오늘 목표는 완벽한 문서를 쓰는 것이 아니라, 팀원들이 같은 프로젝트를 상상하게 만드는 것입니다.
목표 문장은 길게 쓰지 않고 한 줄로 정하겠습니다.
```

## 3. MVP 후보 논의

### 설명할 핵심

MVP는 “최소 기능 제품”이다. 이번 프로젝트에서는 6주 안에 구현하고 발표에서 보여줄 수 있는 최소 기능 묶음으로 본다.

모든 기능을 넣으려고 하면 통합이 늦어지고 발표 직전에 무너질 가능성이 크다. 그래서 기능을 처음부터 **필수 / 선택 / 보류**로 나눈다.

### 기능 구분 기준

| 구분 | 의미 | 예시 |
|---|---|---|
| 필수 | 없으면 그룹웨어로 보기 어려운 기능 | 로그인/권한, 업무/이슈 관리, 문서/회의록 관리, 공지/알림 |
| 선택 | 시간이 남으면 추가할 기능 | 파일 업로드, 댓글, 검색 |
| 보류 | 구현 난도나 통합 리스크가 큰 기능 | 실시간 채팅, 복잡한 전자결재 |

### MVP 후보 초안

| 우선순위 | 기능 | 설명 |
|---:|---|---|
| 필수 | 로그인/권한 | 일반 사용자와 관리자 구분 |
| 필수 | 업무/이슈 관리 | Jira 역할의 작업 관리 기능 |
| 필수 | 문서/회의록 관리 | Confluence 역할의 지식 공유 기능 |
| 필수 | 공지/알림 | Slack 역할을 우선 공지/알림 중심으로 축소 |
| 필수 | 관리자 기능 | 팀원, 프로젝트, 공지 관리의 최소 범위 |
| 선택 | 파일 업로드 | S3 연동 가능성이 있으면 포함 |
| 선택 | 댓글/검색 | 시간이 남으면 추가 |
| 보류 | 실시간 채팅 | WebSocket과 실시간 처리 리스크가 큼 |
| 보류 | 복잡한 전자결재 | 6주 MVP 범위로는 과할 수 있음 |

### 팀원에게 말할 문장

```text
오늘은 기능을 많이 정하는 것보다, 반드시 해야 할 것과 나중으로 미룰 것을 나누는 게 중요합니다.
필수 기능은 6주 안에 구현하고 발표에서 보여줄 수 있는 것만 넣겠습니다.
```

## 4. GitHub 흐름 설명

### 설명할 핵심

GitHub는 코드 저장소만이 아니라, 작업 흐름을 관리하는 공간으로 사용한다.

우리 팀의 기본 흐름은 아래와 같다.

```text
Issue 생성
→ branch 생성
→ 작업
→ PR 생성
→ review 및 검증
→ main merge
```

### 단계별 의미

| 단계 | 의미 | 팀원이 해야 할 것 |
|---|---|---|
| Issue | 해야 할 작업 단위 | 작업 내용, 완료 조건, 담당자를 적는다. |
| branch | 작업 전용 공간 | `main`이 아니라 새 branch에서 작업한다. |
| PR | 작업 결과 공유 | 무엇을 바꿨고 어떻게 확인했는지 적는다. |
| review | 병합 전 확인 | 코드, 문서, 실행 결과, 위험 변경을 확인한다. |
| merge | `main`에 반영 | 리뷰와 검증이 끝난 뒤 반영한다. |

### main 직접 push 금지

`main`은 팀의 기준 branch다. 각자 바로 push하면 다른 팀원의 작업과 충돌하거나, 실행되지 않는 코드가 기준 branch에 들어갈 수 있다.

따라서 기본 원칙은 아래처럼 잡는다.

- 개인 작업은 branch에서 한다.
- 작업 결과는 PR로 올린다.
- PR에는 변경 내용과 확인 방법을 적는다.
- 리뷰 또는 확인 없이 `main`에 직접 push하지 않는다.
- DB, 인증/인가, 배포 관련 변경은 혼자 merge하지 않는다.

### 팀원에게 말할 문장

```text
main은 항상 팀이 기준으로 삼는 branch로 유지하겠습니다.
개인 작업은 branch에서 하고, main에는 PR을 통해서만 합치겠습니다.
```

## 5. Repository 결정

### 오늘 결정할 것

오늘 repository를 완성하지는 않는다. 대신 2일차에 바로 생성할 수 있도록 아래 항목을 정한다.

| 결정 항목 | 권장안 | 비고 |
|---|---|---|
| repository 이름 | 팀에서 알아보기 쉬운 영문 이름 | 예: `groupware-cloud-platform` |
| owner | 황스일 개인 계정 또는 팀 조직 계정 | 팀원 초대 가능해야 함 |
| default branch | `main` | GitHub 기본값과 맞춤 |
| 직접 push 원칙 | `main` 직접 push 금지 | PR 기반 협업을 위해 필요 |
| README 초안 | 프로젝트 한 줄 설명만 우선 작성 | 실행 방법은 4일차 이후 보강 |

### 2일차에 할 것과 미룰 것

| 구분 | 2일차에 할 것 | 4일차 이후로 미룰 것 |
|---|---|---|
| repository | 생성, 팀원 초대, clone 확인 | branch protection 강제 |
| README | 프로젝트 한 줄 설명, 기술 후보, TBD 표시 | 확정 실행 방법 |
| branch | `main` 직접 push 금지 원칙 공유 | 세부 보호 규칙 |
| Issue | 기능 분해 결과를 Issue 후보로 정리 | label/milestone 세부 운영 |
| 협업 문서 | 임시 규칙 메모 | `AGENTS.md`, PR Template, CI |

### 팀원에게 말할 문장

```text
오늘은 repository를 완성하는 날이 아니라, 내일 바로 만들 수 있게 이름과 기준을 정하는 날입니다.
CI, PR Template, AGENTS.md는 기술 구조가 더 정리된 뒤 4일차에 확정하겠습니다.
```

## 회의 진행용 요약 스크립트

```text
오늘은 2시간 OT라서 세부 설계나 구현까지 들어가지는 않겠습니다.

먼저 이번 주 운영 방식은 회의-작업-공유-마무리 구조로 진행하겠습니다.
매일 시작할 때 오늘 정할 것과 작업 묶음을 정하고, 작업 후에는 결과를 공유한 뒤 다음날 입력값을 확정합니다.

프로젝트 목표는 길게 쓰지 않고 한 줄로 정하겠습니다.
현재 주제는 AWS를 활용한 그룹웨어 클라우드 플랫폼 구축이고, 1일차 회의에서는 Jira + Confluence + Slack을 합쳐놓은 경량 애자일 협업 플랫폼 방향으로 좁혔습니다.

기능은 필수, 선택, 보류로 나누겠습니다.
로그인/권한, 업무/이슈 관리, 문서/회의록 관리, 공지/알림은 필수 후보로 보고, 파일 업로드나 댓글/검색은 선택, 실시간 채팅이나 복잡한 전자결재는 보류 후보로 보겠습니다.

GitHub 작업은 Issue를 만들고, branch에서 작업하고, PR로 올리고, review 후 main에 merge하는 흐름으로 가겠습니다.
main에는 직접 push하지 않는 것을 기본 원칙으로 하겠습니다.

오늘 repository는 완성하지 않고, 이름, owner, 기본 branch, README 한 줄 설명까지만 정하겠습니다.
실제 repository 생성과 clone 확인은 2일차에 진행하고, AGENTS.md, PR Template, CI는 4일차에 확정하겠습니다.
```
