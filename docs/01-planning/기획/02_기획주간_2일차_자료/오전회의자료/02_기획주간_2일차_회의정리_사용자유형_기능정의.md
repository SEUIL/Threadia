# 기획주간 2일차 회의 정리 - 사용자 유형과 기능 정의

## 정리 목적

이 문서는 Notion `2주차 해야 할 일` 페이지에 회의 중 정리한 내용을 바탕으로, 2일차 산출물로 사용할 **사용자 유형표, 기능 정의표, 분업 기준, 다음 작업**을 한 페이지에 다시 정리한 것이다.

이번 회의의 핵심은 프로젝트를 단순 그룹웨어가 아니라 **플랫폼 > 회사 > 프로젝트** 구조를 가진 경량 애자일 협업 플랫폼으로 보는 것이다.

```text
플랫폼
└── 회사
    └── 프로젝트
        └── 사용자
```

## 핵심 방향

| 항목 | 정리 내용 |
|---|---|
| 프로젝트 주제 | Jira + Confluence + Slack을 합쳐놓은 경량 애자일 협업 플랫폼 |
| 해결하려는 문제 | 업무, 문서, 알림, 대화가 여러 도구에 흩어져 생기는 맥락 단절 |
| 핵심 방향 | 회사 단위로 프로젝트를 만들고, 프로젝트 안에서 업무/문서/알림/댓글을 연결 |
| 문서 운영 원칙 | 모든 문서는 가능하면 `.md`로 관리 |
| 작업 단위 원칙 | 칸반, Sprint, 문서 등 하나의 주제는 하나의 thread 또는 연결된 흐름으로 관리 |

## 전회차 입력값

| 입력값 | 처리 기준 |
|---|---|
| 프로젝트 한 줄 목표 | Jira + Confluence + Slack을 합쳐놓은 경량 애자일 협업 플랫폼 방향 재확인 |
| 주요 사용자 | 1일차에 못 끝낸 항목이므로 2일차 첫 안건으로 확정 |
| MVP 후보 기능 | 필수/선택/보류로 재분류 |
| 보류 기능 원칙 | 실시간, 복잡한 결재 등 범위 초과 기능 먼저 제외 |
| repository 이름/owner | 팀장이 결정한 값을 공유하고 바로 생성 |
| README 한 줄 설명 초안 | repo 생성 직후 임시 README에 반영 |
| 확정 기술 스택 | MySQL 8.4, Spring Boot, React + Next, AWS EC2/S3 기준으로 기능 분해 |

## 사용자 유형 정의

Notion 회의 메모에서는 사용자 유형을 아래 약어로 정리했다.

| 약어 | 사용자 유형 | 관리 범위 | 핵심 역할 |
|---|---|---|---|
| A | 일반 사용자 | 소속 프로젝트 | 업무 수행, 문서 확인/작성, 알림 확인 |
| P | 프로젝트 관리자 | 특정 프로젝트 | 프로젝트 생성 이후 업무/이슈, Sprint, 칸반, 문서 흐름 관리 |
| C | 회사 관리자 | 특정 회사 | 회사 정보, 부서, 구성원, 권한, 회사 내 프로젝트 관리 |
| F | 플랫폼 관리자 | 전체 플랫폼 | 전체 회사와 서비스 운영 관리. MVP에서는 별도 관리 기능으로 분리하거나 보류 |

> [!note]
> 권한은 사용자 자체에 고정하기보다 회사/프로젝트 소속 관계에 붙이는 것이 안전하다. 예를 들어 한 사용자가 A 회사에서는 회사 관리자이고, B 프로젝트에서는 일반 사용자일 수 있다.

## 기능 정의 원칙

| 구분 | 기준 | 예시 |
|---|---|---|
| 필수 기능 | 없으면 시연과 핵심 흐름이 성립하지 않는 기능 | 로그인/회원가입, 회사/프로젝트 생성, 업무/이슈, 칸반, 문서/회의록 |
| 선택 기능 | 시간이 남으면 붙일 수 있는 기능 | DM, 알림 세부 설정, 검색, 통계 |
| 보류 기능 | 구현 리스크가 크거나 MVP 범위를 넓히는 기능 | 복잡한 결재, 실시간 고도화, 과도한 관리자 기능 |

## 전체 기능 후보

| 우선순위 | 기능 | 사용자 | 설명 | 비고 |
|---|---|---|---|---|
| 필수 | 로그인, 회원가입 | A, P, C | 서비스 진입점 | F는 내부 운영자로 별도 처리 가능 |
| 미정 | 문서관리 시스템 | A, P, C | Confluence의 문서관리 시스템을 채용할지 결정 필요 | `.md` 관리 원칙과 연결 |

## 회사 관리자 기능

회사 관리자는 회사 단위 설정과 사람 관리를 담당한다. 프로젝트 관리자와 일반 사용자 기능을 포함해서 사용할 수 있다.

| 우선순위 | 기능 | 사용자 | 설명 |
|---|---|---|---|
| 필수 | 회사 만들기 | C | 회사 workspace 생성 |
| 필수 | 회사 정보 관리 | C | 회사명, 설명, 기본 정보 등록/수정 |
| 필수 | 부서 정보 관리 | C | 부서 등록, 수정, 삭제 |
| 필수 | 구성원 초대/등록 | C | 회사에 소속될 사용자 초대 또는 등록 |
| 필수 | 구성원 권한 관리 | C | 일반 사용자, 프로젝트 관리자, 회사 관리자 권한 부여 |
| 선택 | 회사관리 WBS | C | 회사 관리 기능을 작업 단위로 분해 |

## 프로젝트 관리자 기능

프로젝트 관리자는 특정 프로젝트 안의 업무, 일정, 문서, Sprint 흐름을 관리한다. 일반 사용자 기능을 포함해서 사용할 수 있다.

| 우선순위 | 기능 | 사용자 | 설명 |
|---|---|---|---|
| 필수 | 프로젝트 생성 | P | 회사 안에 프로젝트 생성 |
| 필수 | 업무/이슈 CRUD | P | 업무와 이슈 등록, 조회, 수정, 삭제 |
| 필수 | 담당자 지정 | P | 업무/이슈에 담당자 지정 |
| 필수 | 칸반 보드 | P | 업무 상태를 칸반 흐름으로 관리 |
| 필수 | 백로그/Sprint | P | Sprint 작업 후보와 진행 단위 관리 |
| 필수 | 문서/회의록 `.md` | P | 프로젝트 문서와 회의록 작성/관리 |
| 선택 | 프로젝트 WBS | P | 프로젝트 기능을 작업 단위로 분해 |

## 일반 사용자 기능

일반 사용자는 본인이 속한 프로젝트 안에서 업무를 수행하고, 필요한 문서와 알림을 확인한다.

| 우선순위 | 기능 | 사용자 | 설명 |
|---|---|---|---|
| 필수 | 칸반 보드 | A | 업무 상태 확인 및 기본 조작 |
| 필수 | 백로그/Sprint | A | 할 일과 Sprint 작업 확인 |
| 필수 | 문서/회의록 `.md` | A | 문서 확인, 작성, 수정 |
| 선택 | 쓰레드/댓글 | A | 업무나 문서 단위의 댓글 흐름 |
| 선택 | 알림 | A | 업무, 댓글, 문서 변경 알림 on/off |
| 보류 후보 | 채팅/DM | A | thread에서 채팅으로 넘어갈 때 요약본 표시 아이디어 포함. 실시간 구현 범위는 별도 판단 필요 |

## WBS 적용 여부

WBS는 필요하지만, 지금 단계에서 너무 자세히 만들면 기능 변경 때마다 다시 고쳐야 한다. 따라서 **기능 정의 1차 정리 후 5일차 Sprint 1 Backlog 직전에 가볍게 작성**하는 방식이 적절하다.

| WBS ID | 대분류 | 작업 | 산출물 | 의존성 |
|---|---|---|---|---|
| 1.1 | 사용자/권한 | 사용자 유형 확정 | 사용자 유형표 | 없음 |
| 1.2 | 기능 정의 | 필수/선택/보류 기능 분류 | 기능 정의표 | 사용자 유형 |
| 2.1 | 회사 관리 | 회사 정보 관리 | 회사 관리 기능 명세 | 회사 관리자 정의 |
| 2.2 | 회사 관리 | 구성원 초대/권한 관리 | 권한 흐름 | 회사 정보 관리 |
| 3.1 | 프로젝트 관리 | 프로젝트 생성 | 프로젝트 기능 명세 | 회사 관리 |
| 3.2 | 프로젝트 관리 | 업무/이슈/칸반 관리 | 기능 명세 | 프로젝트 생성 |
| 4.1 | 문서/회의록 | `.md` 문서 관리 흐름 정의 | 문서관리 기준 | 프로젝트 관리 |

## 남은 쟁점

- 플랫폼 관리자 `F`를 실제 MVP 화면으로 구현할지, 내부 운영자 개념으로만 둘지 결정해야 한다.
- 회사 관리자와 프로젝트 관리자의 권한 경계를 명확히 해야 한다.
- 일반 사용자 안의 팀장/부팀장 같은 역할을 별도 권한으로 둘지, 프로젝트 관리자 역할로 흡수할지 결정해야 한다.
- 문서관리 시스템을 Confluence처럼 독립 기능으로 둘지, 프로젝트 문서/회의록 기능으로 축소할지 결정해야 한다.
- DM/실시간 채팅은 구현 리스크가 있으므로 선택 또는 보류 기능으로 두는 것이 안전하다.
