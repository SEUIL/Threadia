## 4. 조건부 확장 상세 기준

### 4.1 활동 피드

- MySQL `activity_events`를 원장으로 사용한다.
- STOMP push는 새 이벤트 신호 전달에만 사용한다.
- Redis cache는 최근 활동 목록 캐시에만 사용한다.
- NoSQL feed store는 Sprint 1에서 제외한다.

### 4.2 통합 검색

- Sprint 1 조건부 구현 시 MySQL `LIKE` 또는 FULLTEXT를 우선한다.
- 검색 전용 서버는 도입하지 않는다.
- Typesense/Meilisearch는 검색 품질 문제가 확인된 뒤 검토한다.

### 4.3 프로젝트 홈/대시보드

- MySQL aggregate query로 시작한다.
- 반복 조회 비용이 커지면 `project_dashboard_summaries`를 추가한다.
- Redis cache는 dashboard summary 응답 캐시에만 사용한다.

## 5. 6일차 이월 기술 검토 목록

아래 항목은 보류 기능이 아니라 구현 방식 결정이 필요한 기술 검토 사항이다. 4일차에는 확정하지 않고 6일차로 이월한다.

| 출처 | 검토 항목 | 6일차에서 정할 것 |
|---|---|---|
| API v2.0 | JWT 만료/갱신 방식 | refresh token 사용 여부 |
| API v2.0 | 이슈 목록 페이지네이션 | offset vs cursor 기준 |
| API v2.0 | 이슈 상태 변경 시 알림 자동 발송 | 서비스 레이어 자동 처리 여부 |
| API v2.0 | `from-message`에서 thread 자동 생성 | 메시지→이슈 전환 시 thread 생성 정책 |
| API v2.0 | 메시지 목록 실시간 업데이트 | polling vs STOMP push 기준 |
| API v2.0 | DM 방 unread count 처리 | `dm_room_user_states` 집계 vs 서비스 계산 |
| API/ERD | `activity_events`와 `notification_events` 운영 기준 | 분리 유지, 통합 조건, 구현 우선순위 |
| ERD v2.0 | `issues` 정렬용 position | 정수 간격 vs reorder API |
| ERD v2.0 | `threads` 자동 생성 정책 | 이슈/문서 생성 시 자동 생성 vs 수동 생성 |
| ERD v2.0 | attachments 테이블 | Sprint 1 이후 S3 presigned URL과 파일 권한 정책 |

## 6. 보류표 정합성 메모

- `소셜 로그인/비밀번호 찾기`는 더 이상 보류 항목이 아니다.
- `FEED/SEARCH/DASH`는 보류가 아니라 조건부 확장 항목이다.
- Redis는 원본 저장소로는 보류/제외하지만 cache와 STOMP push 보조 용도로는 조건부 채택한다.
- Typesense/Meilisearch는 검색 엔진 후보로만 남기고 Sprint 1에는 넣지 않는다.
