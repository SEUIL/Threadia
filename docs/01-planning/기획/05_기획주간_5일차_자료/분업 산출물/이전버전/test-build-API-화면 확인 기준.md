# test/build/API/화면 확인 기준

## 1. 목적
이 문서는 작업 완료 여부를 검증하기 위한 test, build, API, 화면 확인 기준을 정의한다.

완료 기준이 "무엇을 만족해야 하는가"를 설명한다면, 이 문서는 "어떻게 확인해야 하는가"를 설명한다. 작업자는 변경 범위에 맞는 검증을 수행하고, 리뷰어가 재확인할 수 있도록 실행 명령과 결과를 남긴다.

## 2. 검증 기본 원칙
- 변경 범위에 맞는 test, build, API, 화면 확인을 수행한다.
- 자동 검증이 가능한 항목은 명령어 실행 결과로 확인한다.
- 자동 검증이 어려운 항목은 API 응답, 화면 캡처, 수동 확인 결과로 증빙한다.
- 정상 케이스뿐 아니라 주요 실패 케이스와 예외 상태를 확인한다.
- 검증하지 못한 항목이 있다면 사유와 후속 조치를 남긴다.

## 3. Test 확인 기준
Test는 변경된 기능이 의도대로 동작하고 기존 기능을 깨뜨리지 않았는지 확인하는 절차다.

### 3.1 실행 명령
프로젝트에서 사용하는 명령어를 기준으로 실행한다.

```bash
npm run test
npm run lint
npm run typecheck
npm run test:unit
npm run test:integration
npm run test:e2e
```

다른 기술 스택은 프로젝트 기준에 따라 `yarn test`, `pnpm test`, `./gradlew test`, `mvn test`, `pytest` 등으로 대체한다.

### 3.2 확인 항목
- 변경된 로직에 대한 테스트가 추가 또는 수정되었다.
- 기존 테스트가 모두 통과한다.
- 실패 케이스, 입력값 검증, 권한 조건 등 주요 예외가 테스트되었다.
- 테스트가 없는 영역은 수동 검증 방법과 결과가 기록되었다.
- 실패한 테스트를 임의로 skip하거나 삭제하지 않았다.
- 필수 테스트 명령이 성공한다.
- 변경 범위와 관련된 테스트가 누락되지 않았다.
- 테스트 실패가 있는 경우 원인과 후속 조치가 명확하다.
- 테스트 결과가 PR 또는 작업 기록에 남아 있다.

## 4. Build 확인 기준
Build는 코드가 배포 가능한 상태인지 확인하는 절차다.

### 4.1 실행 명령
프로젝트 기준에 맞게 build 명령을 실행한다.

```bash
npm run build
npm run lint
npm run typecheck
```

다른 기술 스택은 프로젝트 기준에 따라 `yarn build`, `pnpm build`, `./gradlew build`, `mvn package` 등으로 대체한다.

### 4.2 확인 항목
- build가 오류 없이 완료된다.
- 타입 오류, 컴파일 오류, 번들링 오류가 없다.
- 환경 변수 또는 설정 누락으로 build가 실패하지 않는다.
- warning이 있는 경우 배포에 영향이 없는지 확인했다.
- 정적 파일, 이미지, 폰트 등 필요한 리소스가 build 결과에 포함된다.
- build 명령이 성공한다.
- 배포 환경에서 필요한 설정값이 정리되어 있다.
- build 실패 가능성이 있는 변경 사항이 해결되었다.
- build 결과 또는 CI 결과가 PR에 남아 있다.

## 5. API 확인 기준
API 확인은 Backend 기능 또는 Frontend 연동이 실제 요청과 응답 기준으로 올바르게 동작하는지 검증하는 절차다.

### 5.1 확인 대상
다음 변경이 있으면 API 확인을 수행한다.

- 신규 API 추가
- 기존 API 요청 또는 응답 구조 변경
- 인증, 권한, validation 변경
- 검색, 필터, 정렬, 페이징 변경
- DB 저장, 수정, 삭제 로직 변경
- 외부 API 또는 연동 로직 변경

### 5.2 요청 확인 예시
```bash
curl -X GET "http://localhost:8080/api/example" -H "Authorization: Bearer <token>"
curl -X POST "http://localhost:8080/api/example" -H "Content-Type: application/json" -H "Authorization: Bearer <token>" -d '{"name":"sample"}'
```

### 5.3 확인 항목
- 정상 요청 시 기대한 상태 코드와 응답 body가 반환된다.
- 필수값 누락, 잘못된 형식, 존재하지 않는 리소스 요청이 적절히 처리된다.
- 인증이 없거나 권한이 부족한 요청이 차단된다.
- 응답에 불필요한 내부 정보나 민감 정보가 포함되지 않는다.
- 검색, 필터, 정렬, 페이징 결과가 조건에 맞게 반환된다.
- 생성, 수정, 삭제 API는 DB 반영 결과까지 확인한다.
- API 실패 시 Frontend 또는 호출 측에서 처리 가능한 오류 형식이 반환된다.
- 정상 케이스와 주요 실패 케이스가 확인되었다.
- API 스펙과 실제 응답이 일치한다.
- 상태 코드, 에러 메시지, 응답 형식이 일관적이다.
- 요청/응답 예시 또는 테스트 결과가 PR에 남아 있다.

## 6. 화면 확인 기준
화면 확인은 사용자가 실제 흐름을 문제없이 수행할 수 있는지 검증하는 절차다.

### 6.1 확인 대상
다음 변경이 있으면 화면 확인을 수행한다.

- 신규 화면 또는 기존 화면 변경
- 버튼, 입력 필드, 문구, 레이아웃 변경
- 조회, 생성, 수정, 삭제 등 사용자 플로우 변경
- API 응답 또는 데이터 표시 방식 변경
- 권한, 인증, 상태값에 따른 노출 조건 변경
- 로딩, 빈 상태, 오류 상태 처리 변경

### 6.2 실행 전 준비
Frontend와 필요한 Backend/API 서버를 실행하고 확인 조건을 준비한다.

```bash
npm run dev
```

- 확인할 화면 URL
- 테스트 계정과 권한 조건
- 테스트 데이터
- 환경 변수 또는 feature flag
- Backend/API 서버 실행 상태

### 6.3 공통 확인 항목
- 대상 화면에 정상 진입할 수 있다.
- 흰 화면, 무한 로딩, 런타임 오류가 발생하지 않는다.
- 화면 문구, 버튼명, 라벨이 요구사항과 일치한다.
- API 또는 DB에서 받은 데이터가 올바른 위치에 표시된다.
- 날짜, 시간, 금액, 상태값 등 표시 형식이 적절하다.
- 화면 요소가 겹치거나 잘리지 않는다.
- 긴 텍스트나 많은 데이터가 들어와도 레이아웃이 깨지지 않는다.
- 개인정보, 내부 ID, 토큰 등 노출되면 안 되는 정보가 보이지 않는다.

### 6.4 사용자 플로우 확인 항목
- 목록 또는 상세 데이터가 정상 표시된다.
- 검색, 필터, 정렬, 페이징이 조건에 맞게 동작한다.
- 생성 또는 수정 성공 후 화면 상태가 최신 데이터로 갱신된다.
- 필수값 누락 또는 잘못된 입력 시 오류 메시지가 표시된다.
- 삭제 전 확인 절차가 제공되고 삭제 후 화면이 갱신된다.
- 저장 실패 또는 삭제 실패 시 사용자가 다음 행동을 알 수 있다.
- 중복 클릭 또는 중복 제출이 방지된다.
- 새로고침, 뒤로 가기, 재진입 시 화면 상태가 의도대로 유지된다.

### 6.5 상태별 확인 항목
- 로딩 상태가 표시된다.
- 데이터가 없을 때 빈 상태 안내가 표시된다.
- 검색 결과가 없을 때 적절한 안내가 표시된다.
- API 실패 또는 네트워크 실패 시 오류 안내가 표시된다.
- 권한이 없는 경우 접근 제한 또는 권한 안내가 표시된다.
- 세션 만료 시 로그인 이동 또는 재인증 안내가 제공된다.

### 6.6 반응형 확인 기준
최소 다음 화면 크기에서 확인한다.

| 구분 | 기준 |
| --- | --- |
| Mobile | 375px |
| Tablet | 768px |
| Desktop | 1440px |

확인 항목:

- 모바일에서 불필요한 가로 스크롤이 발생하지 않는다.
- 버튼과 입력 필드가 터치하기 충분한 크기다.
- 모달, 드롭다운, 팝오버, 테이블, 목록이 작은 화면에서도 사용 가능하다.
- 고정 버튼, 헤더, 하단 영역이 주요 콘텐츠를 가리지 않는다.

### 6.7 브라우저 및 접근성 확인 항목
기본 확인 브라우저는 Chrome 최신 버전으로 한다. 프로젝트 요구사항이 있으면 Safari, Edge, Firefox도 확인한다.

- 브라우저 콘솔에 치명적인 오류가 없다.
- 이미지, 폰트, 아이콘이 정상 로드된다.
- 주요 버튼, 링크, 입력 필드를 키보드로 이동하고 실행할 수 있다.
- 포커스 위치가 화면에서 확인된다.
- 아이콘만 있는 버튼에는 접근 가능한 이름 또는 설명이 있다.
- 텍스트와 배경의 명도 대비가 사용성을 해치지 않는다.
- 주요 사용자 플로우가 끝까지 동작한다.
- 로딩, 빈 상태, 오류, 권한 상태가 확인되었다.
- 최소 기준 화면 크기에서 레이아웃 문제가 없다.
- 콘솔에 치명적인 오류가 없다.
- 화면 증빙이 PR 또는 작업 기록에 남아 있다.

## 7. 작업 유형별 필수 검증
| 작업 유형 | 필수 검증 |
| --- | --- |
| Backend | test, build, API 정상/실패 케이스 확인 |
| Frontend | test, build, 화면 플로우 확인, API 연동 확인 |
| DB | migration 실행, 검증 쿼리, 관련 API 또는 화면 확인 |
| 문서 | 문서 내용, 링크, 명령어, 예시 확인 |
| PR | test/build 결과, API 또는 화면 증빙, CI 결과 확인 |

## 8. 검증 결과 작성 예시
PR 또는 작업 기록에는 아래 형식으로 검증 결과를 남긴다.

```markdown
## 검증 결과
- Test: npm run test 통과
- Build: npm run build 통과
- API:
  - GET /api/example 정상 응답 확인
  - 필수값 누락 시 400 응답 확인
- 화면:
  - Chrome Desktop 1440px 확인
  - Mobile 375px 확인
  - 목록 조회, 상세 진입, 생성/수정 플로우 확인
- 증빙:
  - 스크린샷 첨부
  - API 요청/응답 예시 첨부
- 미확인 항목: 없음
```

## 9. 완료 판정 기준
검증은 다음 조건을 모두 만족할 때 완료로 본다.

- 변경 범위에 맞는 test, build, API, 화면 확인을 수행했다.
- 실행 명령과 확인 결과가 기록되어 있다.
- 정상 케이스와 주요 예외 케이스를 확인했다.
- 실패 또는 미확인 항목이 있다면 사유와 후속 조치가 명확하다.
- 리뷰어가 동일한 조건으로 검증 결과를 재확인할 수 있다.

## 10. 완료로 보지 않는 경우
다음 중 하나라도 해당하면 검증 완료로 보지 않는다.

- test 또는 build 결과가 없다.
- API 변경이 있는데 요청/응답 확인 결과가 없다.
- 화면 변경이 있는데 스크린샷 또는 화면 확인 결과가 없다.
- 정상 케이스만 확인하고 주요 실패 케이스를 확인하지 않았다.
- 테스트 실패, build 실패, 콘솔 오류가 남아 있는데 사유가 없다.
- 미확인 항목이 후속 작업으로 추적되지 않는다.
