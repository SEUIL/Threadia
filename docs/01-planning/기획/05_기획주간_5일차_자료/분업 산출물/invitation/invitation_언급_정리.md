### 작업 묶음 6. Invitation을 구현했다면 예상되는 어려움 (v1.2 설계 기준 분석)

원본 문서에 "복잡해서/기간이 부족해서"라는 문장 자체는 없지만, v1.2 설계를 기준으로 실제 구현 시 부딪힐 지점을 정리하면 다음과 같다.

| 영역 | 어려움 |
| --- | --- |
| 상태 머신 관리 | `PENDING/ACCEPTED/EXPIRED/CANCELED` 4단계를 일관되게 굴리려면 만료 시각이 지난 PENDING을 배치 job으로 EXPIRED 전환할지, 조회 시점에 lazy 처리할지 결정 필요. Sprint 1 안에 스케줄러까지 넣기엔 부담 |
| 토큰 발급/검증 보안 | 토큰 생성 방식(길이, 충돌 가능성), URL 노출 시 만료·1회성 보장, 비로그인 사용자도 접근하는 새로운 인증 우회 경로가 생겨 별도 보안 검토 대상이 됨 |
| 가입 여부 분기 처리 | 초대 대상이 기존 가입자인지 아닌지에 따라 플로우가 갈라짐 — 가입자는 수락 시 즉시 `company_members` 생성, 미가입자는 "수락 → 회원가입 → 가입 완료 후 자동 소속 처리"까지 이어지는 별도 온보딩 플로우 필요. 즉시 등록 정책에는 이 분기가 없음(미가입이면 400으로 끝) |
| 이메일 실제 발송 여부 | QAO 검토에서도 끝까지 미정으로 남은 항목. 실발송하면 SMTP/SES 연동·실패 처리·템플릿이 늘고, 안 하면 "초대"가 인앱 알림과 차이가 없어져 기능 존재 의미가 약해지는 딜레마 |
| 중복/재초대 정책 | 동일 이메일 중복 초대 방지, PENDING 상태에 재초대 시 갱신할지 차단할지, 이미 소속된 사용자 재초대 시 409인지 PENDING 갱신인지 — 엣지케이스가 케이스별로 늘어남 |
| 알림/이벤트 타입 증가 | v1.2처럼 `MEMBER_INVITED` 이벤트, `INVITATION` 알림 설정 카테고리를 별도로 추가해야 해서 알림 시스템 범위가 늘어남 |

> 요약: 즉시 등록은 "이메일 입력 → INSERT 1번"으로 끝나지만, Invitation을 넣으면 상태 머신 + 토큰 보안 + 미가입자 온보딩 + 메일 발송 인프라 + 만료 배치 + 알림 이벤트까지 6갈래로 작업이 늘어나는 구조였다. 짧은 Sprint 1 기간에 들어가기 어려웠을 것으로 추정된다(문서에 명시된 결론이 아니라 v1.2 설계와 QAO 미해소 항목을 근거로 한 추정).

### 작업 묶음 7. 발표자료 흐름상 "S14 구현 요소 부족" 문제와 Invitation 재도입 검토

발표자료(`민정/day05/발표자료/발표자료/Threadia_1차_기획발표자료.pptx`) 화면 흐름에서 Invitation 제거로 S14(구성원·권한 관리)의 "초대 상태 표시" 요소가 빠지면서, 화면에 구현할 요소가 너무 적어 보인다는 의견이 나왔다. 이를 해결하기 위해 Invitation을 다시 추가하자는 제안이 있었다.

**현재 S14 구성 (`화면정의서_v3.md` L556~589)**

| 항목 | 내용 |
| --- | --- |
| 주요 액션 | 구성원 추가(즉시 등록), 역할 변경, PM 지정, 구성원 검색, 구성원과 1:1 DM 시작 |
| 구성원 추가 응답 분기 | 가입된 이메일 → 201 즉시 등록 / 이미 소속 → 409 / 미가입 → 400 |
| 필터 | `status`, `departmentId`, `q` |
| 연결 화면 | S13, S12, S11, S09 |

→ "초대 상태(PENDING 등)"만 없어진 것이고, 액션·필터·연결 화면 자체는 이미 5개 이상 존재해 화면이 완전히 빈 것은 아니다.

**검토 의견: Invitation 재도입은 권장하지 않음**

- Invitation을 다시 넣으면 작업 묶음 6에서 정리한 복잡도(상태 머신, 토큰 보안, 가입 분기, 메일 발송, 중복/재초대, 알림 이벤트) 전체가 그대로 돌아온다. 화면 요소를 채우려는 목적치고는 비용이 너무 크다.
- 즉시 등록 정책으로 단순화한 3일차 결정(작업 묶음 1, 6)을 발표 화면 구성 때문에 다시 뒤집는 것은 본말이 전도된 선택일 수 있다.

**대안: 이미 설계에 있지만 화면 구현에는 반영되지 않은 요소로 S14를 채우는 방안**

| 후보 요소 | 근거 |
| --- | --- |
| 부서 배정/변경 UI | `company_members.department_id`, S13/S14 연결 — ERD에는 있으나 화면 요소로는 미반영 |
| 역할 변경 confirm 모달 | "최소 1명 C 유지" 같은 정책(`기능 분해표 v3.0` MEMBER-03 인근)을 화면 인터랙션으로 구체화 |
| 구성원 상태(ACTIVE/SUSPENDED) 토글 | `company_members` 상태 변경 API(`PATCH .../company-members/{id}`)는 이미 정의되어 있음 |
| 구성원 검색/필터 UI 구체화 | API 매핑의 `status, departmentId, q` 필터를 화면 요소로 시각화 |

이 방향이면 Invitation 제거 결정(즉시 등록 정책)을 유지하면서도 S14 화면의 구현 요소를 늘릴 수 있다.

### 종합

- **확정 사실**: Invitation 테이블/엔티티는 3일차(`ERD 초안_v1.4`, `API 명세서 초안_v1.4`)에서 명시적으로 제거 결정되었고, 4일차 ERD v2.0까지 일관되게 유지됐다.
- **남아있는 점검 포인트**: 결정 이후 문서에서도 "구성원 초대", "멤버 초대"라는 용어와 "초대 수락", "초대 메일 발송 여부", "초대 token/status" 같은 표현이 일부 남아 있다(작업 묶음 3). 기능 명칭(초대)과 실제 구현 정책(즉시 등록, 테이블 없음)이 한 문서 안에서도 혼재된 경우가 있어, 향후 화면/API 용어를 "추가" 또는 "등록"으로 통일할지 여부를 확인할 필요가 있어 보인다.
- **제거 이유 추정**: 문서에 "복잡해서/기간 부족"이라는 문장은 직접 적혀 있지 않지만, v1.2 설계(작업 묶음 5)와 QAO 미해소 항목(작업 묶음 3)을 함께 보면 토큰/상태머신/만료/온보딩/메일발송 등 6갈래로 늘어나는 작업량이 즉시 등록 1줄로 단순화된 근거로 추정된다(작업 묶음 6).
- **재도입 검토 결과**: 발표자료 S14 화면 요소 부족 문제로 Invitation 재도입이 제안됐으나, 비용 대비 효과가 낮다고 판단된다. 대신 부서 배정, 역할 변경 confirm, 상태 토글, 검색/필터 UI 구체화로 화면 요소를 보강하는 대안을 검토 중이다(작업 묶음 7, 미확정).
