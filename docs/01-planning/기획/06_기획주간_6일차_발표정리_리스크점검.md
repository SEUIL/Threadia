# 기획주간 6일차 발표 정리와 리스크 점검

## 목적

6일차는 1~5일차 기획 산출물을 발표와 개발 착수 기준으로 묶어 **발표 목차, 시연 흐름, 리스크 대응표, Week 2 진입 조건**을 최종 점검하는 날이다.

기획주간을 다시 6일 구조로 운영하므로, 이 문서는 더 이상 5일차에 흡수된 보관 문서가 아니다. 5일차에서 확정한 Sprint 1 Backlog와 검증 기준을 입력값으로 받아 최종 발표/리스크/착수 조건을 정리한다.

## 전회차 입력값

| 입력값 | 없을 때 처리 |
|---|---|
| 최종 MVP 범위 후보 | 발표와 Sprint 1 범위가 흔들리므로 먼저 확정 |
| Sprint 1 목표 | Week 2 개발 방향 설명 불가 |
| Sprint 1 Backlog | 개발 착수 조건 판단 불가 |
| 작업별 권장 담당 그룹 크기 | 역할 분담 설명과 착수 준비가 불명확함 |
| 완료 조건 | 발표에서 검증 기준을 설명할 수 없음 |
| 검증 방법 | 리스크 대응과 PR 기준이 약해짐 |
| 의존성/blocker 목록 | Week 2 진입 여부 판단 불가 |
| GitHub repository와 clone 확인 결과 | 팀 개발 착수 가능 여부 확인 필요 |
| 제출 문서 5종 진행 상태 | 제출/발표 준비 누락 여부 확인 필요 |

## 해야될 목록

| 번호 | 해야될 일 | 산출물 | 권장 담당 그룹 |
|---:|---|---|---|
| 1 | 1~5일차 산출물 점검 | 산출물 체크리스트 | 2명 |
| 2 | MVP freeze | 최종 MVP 범위표 | 황스일 주도, 전체 합의 |
| 3 | 제출 문서 5종 진행 상태 점검 | 기획서/화면정의서/ERD/API 명세서/개발 명세서 상태표 | 황스일 종합, 2명 검토 |
| 4 | 발표 목차 작성 | 발표 목차 초안 | 2~3명 |
| 5 | 시연 시나리오 작성 | 3~5분 시연 흐름 | 정철진 우선, 2~3명 |
| 6 | 리스크 대응표 작성 | 리스크 대응표 | 여도현 우선, 2명 |
| 7 | Week 2 진입 조건 점검 | 시작 조건 checklist | 2명 |
| 8 | 발표 역할 분담 | 발표 파트별 담당자 | 황스일 종합 |

## 회의에서 먼저 정해야 할 것

| 결정 항목 | 기준 | 결과물 |
|---|---|---|
| MVP freeze | 6주 안에 구현 가능하고 시연 가능한 범위 | 최종 MVP 범위표 |
| 발표 구조 | 배경→목표→기능→설계→협업→일정→리스크 | 발표 목차 |
| 시연 흐름 | 구현 가능성과 화면/API 우선순위 기준 | 3~5분 시연 흐름 |
| 리스크 기준 | 일정, 기술, DB, 인증/인가, AWS, 협업 | 리스크 대응표 |
| Week 2 시작 조건 | Backlog, 담당 그룹, 검증 기준, blocker 대응 | 개발 착수 판단 |
| 제출 문서 상태 | 기획서, 화면정의서, ERD, API 명세서, 개발 명세서 | 제출 보완 목록 |

## 팀원 작업 시간 운영

### 작업 묶음 1. 기획 산출물 점검

| 산출물 | 확인할 내용 | 상태 기록 |
|---|---|---|
| 기획서 | 프로젝트 배경, 목표, 주요 사용자, MVP 범위가 들어갔는지 | 완료/보완 |
| 화면정의서 | 주요 화면과 사용자 흐름이 발표 가능한지 | 완료/보완 |
| ERD | 핵심 entity와 관계가 MVP 범위를 감당하는지 | 완료/보완 |
| API 명세서 | 주요 endpoint, 권한, 응답 형식이 정리됐는지 | 완료/보완 |
| 개발 명세서 | Week 2 착수 기준, 검증 기준, 담당 기준이 있는지 | 완료/보완 |
| 협업 규칙 | AGENTS, CLAUDE, CONTRIBUTING, PR Template, CI, AI 규칙이 개발에 적용 가능한지 | AGENTS/CLAUDE/CONTRIBUTING 완료, PR Template/CI 보완 |

### 작업 묶음 2. MVP freeze

| 구분 | 처리 기준 |
|---|---|
| 필수 기능 | Sprint 1 또는 6주 구현 계획에 포함 |
| 선택 기능 | 발표에는 가능하면 언급하되 Sprint 1에는 넣지 않음 |
| 보류 기능 | 구현 범위에서 제외하고 이유를 짧게 기록 |
| 변경 필요 기능 | Week 2 시작 전 승인 필요 작업으로 분리 |

### 작업 묶음 3. 발표 목차

| 순서 | 발표 파트 | 내용 |
|---:|---|---|
| 1 | 프로젝트 배경 | 왜 그룹웨어 클라우드 플랫폼인가 |
| 2 | 프로젝트 목표 | 한 줄 목표, 주요 사용자 |
| 3 | 팀 구성과 역할 | 황스일, 정철진, 담당 그룹 구조 |
| 4 | MVP 범위 | 필수/선택/보류 기능 |
| 5 | 사용자 시나리오 | 일반 사용자/관리자 흐름 |
| 6 | 화면 구성 | 주요 화면 목록 |
| 7 | DB/API 설계 | ERD 초안, 주요 endpoint |
| 8 | System Architecture | Spring Boot, MySQL 8.4, AWS EC2/S3 구조 |
| 9 | 협업 방식 | AGENTS, CLAUDE, CONTRIBUTING, PR Template, CI, docs 운영 |
| 10 | 6주 개발 일정 | Sprint 구조와 Week 2 Backlog |
| 11 | 리스크와 대응 | AWS, DB, 인증, 일정 리스크 |

### 작업 묶음 4. 시연 시나리오

| 단계 | 시연 내용 | 확인 기준 |
|---:|---|---|
| 1 | 로그인/회원가입 흐름 | 사용자 진입 흐름이 이해되는지 |
| 2 | 회사/프로젝트 진입 | 협업 공간 구조가 보이는지 |
| 3 | 프로젝트 홈/칸반 | 핵심 업무 관리 흐름이 보이는지 |
| 4 | 이슈 상세/문서 연결 | 문서와 업무 연결 가치가 보이는지 |
| 5 | 채팅/쓰레드/알림 | 협업 흐름이 하나의 제품처럼 연결되는지 |

시연은 실제 구현 범위가 아니라 발표용 우선순위다. Sprint 1 Backlog에 모두 넣지 않는다.

### 작업 묶음 5. 리스크 대응표

| 리스크 | 영향 | 대응 |
|---|---|---|
| MySQL 8.4 실행 방식 미정 | DB 연결과 배포 계획 지연 | local 실행 방식과 배포 방식을 분리해 확정 |
| React + Next 구조 과설계 | Frontend 구조 지연 | 초기에는 기본 routing/layout 중심으로 제한 |
| AWS DB 배포 방식 미정 | DB 배포 방식 변경 가능 | 2주차에는 EC2/S3 중심, DB 배포는 별도 결정 가능 |
| 인증/인가 복잡도 | 구현 지연 | A/P/C 권한 기준으로 제한하고 변경은 승인 필요 작업 처리 |
| 기능 범위 과다 | 통합 실패 | MVP 필수 기능 중심으로 freeze |
| CI 설정 지연 | PR 품질 관리 실패 | 초기에는 `./gradlew test`만 적용 |
| 문서와 코드 불일치 | 협업 혼선 | PR Template에 문서 변경 여부 체크 포함 |
