# 기획주간 6일차 보고 정리와 리스크 점검

## 목적

6일차는 1~5일차 기획 산출물을 보고 가능한 형태로 묶어 **보고 순서, 핵심 흐름 요약, 리스크 메모, Week 2 진입 조건 checklist, 제출 문서 5종 상태표, PPT 제작**을 정리하는 날이다.

기획주간을 다시 6일 구조로 운영하므로, 이 문서는 더 이상 5일차에 흡수된 보관 문서가 아니다. 5일차에서 확정한 Sprint 1 목표, Backlog, 담당 그룹, Definition of Done, 검증 방법, 의존성/blocker를 입력값으로 받아 기획 내용 보고와 Week 2 착수 조건을 정리한다.

## 전회차 입력값

| 입력값 | 없을 때 처리 |
|---|---|
| 최종 MVP 범위 후보 | 보고 내용과 Sprint 1 범위가 흔들리므로 먼저 정리 |
| Sprint 1 목표 | 5일차 보완 후 보고 순서에 반영 |
| Sprint 1 Backlog | 5일차 보완 후 Week 2 진행 방향에 반영 |
| 작업별 권장 담당 그룹 크기 | 5일차 보완 후 팀 역할 설명에 반영 |
| Definition of Done | 5일차 보완 후 검증 기준 요약에 반영 |
| 검증 방법 | 5일차 보완 후 PR/CI/수동 검증 요약에 반영 |
| 의존성/blocker 목록 | 5일차 보완 후 리스크 메모에 반영 |
| AWS 사용 범위 | EC2/RDS/S3 사용 확정. 계정은 직접 생성하고 비용은 본인 부담. 실제 배포와 S3 파일 저장 구현은 Sprint 1 이후로 반영 |
| GitHub repository와 clone 확인 결과 | 팀 개발 착수 가능 여부 확인 필요 |
| 제출 문서 5종 진행 상태 | 제출/보고 준비 누락 여부 확인 필요 |

5일차 산출물 6개가 비어 있으면 6일차 보고 정리가 지연된다. 따라서 6일차 시작 전 또는 시작 직후 30분 안에 5일차 산출물을 먼저 채우고, 이후 보고용 정리와 PPT 제작으로 넘어간다.

## 팀원 작업 시간 운영

### 작업 묶음 1. 기획 산출물 점검

| 산출물 | 확인할 내용 | 상태 기록 |
|---|---|---|
| 기획서 | 프로젝트 배경, 목표, 주요 사용자, MVP 범위가 들어갔는지 | 완료/보완 |
| 화면정의서 | 주요 화면과 사용자 흐름이 보고 가능한지 | 완료/보완 |
| ERD | 핵심 entity와 관계가 MVP 범위를 감당하는지 | 완료/보완 |
| API 명세서 | 주요 endpoint, 권한, 응답 형식이 정리됐는지 | 완료/보완 |
| 개발 명세서 | Week 2 착수 기준, 검증 기준, 담당 기준이 있는지 | 완료/보완 |
| 협업 규칙 | AGENTS, CLAUDE, CONTRIBUTING, PR Template, CI, AI 규칙이 개발에 적용 가능한지 | AGENTS/CLAUDE/CONTRIBUTING 완료, PR Template/CI 기준 완료. 실제 CI workflow는 skeleton 이후 |

### 작업 묶음 2. MVP freeze

| 구분 | 처리 기준 |
|---|---|
| 필수 기능 | Sprint 1 또는 6주 구현 계획에 포함 |
| 선택 기능 | 보고에는 가능하면 언급하되 Sprint 1에는 넣지 않음 |
| 보류 기능 | 구현 범위에서 제외하고 이유를 짧게 기록 |
| 변경 필요 기능 | Week 2 시작 전 승인 필요 작업으로 분리 |

### 작업 묶음 3. 보고 순서

| 순서 | 보고 파트 | 내용 |
|---:|---|---|
| 1 | 프로젝트 배경 | 왜 그룹웨어 클라우드 플랫폼인가 |
| 2 | 프로젝트 목표 | 한 줄 목표, 주요 사용자 |
| 3 | 팀 구성과 역할 | 황스일, 정철진, 담당 그룹 구조 |
| 4 | MVP 범위 | 필수/선택/보류 기능 |
| 5 | 사용자 시나리오 | 일반 사용자/관리자 흐름 |
| 6 | 화면 구성 | 주요 화면 목록 |
| 7 | DB/API 설계 | ERD 초안, 주요 endpoint |
| 8 | System Architecture | Spring Boot, MySQL 8.4, AWS EC2/RDS/S3 구조 |
| 9 | 협업 방식 | AGENTS, CLAUDE, CONTRIBUTING, PR Template, CI, docs 운영 |
| 10 | 개발 착수 계획 | Sprint 구조와 Week 2 Backlog |
| 11 | 리스크와 대응 | AWS, DB, 인증, 일정 리스크 |

### 작업 묶음 4. 핵심 흐름 요약

| 단계 | 흐름 | 확인 기준 |
|---:|---|---|
| 1 | 로그인/회원가입 흐름 | 사용자 진입 흐름이 이해되는지 |
| 2 | 회사/프로젝트 진입 | 협업 공간 구조가 보이는지 |
| 3 | 프로젝트 홈/칸반 | 핵심 업무 관리 흐름이 보이는지 |
| 4 | 이슈 상세/문서 연결 | 문서와 업무 연결 가치가 보이는지 |
| 5 | 채팅/쓰레드/알림 | 협업 흐름이 하나의 제품처럼 연결되는지 |

핵심 흐름 요약은 실제 구현 화면 계획이 아니라 기획 내용을 설명하기 위한 순서다. Sprint 1 Backlog에 모두 넣지 않는다.

### 작업 묶음 5. 리스크 메모

| 리스크 | 영향 | 대응 |
|---|---|---|
| MySQL 8.4 실행 방식 | local DB와 RDS 배포 환경 차이 | Sprint 1은 local 연결 기준을 먼저 잡고, RDS는 Sprint 1 이후 배포 단계에서 적용 |
| React + Next 구조 과설계 | Frontend 구조 지연 | 초기에는 기본 routing/layout 중심으로 제한 |
| AWS 배포 시점 | 배포 작업이 Sprint 1 구현 범위를 압박할 수 있음 | EC2/RDS/S3 사용은 확정하되 실제 배포와 S3 파일 저장 구현은 Sprint 1 이후로 배치 |
| 인증/인가 복잡도 | 구현 지연 | A/P/C 권한 기준으로 제한하고 변경은 승인 필요 작업 처리 |
| 기능 범위 과다 | 통합 실패 | MVP 필수 기능 중심으로 freeze |
| CI 설정 지연 | PR 품질 관리 실패 | 초기에는 `./gradlew test`만 적용 |
| 문서와 코드 불일치 | 협업 혼선 | PR Template에 문서 변경 여부 체크 포함 |
