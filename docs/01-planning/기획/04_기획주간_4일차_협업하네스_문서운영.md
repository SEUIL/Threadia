# 기획주간 4일차 협업 하네스와 문서 운영

## 목적

4일차는 팀원이 같은 방식으로 개발하고 검증할 수 있도록 **문서 구조, AGENTS.md, PR Template, CI 기준**을 정하는 날이다.

3일차 산출물로 **ERD 초안 v1.4**, **API 명세서 초안 v1.4**, **권한 정책 초안**, **기획서 초안**, **v2 기획 산출물**이 준비되었으므로, 4일차에는 이를 repository 운영 규칙과 개발 협업 기준으로 연결한다.

기획주간을 다시 6일 구조로 운영하므로 4일차는 협업 하네스에 집중하고, Sprint 1 Backlog/검증 기준은 5일차, 발표/리스크/Week 2 진입 점검은 6일차로 넘긴다.

## 팀원 작업 시간 운영

### 작업 묶음 1. repository 문서 구조

현재 repository에는 `docs/` 구조와 `docs/README.md`가 있으므로 4일차 기준으로는 문서 구조가 충분히 준비된 상태로 본다. 다만 `docs/00_INDEX.md`는 현재 없으므로, 만들지 여부는 팀이 후속으로 결정한다.

```text
project-root/
├─ README.md
├─ AGENTS.md
├─ CLAUDE.md
├─ CONTRIBUTING.md
└─ docs/
   ├─ README.md
   ├─ 00-project/
   ├─ 01-planning/
   ├─ 02-requirements/
   ├─ 03-design/
   ├─ 04-api/
   ├─ 05-architecture/
   ├─ 06-meetings/
   ├─ 07-decisions/
   └─ assets/
```

문서 구조를 만들 때 3일차 산출물은 `docs/01-planning/기획/03_기획주간_3일차_자료/최종 산출물/` 아래에 유지한다. `docs/00_INDEX.md`나 `현행_` 문서가 별도로 필요한지는 개발주간 문서 운영 기준을 정할 때 후속 결정한다.

### 작업 묶음 2. AGENTS.md / CLAUDE.md / CONTRIBUTING.md 최소 규칙

회의 전 자료로 [[협업_하네스_최소_규칙_초안]]을 먼저 작성한다. 회의에서는 이 초안을 보고 실제 root 문서에 남길 문장과 팀이 지킬 수 있는 최소 규칙만 확정한다.

2026-06-15 기준으로 아래 파일은 repository root와 `docs/`에 존재한다.

| 파일 | 상태 | 역할 |
|---|---|---|
| `AGENTS.md` | 완료 | 저장소 공통 작업 규칙과 최소 금지사항 |
| `CLAUDE.md` | 완료 | `AGENTS.md` 핵심 내용을 복제한 Claude Code용 진입점 |
| `CONTRIBUTING.md` | 완료 | Git, commit, PR 기준 문서 |
| `docs/AGENTS.md` | 완료 | `docs/` 하위 문서 작업 시 적용되는 AI 작업 규칙 |
| `docs/CLAUDE.md` | 완료 | `docs/AGENTS.md`와 동일한 Claude Code용 문서 작업 규칙 |

검토할 핵심 규칙 후보:

```md
## Git Commit Message

- commit message 첫 줄은 `type(scope): summary` 형식을 따른다.
- 첫 줄 아래에는 번호 목록으로 변경 내용과 변경 이유 또는 영향을 작성한다.
- summary와 본문은 한국어를 허용하며, 일부러 짧게 줄이지 않는다.
- 한 commit에는 한 가지 논리적 변경만 담는다.
- `WIP`, `수정`, `작업중`처럼 의미가 모호한 message는 PR merge 전에 정리한다.
```

### 작업 묶음 3. PR Template 체크 항목

회의 전 자료로 [[PR_Template_체크항목_초안]]을 작성한다. 4일차 최종안은 `PR Template v1.0.md`로 확정했고, 실제 repository에는 `.github/PULL_REQUEST_TEMPLATE.md`를 생성했다.

```md
## 작업 내용

-

## 검증

- [ ] 관련 기능을 직접 실행했다.
- [ ] `./gradlew test` 또는 `./gradlew build`를 실행했다.
- [ ] 실패한 test/build가 없다.

## 보안/승인 체크

- [ ] `.env`, API key, token, password, 개인정보가 포함되지 않았다.
- [ ] DB, 배포, 인증/인가, 보안, 대규모 구조 변경이면 승인자 검토를 요청했다.
```

### 작업 묶음 4. CI 기준

회의 전 자료로 [[CI_검증_기준_회의전_설명]]을 작성한다. 아직 Gradle 프로젝트와 GitHub Actions CI 파일이 없으므로, 이 문서는 팀원이 local 검증과 CI의 차이, `test/build/check` 명령의 의미를 이해하기 위한 설명 자료로 사용한다.

| 단계 | 명령 | 적용 기준 |
|---|---|---|
| 초기 | `./gradlew test` | PR 최소 기준 |
| 안정화 | `./gradlew build` | build 시간이 감당 가능할 때 |
| 확장 | `./gradlew check` | lint/check 도입 후 |

### 작업 묶음 5. AI 사용 규칙

회의 전 자료로 [[AI_사용_규칙_초안]]을 작성한다. 회의에서는 AI 사용을 금지할지보다, 사용했을 때 무엇을 공개하고 어떤 정보는 입력하지 않을지부터 정한다.

| 검토 항목 | 기준 |
|---|---|
| 사용 범위 표시 | PR Template에는 AI 사용 여부 섹션을 두지 않음 |

| 사람 책임 | AI가 만든 코드와 문서는 작성자가 이해하고 검토한 뒤 제출 |
| PR Template 반영 | AI 사용 여부 체크박스는 제외하고 보안/승인 체크만 유지 |

### 작업 묶음 6. 화면 정의서 최종본 / 화면-API 매핑

3일차의 `화면 정의서 v2`를 기준으로 4일차에는 Sprint 1에서 바로 참조할 화면 정의서 최종본을 작성한다. 최종본에는 화면별 목적, 접근 사용자, 주요 데이터, 주요 액션, 연결 기능을 다시 확인하고, 이어서 API 명세서 v1.4와 연결되는 화면-API 매핑표를 만든다.

| 입력값 | 처리 기준 |
|---|---|
| 화면 정의서 v2 | 최종본 기준으로 화면 ID/이름, 목적, 주요 액션 재확인 |
| API 명세서 v1.4 | endpoint, method, 권한 약어 연결 |
| 기능 분해표 v2 | MVP/선택/보류 여부 표시 |

화면 정의서 최종본은 `화면`, `접근 사용자`, `주요 데이터`, `주요 액션`, `연결 기능`을 기준으로 정리한다. 화면-API 매핑표는 화면별로 `화면`, `주요 액션`, `API`, `권한`, `비고`를 갖는 표로 작성한다.

### 작업 묶음 7. AWS 사용 범위

아래 항목은 `보류 기능 최종표`가 아니라, 구현 방식이나 정책을 정해야 하는 기술 검토 목록이다. 4일차에는 목록화하고, 5일차 Sprint 1 Backlog에서 담당 그룹과 결정 시점을 정한다.
