# 기획주간 4일차 협업 하네스와 문서 운영

## 목적

4일차는 팀원이 같은 방식으로 개발하고 검증할 수 있도록 **문서 구조, AGENTS.md, PR Template, CI, AI 사용 규칙**을 정하는 날이다.

## 전회차 입력값

| 입력값 | 없을 때 처리 |
|---|---|
| ERD 초안 | DB 변경 승인 기준만 우선 작성 |
| API 목록 초안 | PR/문서 양식에는 API 변경 여부 항목만 둠 |
| 권한 정책 초안 | 인증/인가 변경은 승인 필요 작업으로 고정 |
| AWS 사용 범위 | EC2/RDS/S3 후보 기준으로 운영 규칙 작성 |
| 승인 필요 작업 목록 | DB, 배포, 인증/인가, 보안, 대규모 구조 변경을 기본값으로 둠 |

## 해야될 목록

| 번호 | 해야될 일 | 산출물 | 권장 담당 그룹 |
|---:|---|---|---|
| 1 | repository 문서 구조 설계 | docs 구조 초안 | 2명 |
| 2 | AGENTS.md 최소 규칙 작성 | 작업/AI/승인 규칙 초안 | 2~3명 |
| 3 | PR Template 체크 항목 작성 | PR 제출 전 체크리스트 | 2명 |
| 4 | CI 검증 기준 정리 | `./gradlew test/build` 기준 | 여도현 우선, 1~2명 |
| 5 | AI 사용 규칙 정리 | 허용/주의/금지 규칙 | 2명 |
| 6 | 팀 공유 문장 작성 | Notion/회의 공유용 운영 문장 | 황스일 종합 |

## 회의에서 먼저 정해야 할 것

| 결정 항목 | 기준 | 결과물 |
|---|---|---|
| docs 구조 | 하나의 docs root, `00_INDEX.md`, `현행_` prefix | 문서 운영 기준 |
| AGENTS.md 범위 | 짧고 실제 지킬 수 있는 규칙 | repository root 규칙 |
| PR Template 필수 항목 | 작업 내용, 검증, AI 사용, 보안/승인 | PR 양식 |
| CI 초기 명령 | 초반은 `./gradlew test`, 안정화 후 `./gradlew build` | CI 기준 |
| AI 사용 규칙 | 사용 허용, 범위 표시, 민감정보 금지 | 팀 규칙 |

## 분업 가이드라인

| 작업 | 권장 인원 | 우선 배치 | 검토자 |
|---|---:|---|---|
| docs 구조 설계 | 2명 | 미배정 | 황스일 |
| AGENTS.md 작성 | 2~3명 | 여도현 포함 가능 | 황스일 |
| PR Template 작성 | 2명 | 미배정 | 황스일, 정철진 |
| CI 기준 정리 | 1~2명 | 여도현 우선 | 황스일 |
| Frontend 협업 기준 | 1~2명 | 정철진 우선 | 황스일 |
| 팀 공유 문장 | 1명 초안, 황스일 종합 | 미배정 | 전체 |

작업은 이름 고정보다 역할과 인원수 중심으로 배정한다. 단, Frontend 협업 기준은 정철진이 중심이 되는 것이 좋고, 검증 기준/기술 리스크 정리는 여도현을 우선 배치한다.

## 오전 회의 운영안

| 안건 | 결정할 내용 | 회의 결과 |
|---|---|---|
| 3일차 설계 리뷰 | DB, API, AWS, 인증/인가 위험 영역 | 승인 필요 작업 기준 |
| 문서 운영 방향 | docs 구조와 `현행_` prefix 사용 여부 | docs 기준 확정 |

| 공유 방식 안내 | Notion에 올릴 문서 톤과 양식 | 팀 공용 문서 기준 |

## 팀원 작업 시간 운영

### 작업 묶음 1. repository 문서 구조

```text
project-root/
├─ README.md
├─ AGENTS.md
├─ .github/
│  ├─ PULL_REQUEST_TEMPLATE.md
│  └─ workflows/
│     └─ ci.yml
└─ docs/
   ├─ 00_INDEX.md
   ├─ 현행_프로젝트_실행가이드.md
   ├─ 현행_API_규칙.md
   ├─ 현행_테스트_기록.md
   └─ 99_보관/
```

### 작업 묶음 2. AGENTS.md 최소 규칙

```md
# AGENTS.md

## 프로젝트 작업 원칙

- 모든 코드는 작성자가 이해한 상태로 제출한다.
- PR 전 관련 기능을 직접 실행한다.
- Spring Boot 기준 최소 검증 명령은 `./gradlew test`다.
- CI가 실패한 PR은 merge하지 않는다.

## AI 사용 규칙

- AI 사용은 허용하되, PR에 사용 범위를 적는다.
- AI가 만든 코드는 작성자가 직접 설명할 수 있어야 한다.
- API key, token, password, `.env`, 개인정보는 AI에 입력하지 않는다.

## 승인 필요 작업

- DB schema 변경
- 배포 설정 변경
- 인증/인가 변경
- 보안 관련 변경
- 대규모 구조 변경
```

### 작업 묶음 3. PR Template 체크 항목

```md
## 작업 내용

-

## 검증

- [ ] 관련 기능을 직접 실행했다.
- [ ] `./gradlew test` 또는 `./gradlew build`를 실행했다.
- [ ] 실패한 test/build가 없다.

## AI 사용 여부

- [ ] 이번 PR에서 AI를 사용했다.
- [ ] AI 사용 범위를 아래에 적었다.
- [ ] AI가 만든 코드를 직접 이해했다.

## 보안/승인 체크

- [ ] `.env`, API key, token, password, 개인정보가 포함되지 않았다.
- [ ] DB, 배포, 인증/인가, 보안, 대규모 구조 변경이면 승인자 검토를 요청했다.
```

### 작업 묶음 4. CI 기준

| 단계 | 명령 | 적용 기준 |
|---|---|---|
| 초기 | `./gradlew test` | PR 최소 기준 |
| 안정화 | `./gradlew build` | build 시간이 감당 가능할 때 |
| 확장 | `./gradlew check` | lint/check 도입 후 |
