# 6일차 발표자료용 리스크 메모

## 전달 목적

이 문서는 6일차 발표자료를 준비하는 팀원들에게 전달할 **리스크/대응 요약 입력값**이다.

발표자료에는 세부 작업 노트가 아니라 아래 4가지를 중심으로 반영한다.

1. Sprint 1 범위를 Auth-only로 제한한 이유
2. 진행 중 정리하면서 해결한 리스크
3. Week 2 시작 전 남은 blocker
4. 발표 슬라이드에 바로 넣을 수 있는 문장

## 발표에 넣을 핵심 메시지

```text
Week 2의 가장 큰 리스크는 기능 부족이 아니라 범위 과확장이다.
그래서 Sprint 1은 Auth-only로 제한하고, invitation은 Sprint 1.5,
회사/프로젝트/이슈 등 도메인 기능은 후속 sprint로 분리했다.
```

```text
Sprint 1에서는 Spring Boot, React + Next.js, MySQL 8.4 기반을 구축하고
이메일 로그인, Google OAuth, 비밀번호 재설정까지 인증 흐름을 local에서 검증한다.
```

```text
AWS는 EC2/RDS/S3 사용 방향만 확정하고,
실제 배포와 S3 파일 저장 구현은 Sprint 1 이후로 분리했다.
```

## 범위 구분

| 구분 | 발표 기준 | 발표자료 반영 위치 |
|---|---|---|
| Sprint 1 | Auth-only. Spring Boot/MySQL/Frontend skeleton, CI/PR baseline, 이메일 로그인, Google OAuth, 비밀번호 재설정, JWT access/refresh 흐름 검증 | Sprint 1 목표/Backlog 슬라이드 |
| Sprint 1.5 | 등록 사용자 대상 app-internal invitation. `invitations` 생성, 기본 7일 만료, lazy expiration, 수락/거절/취소, accept 후 membership 생성 | 후속 범위 또는 invitation 정책 슬라이드 |
| Sprint 2 이후 | 회사/프로젝트/이슈/문서/채팅/DM/쓰레드/알림 구현, invitation email/token link/unregistered onboarding/resend/batch cleanup 고도화 | Roadmap 또는 보류 기능 슬라이드 |

## 해결한 리스크

| 리스크 | 기존 문제 | 해결 내용 | 발표자료 반영 |
|---|---|---|---|
| Sprint 1 범위 과확장 | 회사/프로젝트/이슈/문서/채팅까지 Sprint 1에 섞이면 1주 개발 범위가 과도해진다 | Sprint 1을 Auth-only로 제한했다 | Sprint 1 목표/범위 슬라이드 |
| invitation 범위 혼선 | 초대 기능을 Sprint 1에 넣으면 인증 구현과 도메인 membership 구현이 섞인다 | invitation을 Sprint 1.5 registered-user app-internal invitation으로 분리하고, 기본 7일 만료와 lazy expiration 기준을 확정했다 | Sprint 1.5 또는 후속 범위 슬라이드 |
| JWT 정책 확정 | login/logout/refresh/me 구현 기준이 흔들릴 수 있었다 | access 30분, refresh 14일, refresh token hash 저장, rotation, logout invalidation, access token memory + refresh token `HttpOnly`, `SameSite=Lax` cookie 권장 기준을 확정했다 | 인증 설계/API 슬라이드 |
| `/auth/me` 응답 과확장 | 회사/프로젝트/unread count까지 넣으면 Auth 범위가 커진다 | Sprint 1은 `data.user.id/email/nickname/avatarUrl`만 사용한다 | 인증 API 슬라이드 |
| password reset 발송 방식 | log/local console만 쓰면 실제 검증 기준이 약하다 | Sprint 1은 Google SMTP 실제 발송과 수신 email 확인으로 검증한다 | 인증 검증/API 슬라이드 |
| DB migration 범위 혼선 | MVP 전체 table이 Sprint 1 DB 범위로 오해될 수 있었다 | Sprint 1 DB는 `users`, `oauth_accounts`, `password_reset_tokens`, `refresh_tokens`로 제한했다 | ERD/DB 범위 슬라이드 |
| AWS 범위 과확장 | 실제 배포와 S3 구현이 Sprint 1 일정을 압박할 수 있었다 | EC2/RDS/S3 사용 방향은 확정하되 실제 배포와 S3 파일 저장은 Sprint 1 이후로 분리했다 | Architecture/리스크 슬라이드 |

## 남은 리스크

| 리스크 | 영향 | 대응 계획 | 담당/확인 |
|---|---|---|---|
| 팀원별 Java/Gradle 환경 차이 | 서버 실행과 build 결과가 팀원마다 달라질 수 있다 | Java 17 기준은 확정했다. Week 2 시작 전 팀원별 local 실행을 확인한다 | Backend 담당 |
| MySQL 8.4 실행 방식 차이 | local DB 연결 지연과 API 개발 지연이 생길 수 있다 | Docker 또는 local 설치 기준을 하나로 정하고 연결 test를 먼저 진행한다 | 여도현 |
| React + Next 구조 결정 지연 | Frontend skeleton과 route 작업이 밀릴 수 있다 | 로그인/회원가입 route와 기본 layout 중심으로 먼저 제한한다 | 정철진 |
| Google OAuth 설정 지연 | 소셜 로그인 구현과 검증이 지연된다 | Day 1에 Client ID/Secret, callback URL을 등록하고 secret 비노출 관리 방식을 정한다 | 황스일 + 김민정 |
| Google SMTP 설정 지연 | 비밀번호 재설정 검증이 지연된다 | SMTP credential 관리 방식과 실제 수신 email 확인 절차를 Day 4 전 준비한다 | Backend 담당 |
| CI workflow 생성 시점 | 자동 검증 없이 수동 검증에 의존할 수 있다 | 초기에는 `./gradlew test` 우선, skeleton 이후 GitHub Actions workflow를 생성한다 | 황스일 |
| 문서와 코드 불일치 | 구현 기준이 문서와 달라져 PR review가 어려워질 수 있다 | PR Template에 문서 변경 여부와 검증 기록을 남긴다 | 전체 |

## 슬라이드 문장 후보

### 범위 관리

```text
Sprint 1은 기능을 많이 넣는 것보다 인증 흐름을 끝까지 검증하는 데 집중한다.
```

```text
회사/프로젝트/이슈 등 도메인 기능은 전체 MVP reference로 유지하되,
Sprint 1 구현 commitment에서는 제외했다.
```

### invitation

```text
Invitation은 Sprint 1 인증 구현과 분리해 Sprint 1.5에서 등록 사용자 대상 app-internal invitation으로 처리한다.
```

```text
초대 email 발송, token link, 미가입자 onboarding, resend는 Sprint 2 이후 후보로 분리했다.
```

### 기술 리스크

```text
Week 2 착수 전에는 Java 17 local 실행, MySQL 8.4 연결, Google OAuth, Google SMTP, JWT 정책 반영 여부를 먼저 확인한다.
```

```text
AWS는 사용 방향은 확정했지만 실제 배포와 S3 파일 저장은 Sprint 1 이후로 분리해 일정 리스크를 줄였다.
```

## 발표자료 반영 체크리스트

- [ ] Sprint 1 범위가 Auth-only로 표현되어 있다.
- [ ] Sprint 1.5 invitation이 Sprint 1과 분리되어 있다.
- [ ] Sprint 2 이후 후보가 Sprint 1 구현 범위처럼 보이지 않는다.
- [ ] 해결한 리스크와 남은 리스크가 구분되어 있다.
- [ ] JWT 정책(access 30분, refresh 14일, hash 저장, rotation, logout invalidation, refresh cookie 권장), Google OAuth, Google SMTP, Java 17, MySQL 8.4가 리스크 또는 대응에 들어가 있다.
- [ ] Sprint 1.5 invitation 만료 기준이 기본 7일과 lazy expiration으로 표현되어 있다.
- [ ] AWS는 실제 배포가 아니라 사용 방향 확정으로만 표현되어 있다.
- [ ] 발표 슬라이드에는 문장 3개 이하와 표 1개 정도만 넣는다.

## 발표자료에 넣을 표 추천

발표자료에 표를 1개만 넣는다면 아래 표를 추천한다.

| 구분 | 해결한 내용 | 남은 확인 |
|---|---|---|
| 범위 | Sprint 1 Auth-only 확정 | 후속 sprint 범위가 발표에서 섞이지 않게 설명 |
| 인증 | JWT, OAuth, password reset 기준 확정 | Google OAuth/SMTP 설정 확인 |
| DB | Sprint 1 Auth table 4개로 제한 | MySQL 8.4 local 실행 확인 |
| 인프라 | AWS 사용 방향 확정 | 실제 배포는 Sprint 1 이후로 분리 |
| 협업 | PR/CI/문서 기준 정리 | skeleton 이후 CI workflow 생성 |
