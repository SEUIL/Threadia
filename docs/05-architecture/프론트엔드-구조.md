이 문서는 Threadia 프론트엔드의 폴더 구조, URL 라우팅, API 연동 방식, 인증 토큰 흐름을 정리한다.

### route group `(auth)` vs `(app)` 구분

Next.js의 route group은 괄호 이름 폴더로 **URL에 영향을 주지 않으면서 레이아웃만 분리**한다.

- `(auth)` — 로그인하지 않은 사용자가 접근하는 화면. GNB 없음. 로그인 상태면 `/hub`로 redirect.
- `(app)` — 로그인한 사용자만 접근. `layout.tsx`에서 access token 유무를 확인하고 없으면 `/login`으로 redirect.

두 그룹은 `layout.tsx`를 각각 가지므로 레이아웃이 완전히 분리된다.

## 4. URL 파라미터 네이밍

프론트 URL 파라미터와 백엔드 경로 변수 이름을 아래 기준으로 통일한다.

| 프론트 URL 파라미터 | 백엔드 경로 변수 | 타입 | 비고 |
|---|---|---|---|
| `companyId` | `{companyId}` | number | 회사 ID |
| `projectId` | `{projectId}` | number | 프로젝트 ID |
| `roomId` | `{roomId}` | number | DM 방 ID |
| `docId` | `{documentId}` | number | 문서 ID — 프론트 URL은 `docId`, API 호출 시 `documentId`로 변환 |
| `threadId` | `{threadId}` | number | 쓰레드 ID |

모든 ID는 백엔드 DB의 `BIGINT` PK를 그대로 URL에 사용한다. 별도 slug 변환 없음.

### 4.1 허브 회사 선택 컨텍스트

`/hub`는 회사 선택 상태를 URL query로 받지 않는다. 다중 회사 소속 사용자의 허브 회사 선택은 현재 browser tab의 `sessionStorage`에 `threadia:hubCompanyId`로 저장한다.

이 값은 사용자 편의용 client state이며 권한 근거가 아니다. `/hub` 진입 시 프론트는 `GET /api/v1/users/me/company-memberships`로 받은 `companyMemberships` 안에 저장된 companyId가 있는지 확인한 뒤에만 hub presence, direct-message candidates, notification count 등 company-scoped API에 사용한다. 저장값이 없거나 유효하지 않으면 첫 번째 membership으로 fallback한다.

회사 하위 화면(`/{companyId}/projects`, `/{companyId}/settings` 등)에서 허브로 이동하는 링크는 `/hub`로 이동하기 전에 현재 route의 `companyId`를 같은 tab의 `sessionStorage`에 기록한다. 따라서 URL에는 `/hub?companyId=...`가 노출되지 않지만, 같은 tab 안에서는 현재 회사 허브로 복귀한다. 새 tab, 주소창 직접 입력, bookmark로 `/hub`에 들어오는 경우에는 tab state가 없을 수 있으므로 기본 fallback 규칙을 따른다.

## 5. API 연동

### 5.1 Base URL

```
개발: http://localhost:8080
운영: https://api.threadia.com   (확정 시 업데이트)
```

`frontend/.env.local`의 `NEXT_PUBLIC_API_URL`로 주입한다.  
모든 API 경로는 `/api/v1/...` 형식이다. (OAuth 진입점 `/oauth2/authorization/{provider}` 제외)

### 5.2 인증 토큰 전략

Threadia 프론트는 API 명세서의 확정된 Browser 저장 기준을 따른다.

| 토큰 | 저장 위치 | 만료 | 전송 방식 |
|---|---|---|---|
| access token | **JS 메모리 (모듈 변수)** | 30분 | `Authorization: Bearer <token>` 헤더 |
| refresh token | **HttpOnly cookie** | 14일 (`Max-Age=1209600`) | `withCredentials: true`로 자동 전송 |

**access token을 메모리에 두는 이유**: `localStorage`나 `sessionStorage`는 XSS 공격으로 탈취 가능하다. 메모리 변수는 JS로 직접 접근할 수 없어 더 안전하다. 페이지를 새로고침하면 소멸되지만, 아래 silent refresh로 자동 복구한다.

**refresh token을 HttpOnly cookie에 두는 이유**: JS에서 읽을 수 없어 XSS로 탈취 불가하다. CSRF는 `SameSite=Lax` 설정으로 방어한다.

### 5.3 토큰 흐름 상세

```
[최초 로그인]
  POST /api/v1/auth/login
  ├── 응답: { accessToken, tokenType, expiresIn, user, companies }
  ├── 프론트: accessToken → JS 메모리 변수에 저장
  └── 백엔드: refresh token → Set-Cookie (HttpOnly, SameSite=Lax, Path=/, Max-Age=1209600)

[이후 API 요청]
  axios interceptor가 모든 요청에 자동으로
  Authorization: Bearer <accessToken> 헤더 추가

[access token 만료 또는 페이지 새로고침]
  └── API 응답 401 수신
      ├── interceptor가 POST /api/v1/auth/refresh 호출
      │   (cookie에 있는 refresh token이 자동 전송됨)
      ├── 성공: 새 accessToken 메모리에 저장 → 원래 요청 재시도
      └── 실패 (refresh 만료 또는 revoke): /login 으로 redirect

[로그아웃]
  POST /api/v1/auth/logout
  ├── 프론트: accessToken 메모리 초기화
  └── 백엔드: refresh token DB에서 revoke + Set-Cookie 만료 (Path=/, Max-Age=0)

[비밀번호 재설정 완료]
  POST /api/v1/auth/password-reset/confirm
  └── 백엔드: 해당 사용자의 모든 refresh_tokens revoke
      (기존 access token은 30분 자연 만료에 맡김)
```

구현 위치: [`frontend/lib/axios.ts`](../../frontend/lib/axios.ts)

### 5.4 CORS 및 Cookie 설정 — 백엔드 필요 사항

프론트가 `withCredentials: true`로 요청하므로 백엔드에서 아래 설정이 반드시 필요하다.

| 항목 | 개발 환경 값 | 운영 환경 값 |
|---|---|---|
| `Access-Control-Allow-Origin` | `http://localhost:3000` | 운영 도메인 (와일드카드 `*` 불가) |
| `Access-Control-Allow-Credentials` | `true` | `true` |
| `Access-Control-Allow-Methods` | `GET, POST, PUT, PATCH, DELETE, OPTIONS` | 동일 |
| `Access-Control-Allow-Headers` | `Content-Type, Authorization` | 동일 |

refresh token cookie 설정:

| cookie 속성 | 개발 환경 | 운영 환경 | 이유 |
|---|---|---|---|
| `HttpOnly` | `true` | `true` | JS 접근 차단 |
| `SameSite` | `Lax` | `Lax` | CSRF 방어 |
| `Secure` | `false` | `true` | HTTPS 전용 전송 |
| `Path` | `/` | `/` | 전체 경로에서 전송 |
| `Max-Age` | `1209600` | `1209600` | refresh token 14일 유지 |
| `Domain` | 생략 (localhost) | `api.threadia.com` | 서브도메인 공유 필요 시 조정 |

> **주의**: `Access-Control-Allow-Origin`에 와일드카드 `*`를 쓰면 `credentials: true`와 함께 동작하지 않는다. 반드시 명시적 origin을 지정해야 한다.

### 5.5 axios interceptor 동작 요약

```
요청 전  → Authorization: Bearer <accessToken> 헤더 자동 삽입
응답 401 → POST /api/v1/auth/refresh 호출 (retry 1회)
           성공 → 새 accessToken 저장 + 원래 요청 재시도
           실패 → accessToken 초기화 + /login redirect
그 외 에러 → 호출부로 그대로 전파 (catch에서 처리)
```

### 5.6 OAuth 소셜 로그인 흐름

소셜 로그인은 프론트가 직접 API를 호출하는 방식이 아니라 **브라우저 redirect 방식**을 사용한다.

```
1. 프론트: window.location.href = "http://localhost:8080/oauth2/authorization/google"
   (백엔드 URL로 직접 이동 — axios 호출 아님)

2. 백엔드: Google OAuth 서버로 redirect

3. Google 인증 완료 후 백엔드 callback URL로 redirect
   GET /api/v1/auth/oauth2/callback/google

4. 백엔드: users / oauth_accounts 처리 후 refreshToken cookie 발급
   → Set-Cookie: refreshToken=...; HttpOnly; SameSite=Lax; Path=/; Max-Age=1209600
   → 프론트 /hub 로 redirect
   → accessToken은 URL query/fragment 또는 callback 응답 body로 전달하지 않음

5. 프론트: /hub 마운트 시 AuthProvider가 POST /api/v1/auth/refresh 호출
   → refreshToken cookie가 withCredentials로 자동 전송됨
   → 성공 시 accessToken과 user context를 메모리에 저장
```

> OAuth callback 후 accessToken handoff는 refreshToken cookie + `/api/v1/auth/refresh` 세션 복원 방식으로 구현한다. accessToken을 URL에 노출하지 않는다.

| 회원가입 | `/signup` | 이메일, 비밀번호, 닉네임 입력 |
| 비밀번호 재설정 요청 | `/forgot-password` | 이메일 입력 → 전송 버튼 |
| 비밀번호 재설정 확정 | `/reset-password?token=XXX` | 새 비밀번호 입력 + 확인 |
| 메인 허브 | `/hub` | 로그인 성공 후 도착 화면 (skeleton) |

### 호출 API (Sprint 1)

| Method | Endpoint | 화면 |
|---|---|---|
| POST | `/api/v1/auth/signup` | 회원가입 |
| POST | `/api/v1/auth/login` | 로그인 |
| POST | `/api/v1/auth/logout` | 로그아웃 (GNB) |
| POST | `/api/v1/auth/refresh` | interceptor 자동 호출 |
| GET | `/api/v1/auth/me` | 로그인 상태 확인 |
| GET | `/oauth2/authorization/google` | Google 로그인 시작 (redirect) |
| POST | `/api/v1/auth/password-reset/request` | 비밀번호 재설정 요청 |
| POST | `/api/v1/auth/password-reset/confirm` | 비밀번호 재설정 확정 |

### 폼 유효성 검사 기준 (Sprint 1, 프론트 클라이언트 측)

| 필드 | 규칙 |
|---|---|
| email | 이메일 형식 필수. 전송 전 `trim + toLowerCase` 처리 |
| password (로그인) | 필수 |
| password (회원가입) | 8자 이상, 영문+숫자 조합 |
| password confirm | password 일치 확인 |
| nickname | 2자 이상 100자 이하 |
| newPassword (재설정) | 8자 이상, 영문+숫자 조합 |

> **이메일 정규화**: API 명세서에 따라 모든 이메일 입력은 전송 전 `email.trim().toLowerCase()`로 정규화한다. 백엔드도 동일하게 정규화하지만 프론트도 맞춰서 처리한다.
