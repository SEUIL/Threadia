# 백엔드 구조

이 문서는 Threadia 백엔드의 폴더 구조, Spring Boot 실행 구조, DB 연결 방식, Auth/JWT/OAuth 흐름, 테스트 기준을 정리한다.
프론트엔드 개발자가 API base URL, 인증 API 흐름, CORS·cookie 정책을 맞출 때 이 문서를 기준으로 삼는다.

## 3. Spring Boot application 구조

`BackendApplication`은 Threadia 백엔드의 main entrypoint다.

```text
com.threadia.backend.BackendApplication
```

현재 기본 package는 `com.threadia.backend`다. Spring Boot의 component scan은 이 package 아래를 기준으로 동작한다.

현재 package 역할은 다음과 같다.

```text
com.threadia.backend
├── auth/                 # signup, login, OAuth callback, token issuing domain
│   ├── controller/       # HTTP endpoint와 OAuth handler
│   ├── domain/           # User, RefreshToken, OAuthAccount, PasswordResetToken
│   ├── dto/              # Auth request/response DTO
│   ├── repository/       # JPA repository
│   └── service/          # Auth business logic
├── user/                 # /api/v1/auth/me 조회와 사용자 상태 확인
├── common/               # 공통 응답, error body, exception handler, auth projection
├── config/               # security, JWT, refresh token, cookie, OAuth client 설정
└── BackendApplication.java
```

`/api/v1/auth/me`는 API path는 Auth 하위지만, 현재 구현에서는 user 상태 조회 책임을 분리하기 위해 `user/` package에 둔다.

## 4. datasource / MySQL 연결 구조

백엔드는 `application.properties`에서 datasource를 설정한다.

```properties
spring.application.name=backend
spring.config.import=optional:file:../.env[.properties],optional:file:.env[.properties]
spring.datasource.url=${THREADIA_DB_URL:jdbc:mysql://localhost:3307/threadia_test}
spring.datasource.username=${THREADIA_DB_USERNAME:threadia}
spring.datasource.password=${THREADIA_DB_PASSWORD:}
spring.datasource.hikari.initialization-fail-timeout=0
threadia.jwt.secret=${THREADIA_JWT_SECRET:}
threadia.jwt.access-token-expiration-seconds=1800
threadia.cookie.secure=${THREADIA_COOKIE_SECURE:false}
threadia.refresh-token.expiration-days=${THREADIA_REFRESH_TOKEN_EXPIRATION_DAYS:14}
```

| 설정 | 의미 | 현재 기준 |
|---|---|---|
| `THREADIA_DB_URL` | JDBC URL | 없으면 local test DB 기본값 사용 |
| `THREADIA_DB_USERNAME` | DB 사용자 | 없으면 `threadia` 사용 |
| `THREADIA_DB_PASSWORD` | DB password | secret이므로 repository에 기록하지 않음 |
| `initialization-fail-timeout=0` | Hikari 초기화 동작 | 앱 시작만으로 DB 연결 성공을 단정하지 않음 |
| `THREADIA_JWT_SECRET` | JWT signing secret | 없으면 context load 실패 |
| `THREADIA_COOKIE_SECURE` | refresh cookie Secure 속성 | local 기본 false, `prod` profile은 true 필수 |

DB name과 username의 기본값은 local test 편의를 위한 값이다. Password, root password, JWT secret, OAuth client secret은 secret이므로 `.env` 또는 사용자 환경변수로만 주입한다. Spring Boot 실행은 `spring.config.import`로 repository root 또는 `backend/`의 `.env`를 자동 import한다.

| 항목 | 값 | 설명 |

| Service | `mysql` | compose service 이름 |
| Container | `threadia-mysql84` | 실제 container 이름 |
| Image | `mysql:8.4` | MySQL 8.4 고정 |
| Host port | `3307` | local host에서 접근하는 port |
| Container port | `3306` | MySQL 기본 port |

환경변수는 아래 기준으로 주입한다.

| Compose 변수 | 설명 | 기본값 |

## 6. 테스트 구조

### 6.1 Spring context load 테스트

`BackendApplicationTests`는 Spring Boot application context가 정상 로드되는지 확인하는 기본 테스트다.

```text
backend/src/test/java/com/threadia/backend/BackendApplicationTests.java
```

이 테스트는 skeleton 생성 직후 backend가 최소한의 Spring context를 구성할 수 있는지 확인한다.

### 6.2 MySQL 연결 검증 테스트

`MysqlConnectionTests`는 Sprint 1.1.2의 `test DB 연결 성공` 기준을 검증한다.

```text
backend/src/test/java/com/threadia/backend/MysqlConnectionTests.java
```

테스트 내용은 다음과 같다.

| 검증 | 설명 |
|---|---|
| `JdbcTemplate` 주입 | Spring datasource가 구성됐는지 확인 |
| `SELECT 1` | DB에 실제 query를 실행할 수 있는지 확인 |
| `SELECT VERSION()` | 연결된 DB version 확인 |
| `8.4.x` 검증 | MySQL 8.4 container에 연결됐는지 확인 |

`MysqlConnectionTests`는 아래 조건이 있을 때만 실행된다.

```java
@EnabledIfEnvironmentVariable(named = "THREADIA_DB_PASSWORD", matches = ".+")
```

따라서 단순히 `./gradlew test`가 성공했다는 사실만으로 MySQL 연결 성공을 단정하지 않는다. DB 연결 확인 시에는 `.env` 또는 shell 환경변수로 `THREADIA_DB_PASSWORD`를 주입한 뒤 테스트가 skip되지 않았는지 확인한다.

### 6.3 schema.sql 적용 검증 테스트

`MysqlSchemaValidationTests`는 Docker MySQL 8.4 test DB에 `db/schema.sql`을 적용하고 Sprint 1 Auth 4개 table 생성 여부를 확인한다.

```text
backend/src/test/java/com/threadia/backend/MysqlSchemaValidationTests.java
```

검증 대상은 다음 4개 table로 제한한다. `db/schema.sql`은 전체 MVP DDL을 포함하지만, Sprint 1 backend 검증 범위는 Auth table 중심이다.

| table | Sprint 1 사용 목적 |
|---|---|
| `users` | 이메일 사용자와 OAuth 연결 대상 사용자 |
| `oauth_accounts` | Google OAuth provider 계정 연결 |
| `password_reset_tokens` | 비밀번호 재설정 token hash와 만료/사용 상태 |
| `refresh_tokens` | refresh token hash, rotation, revoke 상태 |

`schema.sql`에는 `DROP TABLE` 구문이 포함되어 있으므로 기존 `threadia_test`가 아니라 임시 검증 DB에서 실행한다. 또한 아래 환경변수가 있을 때만 실행되도록 제한한다.

```java
@SpringBootTest(properties = "spring.jpa.hibernate.ddl-auto=none")
@EnabledIfEnvironmentVariable(named = "THREADIA_DB_PASSWORD", matches = ".+")
@EnabledIfEnvironmentVariable(named = "THREADIA_DB_SCHEMA_VALIDATION", matches = "true")
```

이 테스트는 `schema.sql` 적용 자체를 검증하므로 Spring context 시작 시점의 JPA schema validation은 비활성화한다. JPA Entity와 실제 schema의 정합성은 별도 `JpaSchemaValidationTests`에서 확인한다.


### 6.4 Auth/JWT/OAuth 단위 테스트

Auth 구현 이후에는 DB 없이도 실행되는 controller/service/config 단위 테스트를 둔다.

| 테스트 영역 | 검증 |
|---|---|
| `auth/controller` | signup/login HTTP 응답, validation, error envelope, OAuth handler redirect/cookie |
| `auth/service` | signup/login business logic, Google OAuth user mapping, blind auto-link 금지, ACTIVE-only, refresh token hash 저장 |
| `config/jwt` | JWT 발급, 만료, 변조 검증 |
| `config/cookie` | refresh cookie 속성, prod profile `Secure=true` guardrail |
| `user` | `/api/v1/auth/me` Bearer token 파싱, ACTIVE-only, 401 envelope |

`spring-boot-starter-oauth2-client`가 추가되면 `@WebMvcTest`에도 security filter가 개입할 수 있다. controller 단위 테스트가 SecurityFilterChain이 아니라 controller/error envelope만 검증하는 경우에는 `@AutoConfigureMockMvc(addFilters = false)`로 범위를 명시한다.

## 8. 인증/Auth 구현 시 백엔드 기준

Sprint 1 Auth 구현은 canonical 문서의 hardening 기준을 따른다.

| 항목 | 기준 |
|---|---|
| Email normalization | signup, login, password reset, OAuth, invitation lookup에서 `trim + lowercase` |
| OAuth account link | 이메일만 같다는 이유로 blind auto-link 금지. Google은 `sub`를 `provider_user_id`로 저장 |
| Refresh token | DB 저장, logout 시 revoke, password reset confirm 시 전체 revoke |
| Active user check | login, OAuth callback, refresh, `/auth/me`는 `users.status = ACTIVE` 기준 |
| Google email verification | OAuth callback에서 `email_verified = true`만 허용 |
| Token time | 서버 생성·만료 시각은 UTC 저장, API 응답은 ISO-8601 UTC `Z` |
| Refresh cookie | JSON body 미노출, `Set-Cookie` 전용 전달. `HttpOnly`, `SameSite=Lax`, `Path=/`, `Max-Age=1209600`, 운영 환경 `Secure=true` |
| OAuth access token handoff | URL query/string에 access token을 노출하지 않는다. OAuth redirect 후 `/api/v1/auth/refresh`로 access token을 복구한다 |

프론트엔드는 access token을 JS memory에 저장하고 refresh token은 HttpOnly cookie로 받는 구조를 기준으로 한다. 따라서 백엔드는 CORS와 cookie 정책을 프론트엔드 구조 문서와 맞춰야 한다. Login/OAuth callback은 refresh token cookie를 `Set-Cookie: refreshToken=<refreshToken>; HttpOnly; SameSite=Lax; Path=/; Max-Age=1209600` 형태로 내려준다. refresh는 request body나 Authorization header 없이 refresh cookie만 검증하고, 기존 refresh token을 rotate한 뒤 새 access token과 새 refresh cookie를 내려준다. logout은 access token과 refresh cookie를 함께 검증한 뒤 refresh token을 revoke하고 `Set-Cookie: refreshToken=; HttpOnly; SameSite=Lax; Path=/; Max-Age=0`으로 browser cookie를 만료시킨다. reuse detection과 CSRF 방어는 후속 hardening 범위다.

## 10. 개발 서버 실행

### 10.1 MySQL 8.4 초기화와 schema 적용

팀원이 항상 같은 DB 상태에서 테스트하려면 local Docker volume을 지우고 MySQL을 다시 띄운 뒤 `db/schema.sql`을 적용한다. 이 절차는 `threadia_test`의 기존 데이터를 삭제하므로 local test DB에서만 사용한다. 아래 명령은 repository root에서 실행한다.

```bash
docker compose --env-file .env -f compose.mysql.yml down -v
docker compose --env-file .env -f compose.mysql.yml up -d mysql

set -a
source .env
set +a

until docker exec -e MYSQL_PWD="$THREADIA_DB_PASSWORD" threadia-mysql84 \
  mysqladmin ping -h localhost -u"$THREADIA_DB_USERNAME" --silent; do
  sleep 2
done

docker exec -i -e MYSQL_PWD="$THREADIA_DB_PASSWORD" threadia-mysql84 \
  mysql -u"$THREADIA_DB_USERNAME" "$THREADIA_DB_NAME" \
  < db/schema.sql
```

적용 결과와 MySQL 자체 연결은 다음 명령으로 확인한다.

```bash
docker exec -e MYSQL_PWD="$THREADIA_DB_PASSWORD" threadia-mysql84 \
  mysql -u"$THREADIA_DB_USERNAME" "$THREADIA_DB_NAME" \
  -e "SELECT VERSION(); SELECT 1; SHOW TABLES;"
```

### 10.4 schema.sql 적용 검증

`MysqlSchemaValidationTests`는 `db/schema.sql` 파일 자체가 Auth table을 생성하는지 확인하는 좁은 검증이다. 전체 test 전에는 10.1 절차처럼 Docker volume을 초기화하고 `threadia_test`에 `db/schema.sql`을 직접 적용한다. `MysqlSchemaValidationTests`만 별도로 확인할 때는 기존 test DB를 흔들지 않도록 임시 DB `threadia_schema_validation`에서 실행한다.


## 11. 현재 한계와 후속 작업

| 항목 | 현재 상태 | 후속 기준 |
|---|---|---|
| `db/schema.sql` | 생성됨 | 전체 MVP DDL을 관리하되 Sprint 1은 Auth 4개 table 중심 검증 |
| JPA Entity | Auth 4개 Entity mapping 생성됨 | `db/schema.sql`과 mapping 정합성 유지 |
| Email auth | signup/login/logout/refresh/me 구현 | password reset 구현 필요 |
| Google OAuth | 시작 endpoint, callback, user mapping, refresh cookie 발급 구현 | 실제 browser/Postman 검증 기록 필요 |
| Security config | OAuth login용 SecurityFilterChain과 `/api/**` CORS 설정 있음. 현재 `permitAll`, CSRF disabled | cookie 기반 endpoint의 CSRF와 endpoint별 authorize 정책 재정비 |
| Refresh token lifecycle | 발급, hash 저장, logout revoke, refresh rotation 구현 | reuse detection 구현 필요 |
| Password reset | Entity/schema 기준 존재 | request/confirm API와 성공 시 refresh token 전체 revoke 구현 필요 |
| Rate limiting | 앱 레벨 구현 없음 | login/OAuth/password reset abuse 방어 기준 결정 필요 |
| CI DB test | 아직 없음 | CI에서 MySQL service container 또는 test profile 결정 |

현재 백엔드 구조는 Auth Entity mapping, DB 연결 확인, 이메일 signup/login/logout/refresh/me, JWT 발급·검증, Google OAuth callback, CORS 설정까지 구현된 상태다. production-ready 인증으로 보기 위해서는 CSRF, refresh token reuse detection, rate limiting, endpoint별 authorization 정책이 후속으로 정리되어야 한다.
